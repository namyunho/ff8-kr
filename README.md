# 파이널 판타지 VIII PS1 한국어화

PlayStation용 《파이널 판타지 VIII》(일본판) Disc 1의 한국어 패치 프로젝트다.
분석은 끝났고 지금은 **코드 패치와 번역 삽입** 단계다.

원본 디스크 이미지와 BIOS는 저장소에 포함되지 않는다. 사용자가 직접 준비해
`roms/` 에 둔다. 쓰기는 언제나 `work/patched/` 의 사본에만 한다.

## 확정된 구조 요약

### 디스크

- `MODE2/2352` 단일 트랙, 311,519섹터, 732,692,688바이트
- CRC32 `2319B365` / MD5 `cd2a9d4a…` / SHA-256 `6e26677a…`
- 바깥 ISO9660에는 파일이 **3개**뿐:
  `SYSTEM.CNF`, `SLPS_018.80`, `FF8DISC1.IMG`
- `FF8DISC1.IMG` 첫 섹터가 `(u32 절대 LBA, u32 크기)` 목차이며 유효 엔트리
  **134개** (필드 98 / MIPS 오버레이 12 / LZSS 4 / AKAO 4 / 폰트 1 / TIM 1 / 미상 14)
- 목차가 가리키는 가장 높은 끝 LBA 는 **99,306**. 그 뒤 `LBA 99,307 ~ 311,368`
  (약 434MB)은 목차에 없고 `SMJ` / `SMN` / `SMR` 매직의 **FMV** 다
- 디스크 전체에 Mode 2 **Form 2 섹터가 하나도 없다.** FMV 를 표준 XA/STR 이
  아니라 일반 데이터로 읽어 자체 디코더로 푼다는 뜻이다
- **비어 있는 곳은 디스크 끝 150섹터(`LBA 311,369 ~ 311,518`)뿐**이다.
  어느 파일 범위에도 목차 참조에도 들어가지 않는다

> `LBA 24 ~ 825` 의 0 은 빈 공간이 **아니다.** `SLPS_018.80` 의 꼬리이며
> PSX-EXE 의 text 크기가 `0x190800` 이라 부팅 때 그대로 RAM 으로 실린다.
> 마찬가지로 목차 엔트리 사이의 간격(약 172MB)도 전부 데이터가 차 있다.
> **색인이 없다는 것과 비었다는 것은 다르다.** 쓰기 전에 반드시 읽어 본다.

> PC판의 `menu.fs` / `Data\menu\…` 경로는 이 디스크에 존재하지 않는다.
> PSX는 파일명 없이 숫자 인덱스로만 접근한다.

### 폰트

- 파일: IMG TOC **#130** (LBA 849, 33,764바이트)
- 글리프 셀 **12 × 12**, 텍스처 4bpp **256 × 252** = 21열 × 21행 = **441칸**.
  셀 하나에 글리프 **둘**이 인터리브되므로 뱅크당 **882칸**
- 실효 계조 4단계 (CLUT 4색이 4회 반복 — 하위 2비트만 색)
- VRAM 슬롯: 뱅크0 **`(960,256)`** / 뱅크1 **`(832,256)`** / CLUT **`(288,224)`**
- 뱅크0 은 부팅 때 한 번 올라가고, 뱅크1 은 **필드마다 다른 한자표(TDW)** 라
  필드에 들어갈 때마다 오버레이가 새로 적재한다

> **뱅크 좌표를 한동안 거꾸로 적고 있었다.** 적재기의 뱅크 분기(`0x8002c3b8`)가
> `bne t0, zero` 라 **떨어지는 쪽이 뱅크0**(`x=0x3C0`=960)인데, 의사코드의
> `if (bank != 0) { … }` 블록을 분기가 간 쪽으로 읽으면 갈래가 통째로 뒤집힌다.
> 실행 중 VRAM 을 폰트 파일과 대조해 바로잡았다 — `x=960` 이 원본 폰트와
> **32,256바이트 전부 일치**한다.

- **적재기는 압축을 풀지 않는다.** 하는 일은 폭 테이블 452바이트 복사와
  `LoadImage` 호출 둘뿐이다. 452 는 두 폭 테이블 사이의 정확한 간격이다
  (`0x800821F8` → `0x800823BC` → 다음 구조체 `0x80082580`)

> **CLUT 은 파일이 말하는 `(896,256)` 로 가지 않는다.** 적재기가 x·y 를 상수로
> 덮어쓴다(`0x8002c408`: `0x120`=288, `0x8002c410`: `0xe0`=224). 렌더러가 읽는
> 곳도 `(288,224)` 다. 다만 **w·h 는 파일 값을 쓰고**, h 가 17 이상이면 16 으로
> 자르는 검사가 있다(`0x8002c420`). 파일로 제어되는 것과 코드로만 바뀌는 것의
> 경계가 그 함수 안에서 갈린다.

- 팔레트는 **16벌이 짝을 이룬다.** 짝수 글리프용은 픽셀의 하위 2비트로, 홀수
  글리프용은 상위 2비트로 색을 정한다. 렌더러가 인덱스 홀짝으로 고른다
  (`0x8002f098`, CLUT id `0x3812` / `0x3852`). 창 색 테마 8가지 × 2

```text
팔레트 0 (짝수)  0000 d294 b18c a96a | 반복
팔레트 1 (홀수)  0000 0000 0000 0000 | d294 x4 | b18c x4 | a96a x4
```

### 텍스트 인코딩

| 바이트 | 의미 |
|---|---|
| `0x00` | 종료 |
| `0x01` / `0x02` | 줄 초기화 / 줄바꿈 |
| `0x05` + 1B | 변수 삽입 |
| `0x07` | 페이지 리셋 |
| `0x18`~`0x1B` + 1B | 2바이트 문자, 뱅크 0 |
| `0x1C`~`0x1F` + 1B | 2바이트 문자, 뱅크 1 |
| `0x20`~`0xFF` | 1바이트 문자 (`index = byte − 32`) |

### 텍스트 경로

```text
field.bin(TOC#2) → 해제본 +0x28668 목록 1,003엔트리
  → 3종 세트 [MIM, DAT, LZK] 반복. DAT 는 인덱스 ≡ 2 (mod 3)
  → DAT 섹션 포인터 [8] = MSD, 형식은 [u32 오프셋 배열], N = offset[0]/4
```

목록 1,003엔트리를 전수로 훑으면 **DAT 304개**이고 그중 2개는 MSD 가 비어 대사가
없다. 남은 302개에 **MSD 메시지 9,442건**이 있다. DAT 는 목록만으로 가려지지
않고, 해제한 뒤 포인터 12개가 단조 증가하고 `ptr[11]` 이 해제 크기와 맞물리는지로
판정한다.

메뉴 계열은 따로다 — `mngrp.bin`(TOC#22) 서브엔트리 1, 2단 u16 상대 오프셋 표,
그룹 16, 메시지 579건.

### 글리프 대응표

`data/glyph-map-bank0.json` 이 정본이다. 뱅크0 882칸 중 **픽셀이 있는 879자
전부**에 문자를 배정했다(63은 공백, 880·881은 쓰이지 않는 빈 자리).

눈으로 읽은 값이라 세 가지로 되짚었고 셋 다 오류를 잡아냈다.

1. 같은 문자가 두 인덱스에 배정됐는지 — 816(間→聞), 577(客→各)
2. 글리프와 배정 문자를 나란히 렌더해 대조 — 347..351 이 한 칸씩 밀려 있었다
3. 실제 대사를 디코드해 일본어로 읽히는지 — 749(償→後), 350(術→出)

2번은 특히 중요하다. **오십음순 구간이라도 통째로 밀리면 순서 검산으로는
잡히지 않는다.**

### 번역문이 들어갈 자리

인덱스 `0..223` 은 1바이트, `224` 이상은 2바이트로 실린다. 일본어는 가나가 많아
글리프의 **84.7%가 1바이트**이고 글자당 평균 1.15바이트다.

| 시나리오 | 탐욕 압축 | **최적 파싱 압축** |
|---|---|---|
| 손대지 않고 재압축만 | 2 / 302 | **0 / 302** |
| 한글을 전부 224 뒤에 (최악) | 27 / 302 | **0 / 302** |
| 빈도 상위 224자를 1바이트 자리에 | 0 / 302 | **0 / 302** |

압축기를 최적 파싱으로 바꾸자 **최악 시나리오조차 전부 들어간다.** 배치
최적화는 이제 필수가 아니라 여유를 늘리는 수단이다. 그래도 본문이 심하게
쏠려 있어(가장 잦은 224자가 본문의 93.00%를 덮는다) 상위 224자를 1바이트
자리에 놓으면 글자당 평균이 1.07바이트로 지금(1.15)보다 작아진다.

최악 시나리오는 **번역문의 글자 수가 원문과 같다**고 본 것인데, 초벌번역으로
확인했다. 그려지는 글자가 원문 대비 **0.98배**로 오히려 줄었다.

### 실제로 필요한 글자 수 — 실측

기계 초벌번역(실제 대사 99.6%)을 세었다.

| 항목 | 값 |
|---|---|
| 필드 대사 원문 | 287,804자 |
| 번역문 | 235,220자 (원문의 **0.82배**) |
| 서로 다른 음절 | **1,038** |
| Heaps 곡선 | **V = 71.5 × N^0.22** |

곡선이 매우 완만하다. 표본을 50배 늘리는 동안(4,714자 → 235,220자) 음절은
429 → 1,038 으로 **2.4배**밖에 안 늘었다. 그래서 남은 텍스트를 더해도 크게
늘지 않는다.

| 남은 원문 | 총 음절 추정 |
|---|---|
| 20,000자 (메뉴·이름류) | 1,078 |
| 50,000자 (튜토리얼 포함) | 1,094 |
| 100,000자 (설명문 전부) | **1,117** |

**부호·숫자·라틴 63칸을 더해도 1,180 안팎**이다. 4중 인터리브의 1,512칸이면
여유가 330 이상 남는다.

> **카타카나는 음절을 덜 요구한다.** 메뉴·아이템은 카타카나 비율이 47.0% 로
> 필드 대사(20.7%)의 두 배가 넘는다. 처음엔 불리한 조건으로 봤는데 실측은
> 반대였다 — 같은 글자 수로 견주면 카타카나 많은 쪽이 **0.67배**의 음절만
> 쓴다. 음역은 `라 이 스 트 크 로 드` 같은 좁은 집합을 되풀이하는 반면
> 한국어 산문은 훨씬 넓은 어휘를 쓰기 때문이다.

가장 잦은 224자가 본문의 **89.1%** 를 덮으므로, 그 자리를 1바이트 구간에
놓으면 글자당 평균 **1.11바이트**다. 자세한 내용은
[`docs/translation-pipeline.md`](docs/translation-pipeline.md) 를 본다.

## 4중 인터리브 — 882 → 1,512칸

4bpp 픽셀에 글리프를 **1비트씩 4개** 넣는다. 갈무리는 원래 1비트 픽셀 폰트라
**화질 손실이 0** 이다.

```text
평면 = (뱅크비트 ? 2 : 0) | (인덱스 & 1)
셀   = (인덱스 & 0x3FF) >> 1          378칸 x 4 = 1,512
```

**텍스처는 뱅크0 것 하나만 쓴다.** 뱅크1 에서는 인코딩 공간과 폭 테이블만
빌린다. 이게 핵심이다.

| | 필요 | 있는 것 |
|---|---|---|
| 인코딩 | 1,512 | 896 + 896 = **1,792** |
| 폭 테이블 | 1,512 | 904 + 904 = **1,808** |
| 텍스처 | 1,512 | 378칸 × 4 = **1,512** |

텍스처가 441칸이 아니라 378칸인 이유는 **팔레트 32벌을 둘 자리** 때문이다.
원본 CLUT 아래 16줄 `(288,240)` 을 쓰려 했는데 남의 CLUT 가 덮는 자리였다
— 실기에서 뱅크1 글자만 노이즈로 나왔다. 유일하게 안전한 것이 증명된
뱅크0 텍스처 사각형 안쪽으로 옮기고 21행을 18행으로 줄였다.

    텍스처   (960,256)  256 x 216   21 x 18 = 378칸
    CLUT     (960,472)  16 x 32     뱅크0 472~487 / 뱅크1 488~503

### 왜 뱅크1 의 VRAM 을 쓰지 않는가

앞서 뱅크1 의 `(832,256)` 을 통째로 뺏는 안을 구현해 실기까지 갔다가 무너졌다.
**동영상이 그 자리를 지운다.**

```text
동영상 두 편을 지난 뒤
  (960,256) 뱅크0 텍스처   100% 살아남음
  (832,256) 뱅크1 텍스처   32.5% 만 남음
```

스톡에서는 필드에 들어갈 때 한자표가 다시 올라와 그 자리를 채운다. 그런데 그
적재를 막는 것이 뱅크1 재활용의 전제였다 — **자리를 뺏는 순간 되살릴 방법도
같이 없앤 것**이다. 옮겨 갈 안전한 VRAM 도 없었다(예전에 비어 보이던
`x=448..831` 은 타이틀 화면 시점의 관측이고 게임이 돌면 차 있다).

4중 인터리브는 **게임이 이미 우리 것으로 인정한 자리의 밀도만** 올린다.

### 팔레트 — 한 번 틀렸다

평면이 넷이니 팔레트도 테마당 넷이 필요하다. 처음에는 원본 CLUT 아래 16줄
`(288, 240~255)` 이 실측으로 **완전히 비어 있어** 거기에 얹었다.

**틀렸다.** 실기에서 뱅크1 글자만 노이즈 블록으로 나왔다. 실행 중 VRAM 32줄을
폰트 파일과 대조하니 앞 16줄만 우리 것이었다.

```text
행별 일치 (224~255)   OOOOOOOOOOOOOOOOXXXXXXXXXXXXXXXX
```

적재기는 32줄을 제대로 올린다 — **올린 뒤에 폭 16짜리 남의 CLUT 가 덮는다.**
한 시점의 0 은 빈 자리가 아니다. 같은 함정이 이 프로젝트에서 네 번째다.

그래서 **뱅크0 텍스처 사각형 안쪽**으로 옮겼다. 동영상 두 편 뒤에도 100%
온전한 것이 실측된 유일한 자리이고, 폰트가 적재될 때마다 우리가 다시 쓴다.
대신 텍스처를 21행에서 18행으로 줄여 아래를 비웠다 — 이것이 1,764 → 1,512 의
정체다.

```text
기준줄 +0~15    테마8 × 짝/홀   -> 평면 0, 1     y=472~487
기준줄 +16~31   테마8 × 짝/홀   -> 평면 2, 3     y=488~503
```

16줄 = `16 × 0x40` = **`0x400`** 이고 뱅크 비트가 `s0 & 0x400` 이라 **이미 그
자리에 있다.** 시프트조차 필요 없다 — 그래서 옮길 때도 이 관계는 지켜야 한다.
x 방향으로 옮기려면 `srl` 이 하나 더 드는데 그리기 패치에 빈 슬롯이 없다.

### EXE 패치 — 바뀐 워드 41개

| 자리 | 전 → 후 |
|---|---|
| `0x8002c420` | `slti 0x11` → `0x21` — CLUT 높이 32 허용 |
| `0x8002c470` | `0x1c0`(448) → `0x370`(880) — 폭표 **884바이트** 복사 |
| `0x8002c3b8` | 필드 한자표 적재 차단 |
| `0x23bc` 7곳 | → `0x23b1` — 통합 폭표의 뱅크1 시작(`0x21f8`+441) |
| `0x8002c408` | `0x120` → `0x3c0` — CLUT 적재 x = 960 |
| `0x8002c410` | `0xe0` → `0x1d8` — CLUT 적재 y = 472 |
| `0x3812` 5곳 | → `0x763c` — CLUT id 기준 `(472<<6) | (960>>4)` |
| 그리기 4곳 | tpage 분기 6슬롯 교체 |

그리기 자리가 안전한 이유가 있다. CLUT 계산 지점에는 빈 슬롯이 없는데,
**tpage 분기가 통째로 필요 없어진다** — 두 뱅크가 같은 텍스처를 쓰므로.

```asm
lui  tp, 0xe100
ori  tp, tp, 0x41f      뱅크0 tpage 로 고정
lhu  at, off(prim)      아까 저장한 CLUT
addu at, at, v0         += 뱅크비트. v0 에 이미 들어 있다
sh   at, off(prim)
andi idx, idx, 0x3ff
```

**분기 목적지가 하나도 안 움직인다.** 네 자리가 완전히 균일하고, 매 자리에서
분기 직전에 `v0 = idx & 0x400` 이 이미 계산돼 있다.

### 디스크 발자국

폰트가 29,596바이트로 원본(33,764)보다 **작다.** LBA 849 에 배정된 17섹터
안에 15섹터로 들어간다. LBA 를 옮기지 않고 TOC 의 크기 필드 4바이트만 고친다.

| | 뱅크1 재활용 (폐기) | **4중 인터리브** |
|---|---|---|
| 칸 수 | 1,764 | 1,512 |
| 디스크 변경 | 꼬리 35섹터 + TOC + EXE | **폰트 17섹터 + EXE + TOC 4바이트** |
| 부팅 훅 | 필요 | **없음** |
| 동영상에 지워지는가 | **지워짐** | 안 지워짐 (실측) |

### 확인 방법

화면을 보는 것은 약한 증거다 — 글자가 이상해도 적재 실패인지 배치표가 달라서
인지 구별되지 않는다. **실행 중 VRAM 을 폰트 파일과 바이트로 맞춘다.**

## 도구

| 도구 | 용도 |
|---|---|
| IDA Professional 9.4 + `idalib-mcp` | 주력 정적 분석, xref, 바이트 질의 |
| Ghidra 12.1.2 + GhidraMCP | MIPS 디컴파일 교차검증 |
| `scripts/mips_asm.py` · `mips_dis.py` | MIPS R3000 조립·해체. **외부 도구를 쓰지 않는다** |
| mkpsxiso / dumpsxiso | 디스크 구조 덤프·재구성 대조 |
| xdelta3 | 배포용 차분 패치 |
| DuckStation | 최종 육안 확인. 스크립팅 API 가 없어 자동화되지 않는다 |
| PCSX-Redux | 런타임 조사 — 웹 API 로 RAM/VRAM 통째 덤프, GDB 스텁으로 레지스터 |
| LM Studio / Ollama | 로컬 초벌번역 엔드포인트. OpenAI 호환 HTTP 라 MCP 불필요 |

IDA와 Ghidra는 대체 관계가 아니라 **서로 다른 실패 형태를 잡는 상보 관계**로
쓴다. 실제로 두 도구의 교차검증으로 "게임이 TIM header의 RECT 대신 하드코딩된
VRAM 좌표를 쓴다"는 판정을 얻었다.

조립기를 직접 짠 이유는 **왕복 검산**이다. 조립한 바이트를 도로 해체해 원래 적은
명령과 맞춰 보면 인코딩 실수로 다른 명령이 조용히 박히는 사고를 막을 수 있다.
EXE 전체 **399,789개 명령**을 해체했다가 다시 조립해 바이트가 전부 일치한다.

해체기는 예약 필드가 0 이 아니면 `.word` 로 낸다. `.text` 에 섞인 문자열을 명령
으로 읽어 주면 없는 코드를 보게 되고, 패치 자리를 그렇게 고르면 조용히 망가진다.

### 런타임 조사에서 쓴 것

에뮬레이터는 웹 API(`http://127.0.0.1:8080/api/v1`)로 RAM 2MB 와 VRAM 1MB 를
통째로 준다. 레지스터는 GDB 스텁(포트 3333)에서 받는다. 크래시를 추적할 때는
BIOS 의 프로세스 제어 블록(`[0x0108]` → TCB)에서 **EPC** 를 꺼내 터진 명령을
짚었다 — GDB 가 EPC 를 따로 내주지 않기 때문이다.

### 텍스트 표기 규칙

`ja` 칸은 **제어 코드를 하나도 버리지 않는다.** 대사 사이의 코드를 지우면 창
밖으로 흘러넘치거나 이름·수치 삽입이 깨진다. 줄바꿈 `02` 도 개행 문자로 펴지
않는다 — 표 계열 편집기를 거치면 조용히 사라지는 쪽이 개행이다.

```text
カドワキ先生{02}「あぁ、{03:30}。{02} 私はチョット保健室をあけるんで{02} 後はよろしく頼むよ」
```

| 표기 | 뜻 |
|---|---|
| `{01}` | 파라미터 없는 제어 코드 |
| `{03:30}` | 파라미터 있는 제어 코드 |
| `{b1:123}` | 필드 전용 폰트(뱅크1) 글리프 |

`decode` 한 문자열을 `encode` 하면 원본 바이트가 그대로 나온다. 필드 302개
9,442 메시지에서 왕복 실패 0건이다.

### 줄과 쪽을 재는 규칙

**줄을 끊는 것은 `{02}` 하나가 아니다.** `{01}` 은 행 카운터를 1로 되돌리므로
(`sub_8002E4A0` 확정) 폭과 줄 수를 잴 때 함께 나눠야 한다. 842건이 이 코드를
쓰고, 나누지 않으면 쪽 경계를 넘는 글자가 한 줄로 합산돼 폭이 부풀었다.

| 나누는 방식 | 최대 줄 폭 | 302px 초과 |
|---|---|---|
| `{02}` 만 | 659px | 303건 |
| `{02}` + `{01}` | **448px** | **3건** |

`{b1:N}` 은 제어 코드가 아니라 **화면에 그려지는 글자**다. 폭 계산에서 빼면 안
된다. `scripts/text_metrics.py` 가 이 두 규칙의 정본이며 내보내기·검사기가 함께
쓴다. 바이트 셈은 `ko` 에 `ja` 를 그대로 넣는 항등 시험으로 검증했다 — 9,160건
전부 원본 바이트 수와 정확히 일치한다.

번역을 밖에서 시킬 때는 **꾸러미**로 넘긴다. `--bundle` 이 남은 원문을 한 번에
붙여 넣을 크기로 자르고 지침·용어집을 통째로 넣어 준다. 새 대화창에 파일 하나만
붙여 넣으면 바로 일이 된다. 자르는 단위는 파일 개수가 아니라 메시지 수이며,
**필드 번호 순서를 지켜** 자른다 — 번호가 가까운 필드는 게임에서도 붙어 있는
장면이라 앞뒤 문맥이 살아 있어야 번역이 나아진다. 개발용 디버그 필드는 뒤로
몰아 건너뛸 수 있게 표시한다.

돌아온 답은 `== 필드이름 ==` 절로 나뉜 `id<탭>번역문` 이며, 되받기가 같은
형식을 읽는다. 코드 울타리와 머리말이 섞여 와도 걷어낸다.

**전체 메시지의 34.6%가 다른 곳에도 똑같이 있는 원문이다.** 고유 원문은
6,667종뿐이고, 카드 규칙 안내문 하나가 60곳에 반복된다. `--propagate` 가 같은
원문에 같은 번역을 채워 번역량을 줄이고 표기가 필드마다 갈리는 것을 막는다.

## LZSS — 정본은 우리 코드가 아니라 게임이다

필드 파일은 `[u32][LZSS 스트림]` 이다. 이 압축기로 두 번 실기에서 깨졌고,
**두 번 다 왕복 검사를 통과한 뒤에** 깨졌다.

### ① 선두 u32 는 압축 길이다

해제 크기가 아니다. 원본 필드 613개 전부에서 이 값이 **`디스크 크기 - 4`** 와
같다. 해제기(`0x800393A4`)도 그 값을 `t2` 에 받아 **입력을 소비할 때마다**
줄인다 — 플래그 1, 리터럴 1, 매치 2. 출력이 아니다.

해제 크기를 쓰면 값이 서너 배 커진다(33,080 vs 12,286). 해제기가 스트림이 끝난
뒤에도 계속 읽어 뒤에 있는 아무 데이터나 압축 데이터로 해석하고, 쓰레기를 한참
더 뱉으며 이웃 메모리를 덮는다.

**대사는 멀쩡해 보였다.** MSD 가 파일 앞쪽이라 덮이기 전에 제대로 풀린다.
깨지는 것은 그 뒤에 적재되는 것들이라, 증상이 늘 한 발짝 뒤에서 나타났다 —
동영상이 재생되지 않고, 죽는 자리는 전혀 다른 함수의 memcpy 였다.

### ② 거리 4096 매치는 낼 수 없다

`back = (출력위치 - (offset - 0xFEE)) & 0xFFF` 이라 거리 4096 은 `back = 0` 이
되고, 해제기는 `t1 - 0` 즉 **지금 쓰고 있는 자리**를 읽는다.

**게임에는 진짜 링버퍼가 없다.** 출력 버퍼를 `t1 - back` 으로 직접 되짚는다
(`0x8003946C`). 그래서 쓸 수 있는 거리는 **1~4095** 뿐이다. 링버퍼를 가정한
압축기는 거리 4096 을 "4096바이트 전"으로 여겨 정상으로 취급했다.

### 왜 둘 다 안 걸렸나

**압축기를 우리 해제기로 검산했기 때문이다.** 둘이 같은 잘못된 규칙을 공유하면
왕복 검사는 언제나 통과한다. "무손실 검증 완료"는 참이었다 — **우리 자신에게만**
참이었다.

지금은 `lzss.decode_like_game` 으로 되푼다. 디스어셈블리(`0x800393A4`~
`0x800394F8`)를 그대로 옮긴 것이고, **원본 필드를 먹이면 원본 DAT 가 정확히
나온다**는 것으로 스스로를 검증했다. 압축 필드 613개를 이 기준으로 전수
검산해 실패 0건이다.

> **내 구현끼리 맞춰 보는 검사는 검사가 아니다.** 정본 쪽에서 한 번은 봐야 한다.

## R7 — MSD 가 커지면 뒤 섹션이 밀린다 (해결)

필드 파일은 해제본 머리에 섹션 오프셋 배열이 있고, 대사는 섹션 [8] = MSD 다.
번역문이 원문보다 길면 MSD 가 커지고 **뒤 섹션 오프셋이 전부 밀린다.**

오래 위험 목록에 있었지만 실체는 좁았다. `splice_msd` 는 **처음부터 섹션 표를
제대로 밀고 있었다.** 문제는 **미는 양이 4의 배수가 아닐 수 있다**는 것뿐이다.

밀린 오프셋이 4의 배수를 벗어나면 게임이 죽는다. `0x800394FC` 의 고속 memcpy 가
16바이트씩 `lw` 로 옮기면서 **정렬을 확인하지 않기** 때문이다. 실기에서 그대로
겪었다.

```text
깨진 사본  0x800E80EF  0x800E80F3  0x800EA04B   전부 ≡3 (mod 4)  -> AdEL 예외
깨끗한 것  0x800E8020  0x800E8024  0x800E9F7C   전부 4정렬       -> 정상
```

차이가 정확히 **207바이트**다. 207 은 4의 배수가 아니라서 정렬이 통째로 깨졌다.

원본 DAT **304개의 섹션 오프셋 3,648개가 예외 없이 4정렬**이고 MSD 길이도 전부
4의 배수다. 8·16 정렬은 아니다 — **4정렬이 정확한 불변식**이다.

지금은 `rebuild_msd` 가 길이를 언제나 4의 배수로 맞추고, `splice_msd` 는 미는
양이 4의 배수가 아니면 거부한다. `apply` 는 **원본 크기를 지키는 쪽을 먼저
시도**하고 안 되는 필드만 민다 — 지킬 수 있으면 뒤 섹션이 한 바이트도 안 움직인다.

2뱅크 배치로 전수 측정한 결과다.

| 항목 | 값 |
|---|---|
| 인코딩 | **261필드 전부 성공** (실패 0) |
| 원본 크기 안에 들어감 | 245개 (93.9%) |
| 섹션을 밀어야 함 | 16개, **최대 +56바이트** |
| 민 뒤 섹터가 늘어남 | **0개** — 3개는 오히려 줄어든다 |

> **뱅크1 재활용에는 숨은 대가가 있다.** 원문이 필드 한자표에서 빌려 쓰던
> `ost■□◆◎【】` 9종은 뱅크1 을 뺏으면 존재하지 않게 된다. 뱅크0 만 쓸 때는
> "공짜로 그려지는 글자"라 칸을 안 줘도 됐지만 이제는 칸을 받아야 한다.
> **뱅크 수에 따라 판정이 갈리는 자리다.**
