# 한국어 폰트 삽입 가능성 판정

검토일: 2026-07-27
질문: `fonts/` 에 넣어둔 갈무리 폰트 2종을 FF8 Disc 1에 삽입할 수 있는가.

## 한 줄 답

**화질 문제로는 삽입 가능하다. 제약은 용량 하나뿐이다.**
두 폰트 모두 실제 글리프가 FF8의 12×12 셀에 무손실로 들어간다. 다만 글리프
슬롯이 **882칸**뿐이라 완성형 2,350자를 한 번에 상주시킬 수는 없다.

## 공급 폰트 실측

| 항목 | `galmuri7_8x8_8pt` | `galmuri11_16x16_12pt` |
|---|---|---|
| 파일 | `font-007242d37349daf3.bin` | `font-58c1637749eb0742.bin` |
| 크기 | 18,800바이트 | 75,200바이트 |
| 글리프 수 | 2,350 | 2,350 |
| 바이트/글리프 | 8 | 32 |
| 셀 | 8 × 8, 1bpp | 16 × 16, 1bpp |
| **실측 잉크 범위** | **x 0..6, y 0..6** | **x 2..11, y 3..12** |
| **실효 글리프 크기** | **7 × 7** | **10 × 10** |
| 잉크 폭 분포 | 6px 764개, 7px 1,586개 | 8px 177개, 9px 1,286개, 10px 887개 |
| 잉크 높이 분포 | 6px 55개, 7px 2,295개 | 7px 1개, 9px 55개, 10px 2,294개 |
| 빈 글리프 | 0 | 0 |
| 라이선스 | — | SIL OFL (`OFL.txt` 동봉) |

글리프 인덱스는 `*_glyph_map.json` 의 `{"가": 0, "각": 1, …}` 형태이며 KS X 1001
완성형 2,350자 순서와 일치한다. **조합형이 아니라 완성형 인덱스 폰트다.**

### 12 × 12 적합성

| 폰트 | 12×12 안에 무손실로 들어가는 글리프 |
|---|---|
| `galmuri7` | **2,350 / 2,350 (100 %)** |
| `galmuri11` | **2,350 / 2,350 (100 %)** |

16×16 셀은 대부분 패딩이다. **다운스케일이나 리샘플이 필요 없고, 잉크 영역만
잘라 12×12 셀에 재배치하면 된다.** 픽셀 손실이 0이다.

`galmuri11`(10×10)이 `galmuri7`(7×7)보다 원본 일본어 글꼴의 시각 크기에 가깝다.
원본은 12×12 셀을 거의 채우므로 **`galmuri11` 을 기본으로 권장한다.**

## 대상 측 제약

`docs/font-analysis.md` 에서 확정한 값이다.

| 항목 | 값 |
|---|---|
| 셀 | 12 × 12 |
| 텍스처 | 4bpp, 256 × 252 = 21열 × 21행 = **441칸** |
| 뱅크 | 2개 (VRAM `(832,256)` / `(960,256)`) |
| **총 슬롯** | **441 × 2 = 882칸** |
| 인코딩 표현 범위 | 뱅크당 896, 합계 1,792 |
| 계조 | 하위 2비트만 유효 → 4계조 |
| 폭 테이블 | 452바이트, 니블 단위, 뱅크별 |

### 불가능한 것

**1. 16 × 16 셀로 확대 — 불가능**

셀을 16으로 키우면 텍스처가 `21 × 16 = 336` 픽셀 폭이 필요하다. VRAM 슬롯은
64 halfword = 256픽셀 고정이고, 뱅크 0의 오른쪽은 CLUT(896), 뱅크 1의 오른쪽은
VRAM 경계(1024)다. **가로로 넓힐 공간이 물리적으로 없다.**
다행히 실측 잉크가 10×10이라 확대할 이유도 없다.

**2. 완성형 2,350자 전체 상주 — 불가능**

슬롯 882칸은 2,350자의 **37.6 %**다. 인코딩 공간(1,792)이 더 크더라도 텍스처
칸이 모자란다. 전부 올리려면 `2,350 × 72바이트 = 169,200바이트`의 VRAM이
필요한데, 현재 슬롯 배치로는 배정할 자리가 없다.

## 실현 가능한 경로

### A. 서브셋팅 (권장, 위험 최소)

번역문에 실제로 쓰인 음절만 골라 882칸 안에 넣는다.

- 라틴·숫자·기호에 약 100칸을 남기면 **한글에 약 780칸**
- 한국어 게임 번역에서 실사용 서로 다른 음절은 통상 700~1,300자
- **780칸으로 충분한지는 번역문이 확정된 뒤 실측해야 한다.** 지금 단정할 수 없다.
- 초과하면 B로 넘어가거나 표현을 다듬어 음절 수를 줄인다

작업 단위: `feature/hangul-12x12-font`

### B. 동적 글리프 업로드 (2,350자 전체 지원)

대사 페이지를 그리기 직전에 그 페이지가 쓰는 글리프만 슬롯에 올린다.

- 뱅크 1 `(960,256)` 을 동적 슬롯으로 전용하고 뱅크 0은 고정 문자에 남긴다
- 훅 지점 후보: `sub_8002C358`(적재기) 또는 호출자 `sub_80011CA8`
- 폭 테이블 `0x800823BC` 도 같이 갱신해야 한다
- 위험: 페이지 전환 시 `LoadImage` 지연과 `DrawSync` 타이밍
- 런타임 검증 없이는 진행하지 않는다

작업 단위: `experiment/font-vram-streaming`

### C. PSX BIOS 폰트 활용 — 기각

`roms/scph1001.bin`(미국판, `SCPH1001.BIN` 과 SHA-256 동일)을 역공학한 결과는
다음과 같다.

| 항목 | 값 |
|---|---|
| 비코드 데이터 최대 구역 | `0x06A000..0x07F800`, 88,064바이트 |
| 셀 주기 | 자기상관 결과 **30바이트** (60·90은 배수) |
| 글리프 | **16 × 15 1bpp, 2,934자** (시작 `0x06A01C`) |
| 내용 | **한자(JIS X 0208)** + 악센트 라틴 (`À É Ê Ï Ò Ù Ý` 등) |
| **한글** | **없음** |

한글 유무는 실제 완성형 폰트로 캘리브레이션한 검출기로 판정했다. 완성형은
`가 각 간 갇 갈 …` 순서라 연속 글리프가 초성을 공유하므로 앞부분 바이트가
매우 유사해진다.

| 대상 | 연속 글리프 유사도 |
|---|---:|
| 갈무리11 완성형 2,350자 (기준) | **0.986** |
| BIOS 한자 폰트 | 0.595 |
| SCPH-1001 전 구간 최고치 | 0.90 (전부 패딩·라틴·한자) |

미국판 BIOS에도 한자가 있는 이유는 **메모리카드 세이브 제목이 Shift-JIS**라
지역과 무관하게 렌더링해야 하기 때문이다.

**BIOS 글리프를 한글로 바꿔 쓰는 방안도 기각한다.** 근거는 다음과 같다.

1. **FF8은 BIOS를 호출하지 않는다.** 실행 파일에서 BIOS ROM 주소
   (`0xBFC00000..0xBFC7FFFF`) 상수 참조가 **0회**이고, BIOS 콜 게이트 스텁
   (`li $t2, 0xA0/0xB0/0xC0` + `jr $t2`)도 4바이트 정렬 위치에 없다. 텍스트는
   전부 자체 VRAM 텍스처와 자체 글리프 인덱스로 그린다.
2. **참조하도록 고쳐도 이득이 없다.** 병목은 글리프 **원본 데이터**가 아니라
   VRAM 슬롯 441/882칸이다. BIOS에서 읽어오든 디스크에서 읽어오든 결국 같은
   슬롯에 `LoadImage` 해야 하므로 수용량이 1칸도 늘지 않는다.
3. **형식이 안 맞는다.** BIOS 폰트는 16 × 15, 게임 셀은 12 × 12다. 축소하면
   화질이 나빠진다. 갈무리는 10 × 10이라 축소가 필요 없다.
4. **배포할 수 없다.** 수정 BIOS는 Sony 저작권 펌웨어이고, 실기에서는 ROM 칩
   이라 교체가 불가능하며, 사용자가 어떤 BIOS를 쓰는지 보장할 수 없다. 특정
   BIOS에 의존하는 패치는 대부분의 사용자에게서 깨진다.

디스크 쪽이 모든 면에서 우월하다. 폰트 파일 #130을 교체하고, 필요하면 뱅크 1용
두 번째 파일을 추가하는 것이 정답이다.

### D. 조합형 합성 — 비권장

초·중·종성 자모를 칸에 넣고 런타임 합성하면 슬롯을 크게 아낄 수 있다. 그러나
12픽셀에서 받침 있는 음절의 가독성이 무너진다. 완성형 비트맵이 이미 있는
상황에서 택할 이유가 없다.

## 변환 시 지켜야 할 것

1. **1bpp → 4bpp**: 갈무리는 1bpp다. `0 → 0`, `1 → 3` 으로 확장한다.
   픽셀의 상위 2비트는 팔레트 뱅크 선택용이므로 건드리지 않는다.
2. **계조 차이**: 원본 일본어 글꼴은 4계조로 안티에일리어싱돼 있고 갈무리는
   1bpp다. 그대로 넣으면 한글만 또렷하고 일본어만 부드러워 보인다. 화면에서
   확인한 뒤 필요하면 가장자리에 계조 1단계를 넣는다.
3. **셀 안 배치**: 10×10 잉크를 12×12 셀에 넣을 때 좌우 1픽셀씩 여백을 준다.
   기준선은 원본 가나의 기준선에 맞춘다.
4. **폭 테이블**: 한글은 전각이므로 대부분 `13`(글리프 12 + 간격 1)을 쓴다.
   `sub_8002E3EC` 규칙대로 니블 단위로 채운다.
5. **인코딩 배정**: 한글을 뱅크 1에 두면 2바이트 lead `0x1C`~`0x1F` 를 쓴다.
   완성형 음절 → 글리프 인덱스 매핑표를 따로 만들어 추적한다.

## 다음 게이트

이 판정을 실제 패치로 옮기기 전에 다음이 먼저 닫혀야 한다.

1. **글리프 인덱스 ↔ 문자 대응표** — 어떤 인덱스를 비워도 되는지 알아야
   서브셋 배정을 할 수 있다.
2. **뱅크 1 폰트 파일의 출처** — 뱅크 1에 무엇이 올라가는지 미확정이다.
3. **번역문 확정 후 서로 다른 음절 수 실측** — A안 성립 여부가 여기서 갈린다.
4. **런타임 VRAM 검증** — 슬롯 좌표가 실제 화면에서 그대로 쓰이는지 확인.

## 재현 명령

```bash
# 공급 폰트 실측 (잉크 바운딩 박스)
python3 - <<'PY'
import json
from collections import Counter
for d, name, cw, ch, bpg in (
        ('galmuri7_8x8_8pt',      'font-007242d37349daf3',  8,  8,  8),
        ('galmuri11_16x16_12pt',  'font-58c1637749eb0742', 16, 16, 32)):
    data = open(f'fonts/{d}/{name}.bin', 'rb').read()
    bpr = (cw + 7) // 8
    boxes = []
    for g in range(len(data) // bpg):
        cell = data[g * bpg:(g + 1) * bpg]
        xs, ys = [], []
        for y in range(ch):
            for xb in range(bpr):
                byte = cell[y * bpr + xb]
                for bit in range(8):
                    x = xb * 8 + bit
                    if x < cw and (byte >> (7 - bit)) & 1:
                        xs.append(x); ys.append(y)
        if xs:
            boxes.append((min(xs), max(xs), min(ys), max(ys)))
    fit = sum(1 for a, b, c, e in boxes if b - a + 1 <= 12 and e - c + 1 <= 12)
    print(f'{d}: {len(boxes)}글리프, 12x12 적합 {fit}')
PY
```
