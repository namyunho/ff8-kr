# 실패 기록

이 프로젝트에서 실제로 밟은 함정을 모았다. **다음 타이틀에서 같은 값을 두 번
치르지 않으려고** 쓴다. 그래서 FF8 고유의 사실보다 **어떤 종류의 착각이었는지**를
앞에 둔다.

각 항목은 이렇게 적는다.

    증상 → 무엇을 믿었나 → 무엇이 참이었나 → 어떻게 잡았나 → 다음엔 이렇게

## 1. "0 이라고 빈 자리가 아니다" — 다섯 번 밟았다

가장 비싼 착각이고, **다섯 번 반복했다.** 형태만 매번 달랐다.

| 자리 | 0 이었던 이유 | 실제 |
|---|---|---|
| 목차 사이 간격 | 색인이 없었다 | 데이터가 꽉 차 있다 (약 172MB) |
| `LBA 630~824` | 파일 꼬리라 0 | 부팅 EXE 의 text 로 RAM 에 실린다 |
| EXE 안의 긴 0 구간 | 초기화 안 된 영역 | 실행 중 55~71% 가 찬다 (BSS/힙) |
| VRAM `(288,240)` 16줄 | 관측 시점에 0 | 폭 16짜리 **남의 CLUT** 가 덮는다 |
| EXE `0x8001f5a4` 4KB | 함수 사이 여백처럼 보임 | `jal` 로 불리는 **빈 함수** (nop 1,024개 + `jr ra`) |

마지막 것이 특히 고약했다. 앞이 `jr ra`, 뒤가 함수 프롤로그, 실행 중 RAM 에서도
100% 0 — 여백의 조건을 전부 만족했다. 그런데 **참조를 훑는 검사**가
`0x80011ac0` 의 `jal 0x8001f5a4` 를 잡아냈다. 거기 코드를 얹었으면 그 호출이
글리프 루프로 뛰어들었을 것이다.

게다가 그 함수를 부르는 자리가 이랬다.

```
jal  0x800386ec      CD 읽기
jal  0x8003924c      끝날 때까지 폴링
bne  v0, zero, ...
jal  0x8001f5a4      <- nop 4,096개
```

폴링 직후에 부르는 nop 덩어리는 **하드웨어 지연**일 수 있다. 에뮬레이터는
타이밍을 안 따지므로 즉시 반환으로 바꿔도 통과한다.

**다음엔 이렇게.** 빈 자리는 세 관문을 다 통과해야 쓴다.

1. **파일에서 0 인가** — 필요조건일 뿐이다
2. **실행 중에도 0 인가** — 여러 장면에서 재라. 한 시점은 증거가 아니다
3. **아무도 가리키지 않는가** — 이미지 전체를 훑어 `j`/`jal`/분기 목적지와
   데이터 참조를 센다. **이 검사를 먼저 코드로 만들고 시작하라**

셋을 다 통과해도 남는 위험이 있으면, **칸 수를 줄여서라도 소유가 증명된 자리를
쓴다.** 우리는 팔레트를 폰트 텍스처 사각형 **안쪽**으로 옮기며 칸을
1,764 → 1,512 로 줄였다. 그 사각형은 동영상 두 편 뒤에도 100% 온전한 것이
실측됐고, 폰트가 적재될 때마다 우리가 다시 쓰는 땅이다.

## 2. 에뮬레이터가 봐주고 실기가 안 봐주는 것

**이 프로젝트에서 유일하게 "실기에서만 죽은" 부류다.** 에뮬레이터 검증만 믿으면
끝까지 안 보인다.

### 2-1. 자료구조 정렬 (실제 크래시 원인)

메뉴 텍스트 표를 다시 짜면서 그룹을 그냥 이어 붙였다. 원본은 **16개 그룹의
오프셋이 예외 없이 4의 배수**였고, 머리도 `2 + 16×2 = 34` 에서 끝내지 않고
36까지 채워 두었다.

```
그룹   원본   우리것
  0      36     34
  5    3588   3041
  6    4648   4087
```

그룹 데이터를 워드로 읽는 코드가 있으면 실기에서 **정렬 안 된 `lw` → 주소 오류
예외**다. 크기도 맞고 내용도 맞아서 에뮬레이터 둘(PCSX-Redux, DuckStation)이
모두 통과시켰다.

**같은 규칙을 이미 한 번 배웠다.** 필드 대사(MSD)의 섹션 오프셋 3,648개가 전부
4의 배수라는 것을 R7 때 확인했는데, 메뉴 표에서는 재지 않고 들어갔다.

### 2-2. R3000 적재 지연 슬롯

```
lhu   at, 0x12(prim)
addu  at, at, v0      <- 실기에서는 at 이 아직 옛 값이다
```

MIPS R3000 은 적재한 값이 **바로 다음 명령에서 안 보인다.** 대부분의 에뮬레이터가
이걸 봐준다. 우리 그리기 패치 4곳 전부가 이 위반이었다.

고치는 데 슬롯이 더 들지도 않았다 — 순서만 바꿔 적재와 사용 사이에 두 명령을
끼웠다.

**다음엔 이렇게.** 기계어를 주입하면 **넣은 코드 전체를 훑는 위험 검사**를
같이 만든다. 적재 지연은 기계적으로 잡힌다.

    적재 명령(lb/lh/lw/lbu/lhu/lwl/lwr)의 목적 레지스터를
    바로 다음 명령이 읽으면 위반

### 2-3. 그 밖에 의심 목록

실기에서만 갈리는 것들이라 미리 표로 둔다.

| 종류 | 확인법 |
|---|---|
| 자료구조 정렬 | 원본 오프셋을 전수로 재서 불변식을 찾는다 |
| 적재 지연 슬롯 | 주입 코드 정적 검사 |
| 분기 지연 슬롯 | 훅을 걸 때 원래 지연 슬롯을 보존했는가 |
| 섹터 EDC/ECC | 고쳐 쓴 섹터를 다시 계산해 대조 |
| 동기·헤더·서브헤더 | 사용자 데이터만 갈아 끼웠는가 (EDC 는 이걸 못 잡는다) |
| 타이밍 | 지연 루프처럼 보이는 것을 지우지 않았는가 |

**EDC/ECC 가 맞다고 섹터가 온전한 게 아니다.** EDC 는 오프셋 16부터 계산하므로
앞의 12바이트 동기신호와 4바이트 헤더가 망가져도 검사값은 일관되게 다시
만들어진다. 둘을 따로 대조해야 한다.

## 3. 검사기는 "찾기로 한 것"만 센다

개수를 세는 검사는 **무엇을 안 찾고 있는지 못 알려 준다.** 두 번 크게 데었다.

### 3-1. 상수는 짝을 이룬다

팔레트를 옮기며 `0x3812` 를 찾아 고쳤다. "5곳 찾았고 5곳 고쳤다" 로 검사가
통과했다. 그런데 **홀수 글리프용 `0x3852` 가 4곳 따로 있었다.**

    addiu a0, zero, 0x3812      짝수
    addiu a0, zero, 0x3852      홀수  = +0x40 (한 줄 아래)

결과: 홀수 인덱스 글리프가 **게임 전체에서 안 보이는** 상태로 한동안 굴렀다.
옛 자리를 가리키는데 거기엔 아무것도 없어서 투명하게 그려진다.

### 3-2. 세지 말고 넣어 봐라

번역문 검사기가 **한글 음절만** 폰트 대조했다. 번역기가 낸 둥근 작은따옴표
`‘’` 는 폰트에 없는데 검사를 통과했고, 삽입 단계에서 6건이 조용히 실패했다.

인코딩이 실패하면 그 메시지는 **원문 바이트가 그대로 남는다.** 그걸 한국어
대응표로 읽으니 화면에 잡음처럼 보였다 — 시끄러운 실패였는데 검사기가 못 봤다.

고친 방법은 세는 대신 **삽입기가 쓰는 바로 그 인코더를 불러 보는 것**이다.

```python
try:
    GT.encode(ko, glyphs, bank1)
except ValueError as error:
    return f"넣을 수 없다 — {error}"
```

**다음엔 이렇게.** 검사는 대리 지표가 아니라 **실제 동작으로** 한다. 그리고
상수를 옮길 때는 먼저 묻는다 — **혼자인가 짝인가. EXE 안에만 있는가.**

## 4. 압축기를 자기 디코더로 검증하면 안 된다

LZSS 압축기에 버그가 둘 있었고, `--check` 가 **우리 디코더**로 검증해서 둘 다
통과시켰다.

1. 헤더에 **해제 크기**를 썼다. 실제로는 **압축 스트림 길이**다
2. 거리 4096 매치를 냈다. 게임 해제기는 링 버퍼가 없어 **1~4095만** 유효하다

둘 다 실기(그리고 에뮬레이터)에서 크래시로 나타났고, 원인을 찾는 데 오래 걸렸다.

**다음엔 이렇게.** 게임의 해제기를 역어셈블해 **그대로 옮긴 참조 구현**으로
검증한다. 우리 구현끼리 맞춰 보는 것은 검증이 아니다.

```python
def decode_like_game(payload): ...   # 0x800393A4 를 그대로 옮긴 것
```

## 5. 눈으로 읽은 값은 문맥으로 교차검증한다

폰트 글리프 ↔ 문자 대응표는 자동으로 알 방법이 없어 사람이 읽어야 한다.
**12×12 픽셀에서 획 하나 차이는 눈으로 안 갈린다.**

- 뱅크0: 오십음순 구간이 **통째로 한 칸 밀려** 있었다. 순서 검산으로는 안 잡힌다
- 뱅크1: 90자를 읽었는데 **문맥이 여덟 개를 뒤집었다**

| 눈 | 문맥 | 근거 |
|---|---|---|
| 忘 | **危** | 「車が来たら危ないって」 |
| 嘩 | **噂** | 「お噂はかねがね」 |
| 運 | **遅** | 「出遅れてしまう」 |
| 屋 | **雇** | 「SeeDを雇うのに金を」 |
| 壊 | **嬢** | 「お嬢ちゃんは…」 |
| 幸 | **孝** | 「親孝行」+「親不孝」 |

애매한 둘은 **자료 안의 다른 증거**로 확정했다.

- `絵` — 어느 필드에 가나와 같은 음의 한자를 짝지은 시험 문구가 있었다
  (`2Bい意 3Cう宇 4Dえ▮`). 「え」로 읽는 글자다
- `旨` — 문장 전체가 술 담그는 이야기였다. 「思ったより旨かった」

**다음엔 이렇게.** 판독은 세 가지로 되짚는다. ① 같은 문자가 두 인덱스에
배정됐는가 ② 글리프와 배정 문자를 나란히 렌더해 대조 ③ **실제 대사를 디코드해
말이 되는가.** 셋 다 서로 다른 오류를 잡는다.

## 6. 코드는 부팅 EXE 에만 있지 않다

글자를 그리는 코드가 EXE 안에만 있는 줄 알고 팔레트 상수를 EXE 에서만 고쳤다.
**오버레이가 자기 코드로 그린다.** 타이틀 화면에서 커서만 나오고 메뉴 글자가
통째로 사라졌다 — 옛 자리를 가리키는데 거기엔 아무것도 없으니 투명하게 그려진다.

목차 134개를 전수로 훑어 두 곳을 찾았다. 그런데 **값만 보고 고르면 안 된다** —
`0x3812` 라는 값은 우연히도 자주 나온다(`ori k0, v1, 0x3812`). 진짜 코드는
짝수용 바로 뒤에 홀수용이 붙고 둘 다 `addiu rX, zero, …` 꼴이다. 짝을 보고
골랐더니 134개 중 둘뿐이었다.

**다음엔 이렇게.** "이 코드가 여기 말고 또 있는가" 를 **이미지 전체에서** 묻는다.
찾을 때는 값이 아니라 **패턴(짝, 앞뒤 문맥, 레지스터 조합)** 으로 고른다.

## 7. 진단 도구가 낡으면 멀쩡한 것을 실패로 본다

두 번, 도구가 거짓 경보를 냈고 그걸 쫓느라 시간을 썼다.

- `--check` 가 선두 u32 를 **해제 크기**로 읽어 `decoded[:declared]` 로 잘랐다.
  압축 스트림 길이가 맞다. **멀쩡한 필드가 전부 "포인터가 어긋난다"** 로 나왔다
- 런타임 검증기가 **스톡 EXE 를 돌리는 채로** 검사해 "팔레트가 덮였다" 라고
  보고했다. 덮인 게 아니라 애초에 올라간 적이 없었다

둘째는 특히 위험했다. 세이브 스테이트는 RAM·VRAM 을 통째로 복원하므로 **디스크를
바꿔 꽂아도 스테이트 안의 옛 코드가 돈다.** 빌드를 바꿨으면 스테이트가 아니라
재부팅해야 한다.

**다음엔 이렇게.** 런타임 검증기는 **맨 먼저 "지금 도는 게 우리 빌드인가"** 를
확인한다. 패치 표식 몇 개를 읽어 어긋나면 그 사실부터 말하고 멈춘다.

## 8. 자원은 "지금 안 쓴다"가 아니라 "우리가 소유한다"로 확보한다

VRAM 뱅크1 `(832,256)` 을 통째로 뺏는 안을 구현해 실기까지 갔다가 무너졌다.

```
동영상 두 편을 지난 뒤
  (960,256)  뱅크0 텍스처   100% 살아남음
  (832,256)  뱅크1 텍스처   32.5% 만 남음
```

스톡에서는 필드에 들어갈 때 그 자리가 다시 채워진다. 그런데 **그 적재를 막는 것이
우리 계획의 전제였다** — 자리를 뺏는 순간 되살릴 방법도 같이 없앤 것이다.

**다음엔 이렇게.** 자원을 잡을 때 두 가지를 따로 묻는다.

- **누가 지운다** — 동영상, 장면 전환, 다른 모듈
- **누가 되살린다** — 그 경로를 우리가 막고 있지는 않은가

되살리는 경로가 우리 손에 있으면(예: 우리가 매번 올리는 파일) 그 자원은 안전하다.

## 9. 가르는 실험이 추측보다 빠르다

실기 크래시를 **여섯 번 갈라** 잡았다. 매번 절반씩 줄었다.

```
1. 그림자·주입 코드를 뺀다        -> 여전히 죽음   (무죄)
2. EXE 를 원본으로 되돌린다        -> 여전히 죽음   (EXE 패치 무죄)
3. 섹터 구조·EDC/ECC 대조          -> 원본과 동일   (무죄)
4. 디스크 전체 대조                -> 바뀐 곳 4군데뿐
5. 폰트만 바꾼 롬                  -> 뜬다         (폰트 무죄)
6. 폰트 + 메뉴                     -> 죽는다       ★ 메뉴 블록
```

4번이 특히 값어치를 했다. **우리가 정확히 무엇을 바꿨는지**를 짐작이 아니라
실측으로 확정하니(TOC 1섹터, 폰트 15, 필드 1,590, 메뉴 6) 그다음 실험 설계가
저절로 나왔다. 예기치 않게 건드린 곳이 없다는 것도 함께 확인됐다.

**다음엔 이렇게.** 원인이 안 보이면 추측을 늘리지 말고 **가르는 실험을 만든다.**
실기 왕복이 비싸므로 한 번에 최대한 많이 가르도록 설계한다.

그리고 **원본이 그 환경에서 도는지**를 먼저 확인한다. 그래야 "우리 패치 탓" 과
"환경 탓" 이 갈린다.

## 10. 폰트 렌더러가 하나라고 생각했다

아이템·마법 메뉴에 들어가면 멈췄다. 이틀을 문자열에서 찾았고, 원인은 문자열이
아니라 **어느 색인에 글자를 놓았는가** 였다.

메뉴 항목 이름은 우리가 만든 텍스처 폰트가 아니라 **EXE 안의 별도 벡터 폰트
루틴**(`0x8002c540`)이 그린다. 표 `0x800528a8` 에서 글자마다 파트 수를 읽어 그만큼
20바이트 프리미티브를 찍는다.

```
8002c5e8  addiu v1, v1, 0xe0    색인 = 둘째바이트 + 448  (선두 0x19)
8002c5f0  beq   v0, zero, …     색인 512 이상이면 빠져나간다
8002c60c  srl   t1, v0, 16      **파트 수를 그대로 믿는다**
8002c6a0  addiu a1, a1, 0x14    **프리미티브 포인터에 경계 검사가 없다**
```

색인 484~511 중 18칸이 쓰레기 항목이라 파트 수가 **49,312** 로 나온다. 한 글자에
약 1MB. 두 글자면 RAM 2MB 를 넘어 0 으로 되감기고 BIOS 예외 벡터를 깔아뭉갠다.
그 뒤로는 인터럽트마다 벡터의 쓰레기를 실행해 「없는 명령」 예외가 무한 반복된다.

`つかう` 를 `사용` 으로 옮겼는데 `용` 이 하필 색인 228 이었다.

**왜 오래 걸렸나.** 「글자를 바꿨더니 죽는다」에서 곧바로 문자열의 성질을
의심했다. 구조·제어 코드·널 위치·2바이트 선두·글리프 인덱스 범위·픽셀 폭까지
전부 원본과 맞췄는데도 죽으니, 맞출수록 더 헤맸다. **문자열은 처음부터 결백했다.**

들어맞지 않던 관측 하나가 답을 품고 있었다. `사용`(`2d 19 24`)이 죽는데 같은
바이트가 통째로 든 `마법 사용`은 멀쩡했다. **같은 바이트가 자리에 따라 다르게
동작하면, 읽는 코드가 하나가 아니라는 뜻이다.** 항목 이름은 벡터 폰트, 설명문은
텍스처 폰트였다.

**다음엔 이렇게.**

- 폰트·문자열을 건드리기 전에 **그리는 코드가 몇 개인지** 먼저 센다. 텍스처
  폰트만 찾고 끝내지 않는다
- 게임이 **표를 읽어 그 값만큼 반복**하는 곳을 찾는다. 그 표의 유효 범위가
  우리가 쓸 수 있는 색인의 상한이다
- **배치는 미학이 아니라 안전 문제다.** 어느 글자를 어느 색인에 놓느냐가
  크래시를 만든다. 금지 색인 목록을 배치 생성기에 못 박는다
- 원본이 안 쓰던 색인은 **표가 비어 있을 수 있다.** 원본이 쓰는 범위 안에
  머무는 것이 가장 안전하다

수정은 `build_layout_all.py` 의 `VECTOR_BOMB` 18칸을 배치에서 빼는 것으로 끝났다.
메뉴 526건의 최대 파트 수가 197,317 에서 84 로 떨어졌고, **실기에서 아이템·마법
메뉴 진입을 확인했다.**

## 11. 관측 도구를 나중에 만들었다

실기 왕복으로 문자열을 절반씩 갈랐다. 여섯 판을 돌려 56개를 8개까지 줄였다.
그동안 **에뮬레이터에 GDB 스텁이 계속 열려 있었다.** 붙고 나서는 감시점 한 번에
범인을 찍었다.

붙는 데까지도 헛발질이 많았다. 전부 **도구를 안 믿고 관측을 안 검산한 탓**이다.

- **`/dev/tcp` 로 포트를 재고 「닫혔다」고 단정했다.** zsh 에서 안 먹는 것이었다.
  `lsof -nP -iTCP -sTCP:LISTEN` 로 보니 처음부터 열려 있었다. 없다는 결론은
  **다른 방법으로 한 번 더** 확인한다
- **`g` 응답에서 PC 를 「코드 주소처럼 보이는 값」으로 골랐다.** 0 도 유효한
  주소라 FPU 의 0 을 PC 로 읽었다. 규격대로 37번을 쓰면 될 일이었다.
  휴리스틱으로 고르지 말고 **규격을 확인**한다
- **인터럽트로 붙잡으면 언제나 예외 벡터가 잡힌다.** 게임이 어디 있었는지는
  BIOS 처리기가 TCB 에 넣어 둔 EPC(`*(*(0x108)) + 8 + 0x80`)를 읽어야 한다
- **Lua 콘솔에서 PC 를 4,000번 표집하는 루프를 짰다.** Lua 는 에뮬레이터와 같은
  흐름에서 돌아 그동안 게임이 한 발짝도 못 나간다. 같은 값만 4,000번 나온다
- **가장 나빴던 것**: 멈춘 상태가 아닌 RAM 을 보고 「프리미티브가 커널을 덮었다」는
  **맞는 판단을 취소했다.** 관측 대상이 정말 그 상태인지 확인하지 않았다.
  메뉴 문자열이 RAM 에 있는지만 봤어도 알 수 있었다

**다음엔 이렇게.**

- **실기 왕복이 비싸다고 느껴지는 순간이, 관측 도구를 만들 때다.** 가르는 실험은
  판당 1비트지만 PC 하나는 답을 통째로 준다
- 에뮬레이터의 **디버깅 통로를 착수 시점에 확보**한다. GDB 스텁, 웹 API, 설정
  파일 위치까지 미리 확인해 둔다
- 무엇을 관측하든 **그 관측이 유효한 상태에서 뜬 것인지** 먼저 검산한다.
  「지금 이 화면이 맞다」를 증명하는 지표를 하나 정해 둔다
- 관측을 근거로 판단을 뒤집을 때는, **뒤집는 근거 자체가 유효한지** 본다

## 12. `--init --force` 가 이미 적용한 패치를 통째로 지웠다

번역 텍스트를 갱신하려고 사본을 `--init --force` 로 다시 만들었다. 원본을
복사하는 도구니 당연하다고 생각했는데, **그 사본에는 이미 적용해 둔 한글
폰트 패치(EXE 코드 + 글리프 텍스처 + 오버레이 CLUT)가 들어 있었다.** 새로
만든 사본은 순수 원본이라 그 패치가 전부 사라졌다.

대사만 다시 넣고 빌드를 넘겼더니, 실기에서 한글 인덱스로 인코딩된 텍스트가
**원래 그 자리에 있던 한자로 그대로 보였다** — 사용자가 "한글 폰트가 안
들어간 것 같다, 일본어와 한자만 출력된다"고 알려줘서 알았다.

**무엇을 믿었나.** "사본을 다시 만드는 것"과 "텍스트만 갱신하는 것"이 서로
다른 층이라 섞여도 안전하다고 생각했다.

**무엇이 참이었나.** 이 프로젝트의 패치는 여러 도구가 각자 다른 파일 영역에
순차로 쓰는 **누적형**이다(`patch_font_4plane.py` → `install_font_4plane.py`
→ `patch_overlay_clut.py` → `patch_disc.py --apply`). `--init --force` 는
그 누적을 전부 원점으로 되돌리는데, 이름이 "텍스트 재적용"과 무관해 보여
그걸 깨닫기까지 시간이 걸렸다.

**어떻게 잡았나.** 사용자가 실기에서 직접 확인해 알려줬다 — 정적 검증
(EXE 바이트 대조, round-trip)만으로는 "패치가 순서대로 다 적용됐는가"를
못 잡는다. 놓친 단계를 다시 실행하고, 그제야 **EXE 패치 바이트·폰트
텍스처·필드 텍스트 셋 다** 대조해 전부 있는지 확인했다.

**다음엔 이렇게.**

- **`--init --force` 뒤에는 누적 패치 단계를 전부 다시 밟는다.** 무엇을 다시
  해야 하는지 목록으로 둔다(폰트 EXE 패치 → 폰트 설치 → 오버레이 CLUT →
  텍스트 적용). 하나만 다시 하고 끝냈다고 여기지 않는다
- 빌드가 끝나면 **각 패치 단계의 흔적을 전부 따로 확인**한다 — 텍스트가
  들어갔다는 것과 그 텍스트를 그릴 폰트가 있다는 것은 별개의 확인이다
- "재초기화"류 명령은 이름이 무해해 보여도 **무엇을 지우는지 먼저 묻는다**

## 13. 쓰기 감시점을 아무 필드에나 걸면 다른 필드가 잡힌다

전투 대사가 실리는 RAM 자리를 찾으려고 그 주소에 쓰기 감시점을 걸었다.
여러 번 걸렸는데, 걸릴 때마다 그 자리에 쓰인 값을 디코드해 보면 **텍스트가
아니었다** — 커서 좌표 클램핑 같은 무관한 값이었다.

**무엇을 믿었나.** RAM 의 한 주소는 한 가지 용도라고 생각했다.

**무엇이 참이었나.** 그 4바이트는 **여러 필드가 겹쳐 쓰는 공용 구조체
자리**였다 — 텍스트 문자열이 시작하는 자리이면서, 동시에 커서 위치 같은
다른 필드의 오프셋과도 겹쳤다. 감시점은 "이 주소를 누가든 쓰면" 걸리므로,
텍스트를 쓰는 그 순간이 아니라 **아무 쓰기에나** 걸렸다.

부수적으로 감시점 처리 스크립트 자체에도 결함이 있었다 — 정지 직후에
타깃 콘솔 출력(`O` 패킷)이 먼저 오면, 그걸 정지 응답으로 착각해 레지스터
파싱이 깨졌다. 콘솔 패킷을 건너뛰고 진짜 정지 응답(`S`/`T`)이 올 때까지
기다리게 고쳤다(`scripts/gdb_peek.py`).

**어떻게 잡았나.** 감시점이 걸릴 때마다 **그 순간의 목적지 버퍼를 실제로
디코드**해서 우리가 찾는 문자열이 맞는지 확인하는 자동 재시도 루프로
바꿨다. 결국 이 방식으로도 정확한 순간을 못 잡아, CD 읽기 요청 함수
자체에 거는 방식으로 전략을 바꿨다.

**다음엔 이렇게.**

- 감시점을 걸기 전에 **그 주소가 정말 한 가지 용도인지** 먼저 확인한다.
  안 되면 감시점이 걸릴 때마다 **내용을 실제로 검사**하는 자동 루프로
  거른다 — 한 번 걸렸다고 그게 찾던 것이라 단정하지 않는다
- 목적지보다 **더 이른 지점**(요청을 발생시키는 함수)에 거는 편이 공용
  자리 문제를 피하기 쉬울 때가 있다
- GDB 원격 프로토콜에서 **콘솔 출력(`O`)과 정지 응답(`S`/`T`)을 구분해서
  읽는다.** 첫 패킷을 무조건 정지 응답으로 가정하지 않는다

## 다음 타이틀 착수 체크리스트

순서대로 하면 위의 대부분을 미리 막는다.

**착수 전에 만들 것**

- [ ] 게임의 해제기를 역어셈블해 **참조 구현**으로 옮긴다. 압축기 검증은 이걸로만 한다
- [ ] 빈 자리 판정기 — 파일 0 + 실행 중 0 + **참조 없음** 세 관문
- [ ] 주입 코드 위험 검사 — 적재 지연 슬롯, 분기 지연 슬롯
- [ ] 런타임 검증기 — **맨 먼저 패치 표식으로 우리 빌드인지 확인**
- [ ] 섹터 검사 — EDC/ECC 와 **동기·헤더·서브헤더를 따로**

**자료구조를 다시 짜기 전에**

- [ ] 원본의 오프셋을 **전수로 재서 불변식을 찾는다** (정렬, 패딩, 경계)
- [ ] 크기·내용만 맞추면 에뮬레이터는 통과시켜 준다는 것을 기억한다

**상수를 옮기기 전에**

- [ ] 혼자인가 **짝인가**
- [ ] EXE 안에만 있는가, **오버레이에도 있는가**
- [ ] 찾을 때 값이 아니라 **패턴**으로 고르는가

**자원을 잡기 전에**

- [ ] 누가 지우는가 / 누가 되살리는가
- [ ] 되살리는 경로를 우리가 막고 있지는 않은가

**검증할 때**

- [ ] 세지 말고 **실제로 넣어 본다**
- [ ] 사람이 읽은 값은 **문맥으로 교차검증**한다
- [ ] 에뮬레이터 통과는 절반이다. **실기는 별도 관문이다**

**글자를 배치하기 전에**

- [ ] 글자를 그리는 코드가 **몇 개인가** — 텍스처 폰트만 찾고 끝내지 않는다
- [ ] 게임이 **표를 읽어 그 값만큼 반복**하는 곳이 있는가. 그 표의 유효 범위가
      우리가 쓸 수 있는 색인의 상한이다
- [ ] 금지 색인을 **배치 생성기에 못 박았는가** — 배치는 안전 문제다

**착수 시점에 확보할 것**

- [ ] 에뮬레이터의 **GDB 스텁·웹 API·설정 파일 위치**
- [ ] 멈춘 순간의 PC 를 읽는 방법 (인터럽트에 가려지므로 **TCB 의 EPC**)
- [ ] 특정 주소를 누가 망가뜨리는지 잡는 **쓰기 감시점**

**막혔을 때**

- [ ] 원본이 그 환경에서 도는가부터 확인
- [ ] 추측을 늘리지 말고 **가르는 실험**
- [ ] 먼저 **무엇을 바꿨는지 실측**한다 (전체 대조)
- [ ] 실기 왕복이 비싸게 느껴지면 **관측 도구를 만들 때다**. 가르기는 판당
      1비트, PC 하나는 답 전체다
- [ ] 관측이 **유효한 상태에서 뜬 것인지** 검산한다. 판단을 뒤집을 때는
      뒤집는 근거부터 본다
- [ ] 「없다」는 결론은 **다른 방법으로 한 번 더** 확인한다
