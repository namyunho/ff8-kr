# Git 작업 흐름

이 저장소는 소수 인원이 작업하는 프로젝트에 맞춰 복잡한 Git Flow 대신
GitHub Flow에 가까운 **`main` + 짧은 작업 브랜치 + 릴리스 태그** 구조를
사용한다. 별도 `develop` 브랜치는 두지 않는다.

## 브랜치 역할

| 이름 | 역할 |
|---|---|
| `main` | 항상 현재 검증 기준을 통과하는 통합 기준 브랜치 |
| `feature/<주제>` | 새로운 기능 또는 결과가 명확한 분석 작업 |
| `fix/<주제>` | 재현된 결함 수정 |
| `docs/<주제>` | 실행 코드의 동작을 바꾸지 않는 문서 변경 |
| `refactor/<주제>` | 동작을 유지하는 구조 개선 |
| `analysis/<주제>` | 독립적인 역공학 판정이나 소비 경로 조사 |
| `experiment/<주제>` | 결론이 정해지지 않은 단기 실험과 PoC |
| `release/<버전>` | 배포 직전 별도 안정화가 실제로 필요할 때만 사용 |
| `v0.1.0`, `v0.2.0` | 실제 패치 릴리스 지점을 표시하는 태그 |

브랜치 이름의 `<주제>`는 소문자 kebab-case로 작성한다. 개인이나 작업 도구를
나타내는 `codex/`, `claude/` 같은 접두사는 붙이지 않는다.

이 프로젝트의 예시는 다음과 같다.

```text
main
├── analysis/img-toc-denominator
├── analysis/text-encoding-table
├── feature/font-glyph-extractor
├── feature/hangul-12x12-font
├── feature/dialogue-extractor
├── fix/mode2-sector-ecc
├── docs/disc1-baseline
└── release/v0.1.0
```

Disc 1의 ISO/IMG 구조, LZSS 해제, TOC 134엔트리 분류, 12×12 폰트 위치 확정이
`main`의 현재 통합 기준이다.

## 표준 흐름

```text
main에서 브랜치 생성
→ 한 가지 목적의 변경
→ 테스트·원본 검증
→ PR 또는 자체 검토
→ main에 병합
→ 작업 브랜치 삭제
```

1. 작업을 시작할 때 최신 `main`에서 목적에 맞는 브랜치를 만든다.
2. 한 브랜치는 한 가지 검증 가능한 결과만 다룬다.
3. 변경 성격에 맞는 회귀 테스트와 원본 무결성 검증을 통과시킨다.
4. PR 또는 자체 검토에서 변경 범위와 생성물을 확인한다.
5. 검증된 결과를 `main`에 병합하고 작업 브랜치를 삭제한다.
6. 실제 배포 지점에는 의미 버전 형식의 태그를 붙인다.

## 커밋 메시지

```text
<type>: <설명>

<본문(선택)>
```

`type`은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`,
`analysis` 중 하나를 쓴다.

**작성 도구를 저자·공동저자·출처로 기입하지 않는다.** `Co-Authored-By`,
`Generated with`, 도구 이름이 들어간 트레일러를 커밋 메시지, PR 본문, 문서
어디에도 넣지 않는다. 이 저장소의 기여자는 사람만 표기한다.

## 프로젝트별 원칙

### 변경 목적 단위로 분리

`reverse-engineering`처럼 종료 조건이 없는 거대한 브랜치를 만들지 않는다.
예를 들어 폰트 추출기 구현은 `feature/font-glyph-extractor`, 텍스트 인코딩
판정은 `analysis/text-encoding-table`처럼 결과와 종료 조건이 드러나게 나눈다.

### 짧게 유지

작업 브랜치는 며칠, 길어도 1~2주 안에 병합할 수 있는 크기를 권장한다. 범위가
커지면 독립적으로 검증 가능한 작업으로 다시 나눠 충돌과 장기 분기를 줄인다.

### 실험과 재현 가능한 결과를 구분

불확실한 조사는 `experiment/font-vram-hook` 같은 별도 브랜치에서 수행할 수
있다. `main`에는 조사 과정 전체가 아니라 다시 실행할 수 있는 스크립트, 테스트,
입력 조건, 확정된 판정 문서만 병합한다. 실험 결과가 기능 구현으로 확정되면
필요에 따라 `feature/` 또는 `fix/` 범위로 정리한다.

### 원본과 대용량 덤프는 커밋하지 않음

원본 BIN/CUE, 패치된 전체 디스크 이미지, RAM/VRAM 덤프, 추출 게임 자산,
IDA/Ghidra 데이터베이스는 어떤 브랜치에도 커밋하지 않는다. `.gitignore` 정책을
유지하고, 재현에 필요한 경로·해시·생성 명령만 추적한다.

`fonts/` 아래의 한국어 폰트 소스는 원본 매체가 아니므로 예외로 추적한다.
라이선스 파일(`OFL.txt`)을 함께 둔다.

### 릴리스 브랜치는 필요한 경우에만 사용

동시에 여러 릴리스를 안정화하거나 구버전을 유지하지 않는 동안에는 `main`에서
검증한 뒤 바로 `v0.x.y` 태그를 붙여도 충분하다. 장기 유지보수할 구버전이
생길 때만 `release/0.x` 또는 `maintenance/0.x`를 추가한다.

## 병합 전 최소 확인

- 변경 파일이 브랜치의 한 가지 목적에 맞는지 확인한다.
- 원본 매체, 추출물, 덤프, 빌드 이미지가 stage되지 않았는지 확인한다.

  ```bash
  git status --short
  git diff --cached --stat
  ```

- 원본 무결성 검증을 실행한다.

  ```bash
  python3 scripts/psx_disc.py verify
  ```

- 생성 파일을 스크립트로 재생성할 수 있는지 확인한다.
- 미확정 분석 결과와 실행 검증 대기 항목을 완료로 표현하지 않는다.
  추정은 문서에 **추정**으로 남기고, 실행 증거가 생긴 뒤에만 확정으로 올린다.
- **이번 작업에서 겪은 실수·시행착오·잘못된 가정이 있으면 커밋하기 전에
  `docs/lessons.md`에 남긴다.** 형식은 그 문서의 기존 항목을 따른다 —
  증상 → 무엇을 믿었나 → 무엇이 참이었나 → 어떻게 잡았나 → 다음엔 이렇게.
  성공한 결과만 커밋하고 착각·헛수고를 안 남기면 다음 세션이 같은 값을
  다시 치른다. 사소한 오타 수정 같은 건 대상이 아니다 — **다시 만날 만한
  종류의 착각**(잘못된 가정, 안 통한 접근, 원인을 착각해 헤맨 시간)만
  추린다.
