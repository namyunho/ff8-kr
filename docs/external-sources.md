# 외부 자료 대조

검토일: 2026-07-28
대상: `Final Fantasy VIII (Japan, Asia) (Disc 1)` — CRC32 `2319B365`

이 문서는 커뮤니티 자료의 주장을 **이 디스크에 직접 대조한 결과**다. 자료는
길잡이로 쓰고 판정은 실측으로 한다. 맞은 것과 틀린 것을 모두 남긴다.

## 원칙

1. **외부 자료를 판정 근거로 쓰지 않는다.** 탐색 방향을 좁히는 데만 쓴다.
2. 파일 이름은 외부 목록이 아니라 **부트 EXE 안의 이름 문자열 표**
   (`0x80054340` 의 두 번째 u32)에서 읽는다.
3. 대조 결과가 어긋나면 **이 디스크의 실측값을 채택**하고 어긋난 사실을 남긴다.

| 자료 | 용도 |

| Qhimm Modding Wiki — FF8 색인 | 파일 형식 이름과 구성 개관 |

## 대조 결과

판정은 넷이다. **확인** = 실측이 주장과 일치. **정정** = 부분적으로 맞으나
값이나 조건이 다름. **반증** = 실측이 주장과 어긋남. **미확인** = 검사 안 함.

### A. 섹터·오프셋 기준

| # | 주장 | 판정 | 근거 |
|---|---|---|---|
| A1 | 섹터 2352B = 헤더 16B + 데이터 2048B + EDC/ECC 288B | **정정** | Mode 2 Form 1 은 sync 12 + header 4 + **subheader 8** + data 2048 + EDC 4 + ECC 276. 사용자 데이터 시작은 **24**다. |
| A2 | 파서 예시 `sectorIndex * 2352 + 16` | **반증** | LBA 826 을 `+16` 으로 읽으면 subheader `00 00 08 00 00 00 08 00` 을 데이터로 오독해 첫 엔트리가 `(524288, 524288)` 이 된다. `+24` 는 `(827, 1176)` = TOC#0. |
| A3 | 일본판은 변위 없이 IMG 첫 섹터부터 목차가 시작 | **정정** | 목차가 `FF8DISC1.IMG` 첫 섹터인 것은 맞다. 다만 그 위치는 **디스크 절대 LBA 826** 이다. 예시 코드의 `GetSectorOffset(0)` 은 디스크 LBA 0 을 읽어 목차가 아니다. |
| A4 | 목차의 값은 "ISO 내부 상대 섹터, 기본 `0x200` 부터" | **반증** | **절대 디스크 LBA** 다. 엔트리 #0 이 827 이고, 게임 로더가 이 값을 `CdIntToPos()` 에 그대로 넘긴다. `0x200`(512)에서 시작하지 않는다. |
| A5 | 루트 엔트리 132개 로드 | **정정** | 유효 엔트리는 **134**다. 부트스트랩 상수가 `LBA 826 / 1,072바이트` 이고 `1,072 = 134 × 8` 이다. |

### B. 루트 아카이브 ID 할당

외부 자료의 ID 는 **이 디스크의 TOC 인덱스와 어긋난다.** `wm2field.tbl` 은
양쪽 다 3 이지만(크기 1,728바이트가 정확히 일치한다) `mngrp.bin` 은 외부 21 /
이 디스크 22 다. 즉 인덱스 3 과 21 사이에 일본판 전용 엔트리가 하나 더 있다.

| # | 주장 | 판정 | 이 디스크의 값 |
|---|---|---|---|
| B1 | ID 2 = `FIELD.BIN` (LZS 압축) | **확인** | TOC#2, LBA 33,249, 102,500B → 해제 191,824B |
| B2 | ID 3 = `wm2field.tbl` (72 × 24 = 1,728B) | **확인** | TOC#3, 크기 정확히 1,728B |
| B3 | ID 21 = `mngrp.bin` | **정정** | TOC**#22** — EXE 이름 문자열로 확인 |
| B4 | ID 22 = `init.out` | **정정** | TOC**#23** — EXE 이름 문자열로 확인 |
| B5 | ID 26 = `world.bin` | **정정** | TOC**#27** — 해제 시 `\DAT\WMSET.OBJ` 등 월드맵 경로 문자열 |
| B6 | ID 30~127 = AKAO 음원 | **정정** | TOC**#31~#128** — 각 파일의 서브엔트리 0 이 `AKAO` |
| B7 | ID 128 = `kernel.bin` | **정정** | TOC**#129** — u32 오프셋 배열 아카이브 |
| B8 | ID 129 = `sysfnt.tdw` | **정정** | TOC**#130** — 이 프로젝트의 폰트 파일 |
| B9 | ID 0 = `packcode.bin`, 폰트 데이터 포함 | **반증** | TOC#0 은 1,176바이트 MIPS 코드다. 시스템 폰트는 #130 이다. |
| B10 | ID 25 = `battle.bin` | **미확인** | +1 규칙이면 TOC#26(346,560B). 내용을 열지 않았다. |

**외부 ID 를 그대로 옮겨 쓰면 안 된다.** 이름은 EXE 표에서 읽고 인덱스는
이 디스크 기준으로 쓴다. 전체 표는 `docs/disc1-baseline.md` 에 있다.

### C. 필드 데이터 색인

| # | 주장 | 판정 | 근거 |
|---|---|---|---|
| C1 | `field.bin` 안에 필드 디렉터리가 있고 28바이트 시작 패턴 뒤에 온다 | **확인** | 해제본 오프셋 `0x2864C` 에서 패턴 발견, 목록은 `0x28668` 부터 |
| C2 | 종료 패턴 `00 00 01 00 02 00 03 00` | **확인** | `0x2A5C0`. 목록 길이 8,024바이트 |
| C3 | 목록 형식은 루트와 같은 `[4B LBA][4B 크기]` | **확인** | 엔트리 1,003개, LBA 33,301..87,815 |
| C4 | 필드마다 MIM / DAT / LZK 3종이 **순서대로** 묶인다 | **확인** | 해제 크기가 큰·작은·중간으로 3주기 반복. 예: #103 441,944(MIM) → #104 34,820(DAT) → #105 228,080(LZK) |
| C5 | 목록 앞 76개가 `D000.MCH`..`D075.MCH` | **미확인** | 검사하지 않았다 |
| C6 | 목록이 정렬돼 있다 | **반증** | LBA 가 단조 증가하지 않는다 |

### D. DAT 섹션과 MSD

| # | 주장 | 판정 | 근거 |
|---|---|---|---|
| D1 | DAT 선두에 PSX RAM 주소 포인터 12개, 첫 섹션은 오프셋 48 | **확인** | `ptr[11]` 로 계산한 오프셋이 해제 크기와 정확히 일치 |
| D2 | 9번 섹션(포인터 `[8]`)이 텍스트(MSD) | **확인** | 그 구간이 대사다 |
| D3 | MSD 는 위치 목록 + 텍스트, `nbText = firstTextPos / 4` | **확인** | u32 오프셋 배열. 목록 1,003엔트리 전수에서 **DAT 302개, 메시지 9,442건, 형식 위반 0건** |

MSD 형식은 위키 서술과 실측이 완전히 일치한다. **외부 자료가 가장 정확했던
항목이며, 자체 탐색으로 막혀 있던 지점을 바로 풀어 줬다.**

처음 적은 "DAT 140개 / 메시지 5,445개" 는 앞쪽만 훑은 부분 결과였다. 5,445 는
앞 138개 필드까지의 누적치다. 전수로 훑으면 DAT 302개에 메시지 9,442건이며
형식 위반은 여전히 0건이다. **판정은 그대로 유지되고 표본만 넓어졌다.**
서로 다른 오프셋도 9,442개로 중복 슬롯이 없다.

### E. 텍스트 제어 코드

정본은 부트 EXE 의 문자열 측정기 `sub_8002E4A0` 과 토큰 확장기
`sub_8002F73C` 다. 아래 빈도는 필드 MSD 섹션 100개를 훑은 실측값이다.

| # | 주장 | 판정 | 근거 |
|---|---|---|---|
| E1 | `0x00` 문자열 종료 | **확인** | 전수 9,442개가 전부 이 바이트로 끝난다 |
| E2 | `0x02` 줄바꿈 | **확인** | 9,968회로 가장 흔하다 |
| E3 | `0x03` = 페이지 넘김 / 대화창 대기 | **반증** | `0x03` 은 **파라미터 1바이트를 소비하는 삽입 코드**다(443회). 페이지 리셋은 `0x07` 이며 필드 MSD 표본에서 **0회**다. |
| E4 | `0x05` + ID = 캐릭터 이름 출력 | **정정** | `0x05` 는 변수 삽입(`sub_8002C700(id)`)이고 56회로 드물다. 이름·수치 삽입의 주력은 `0x03`(443회)과 `0x06`(1,578회)다. |
| E5 | `0x06` = 색상/포맷 변경 (wiki.ffrtt.ru) | **정정** | 토큰 확장기 `sub_8002F73C` 를 전수 디스어셈블한 결과 `0x06` 은 이름표 조회를 거치지 않고 파라미터 1바이트를 그대로 출력에 복사하는 **원시 통과 코드**다(`0x05`·`0x08`·`0x09`·`0x0A`·`0x0B`와 동일 그룹). **E4 를 정정한다** — "이름·수치 삽입의 주력은 `0x03`과 `0x06`"은 빈도만 보고 낸 추정이었고, 실제로 이름을 확장 삽입하는 코드는 `0x03`·`0x04`뿐이다. "색상"이라는 구체적 의미는 그리기 루틴까지 대조하기 전엔 **미확인**이다. |
| E6 | `0x0B` = 커서 위치, 가변 길이 2~3바이트 (wiki.ffrtt.ru) | **반증** | 측정기(`sub_8002E4A0`)와 확장기(`sub_8002F73C`) 둘 다 `0x0B` 를 파라미터 1바이트 고정(총 2바이트)으로 처리한다. 3바이트를 소비하는 경로는 코드에 없다. |

**토큰 확장기의 저값 제어 코드 분류 (2026-08-06 재검증).** `sub_8002F73C` 를
전수 추적한 결과 세 그룹으로 갈린다.

- **이름·값 매크로 삽입** — `0x03`·`0x04`: 파라미터 1바이트로 표
  `dword_80081D10` 를 찾아 `sub_8002A280` 으로 문자열을 복사한다. 실제
  가변 길이 텍스트를 삽입하는 코드는 이 둘뿐이다.
- **원시 통과** — `0x05`·`0x06`·`0x08`·`0x09`·`0x0A`·`0x0B`: 파라미터
  1바이트를 그대로 복사만 한다. 확장 없이, 나중에 그리기 루틴이 해석하는
  것으로 보인다.
- **kernel.bin 참조 삽입** — `0x0C`(`sub_80020BE4`)·`0x0D`(`sub_80020CBC`):
  파라미터로 얻은 값을 **RAM `0x80077B20` 기준 바이트 오프셋**으로 써서
  `sub_80020F98` 이 그 위치의 문자열을 그대로 가리킨다(`sub_8002A280` 으로
  복사되는 것까지 확인). ID `0xFFFF` 는 예외로 EXE 안의 고정 위치
  `0x8005273C` 를 가리키며, 첫 바이트가 `0x00` 이라 **빈 문자열**로 보인다.
  `0x0E` 는 `sub_8002F6C4` 를 호출해 별도로 확장한다. **내용 확인됨(2026-08-06)**
  — IMG TOC#132(LBA 883, 176B)를 가리킨다. `[u16 count=19][u16 offset]×19` +
  문자열 풀이고, 지명 19개(`ガルバディア` `エスタ` `バラム` `ドール` …)가 전부다.
  인덱스는 제어 코드 파라미터에서 **32를 뺀 값**이다(`sub_8002F73C` 의
  `{0E:XX}`/`{0F:XX}` 분기). 필드 대사 번역 파이프라인이 이 표를 건드리지
  않아, 한글 폰트 패치 후에는 원본 일본어 인덱스가 엉뚱한 한글로 보였다 —
  `scripts/patch_location_table.py` 로 재기록해 해결했다.

**번역 함의.** `0x0C`/`0x0D` 가 나오는 대사는 `field.bin` 이 아니라
**kernel.bin 내부 문자열**을 가리킨다 — 그 대사만 한글화해서는 표시되는
이름이 안 바뀐다. `dword_80077B20` 이 실제로 kernel.bin(TOC#129) 런타임
로드 위치인지는 **로더 호출부를 아직 못 찾아 추정이다.** 정적 이미지에서
이 주소는 전부 0이라(BSS 성격), 부트 시 다른 곳에서 채워 넣는 것은 맞다.

실측 빈도 전체:

```text
0x01   531   줄 초기화
0x02  9968   줄바꿈
0x03   443   +1B
0x04    32   +1B
0x05    56   +1B
0x06  1578   +1B
0x09   103   +1B
0x0E   347   +1B
0x12     1   폭 미기여
0x07     0   페이지 리셋 — 필드 MSD 에서는 쓰이지 않는다
```

2바이트 문자 lead: `0x19` 8,645 · `0x1A` 7,986 · `0x1B` 3,720 · `0x1C` 4,950.
`0x18` 과 `0x1D`~`0x1F` 는 표본에서 0회다.

### F. 폰트

| # | 주장 | 판정 | 근거 |
|---|---|---|---|
| F1 | 16 × 16 픽셀 폰트 타일 | **반증** | 셀은 **12 × 12** 다. 텍스처 256 × 252 에 21 × 21 = 441칸. 16 은 셀 크기가 아니라 **줄 진행 높이**다(`16 × 행수 − 4`). |
| F2 | 다쿠텐·한다쿠텐은 앞 글자에 겹쳐 그리는 오프셋 연산 | **반증** | 탁음·반탁음 가나가 **인덱스 0..49 에 독립 글리프**로 들어 있다(ブ ぶ ベ べ ボ ぼ ガ が …). 겹쳐 그리지 않는다. |
| F3 | MIM 안에 폰트 데이터(TDW)가 들어 있다 | **확인** | MIM 섹션 3, 파일 오프셋 438,284. 구조가 `sysfnt.tdw` 와 같다. 자세한 내용은 `docs/font-analysis.md` |

`F3` 은 이 프로젝트의 판정 하나를 뒤집었다. 이전에는 "뱅크 1 이 비어 있다"
고 봤으나 **필드마다 전용 TDW 가 뱅크 1 자리를 쓴다.** 한글 뱅크를 그 자리에
올리려던 계획이 무효가 됐다.

## 요약

| 구분 | 개수 |
|---|---:|
| 확인 | 10 |

| 반증 | 8 |

**정확했던 영역**은 필드 색인 구조(`field.bin` 패턴, 목록 형식, 3종 세트)와
DAT 섹션·MSD 형식이다.

**틀렸던 영역**은 섹터 오프셋(`+16`), 루트 ID 번호, 제어 코드 `0x03` 의 의미,
폰트 셀 크기와 다쿠텐 처리다. 이 값들을 그대로 코드에 옮겼다면 전부 오작동
했을 것이다.
