# kernel.bin 을 축약 없이 완역할 수 있는가 (2026-08-09)

> **2026-08-09 정정과 해결.** 처음에 「게임이 널을 세어 문자열을 찾으므로
> 자리를 옮겨도 된다」고 적었다. **틀렸다** — 실기에서 문자열이 통째로 밀렸고
> 키스티스 이름이 안 떴다(경위는 `lessons.md` 21번). 문자열은 **u16 상대
> 오프셋 표**로 가리켜진다. 그 표를 **전부 찾아 함께 고치는 것**으로 해결했다.

## 결론

**축약은 기술적 필연이 아니다.** 문자열을 옮기려면 오프셋 표를 빠짐없이
찾아 다시 써야 하는데, **25벌을 전부 찾았다 (문자열 1,320/1,320).**

## 무엇이 사실인가

### 1. 완역은 279바이트가 모자랄 뿐이다

```
문자열 풀 합계   16,000B
완역 필요 합계   16,279B      -279B  (1.7%)
```

### 2. 279바이트를 놓을 자리가 이미 있다

```
kernel.bin  LBA 831  35,976B  →  18섹터 = 36,864B
마지막 섹터의 남는 자리 888B   (전부 0x00)
```

### 3. 문자열은 **u16 상대 오프셋**으로 가리켜진다  ← 여기가 틀렸던 곳

글자 섹션마다 **짝이 되는 구조체 섹션**이 있고, 그 안의 레코드가
`u16 이름오프셋 / u16 설명오프셋`을 갖는다. 값은 **글자 섹션 시작 기준
상대 오프셋**이다.

    #39 아이템 설명 332개  ←  #8 이 332칸짜리 u16 통짜 표
    #55 전투 결과  128개  ←  #30 이 128칸짜리 u16 통짜 표
    #47 어빌리티            ←  #17 이 8B 레코드 24개, 필드 +0(이름) +2(설명)

**내가 이것을 못 본 이유는 상대 오프셋을 한 번도 안 재 봤기 때문이다.**
절대 오프셋(u32·u16)만 훑고 「33개뿐」이라는 숫자를 얻어, 「나머지 1,287개는
널을 세어 찾는 모양」이라고 **없는 것을 근거로 결론지었다.**

「글자 섹션이 널로 이어 붙인 순열이다」는 참이지만, 그것은 **문자열을 세어
찾는다는 증거가 아니다** — 그냥 문자열이 이어져 있다는 뜻일 뿐이다.

### 4. 표를 전부 찾았다 — **1,320 / 1,320 (100%)**

`scripts/kernel_offset_tables.py`. 글자 섹션 25개가 구조체 섹션과 **하나씩
짝**이고, 레코드 한 벌에 이름(+0)과 설명(+2)이 들어 있다.

```
글자 #31←구조체 #0/8B   #32←#1/60B   #33←#2/132B  #34←#3/20B   #35←#4/12B
     #36←#5/24B        #37←#6/36B   #38←#7/24B   #39←#8/2B    #40←#9/20B
     #41←#11/8B        #42←#12/8B   #43←#13/8B   #44←#14/8B   #45←#15/8B
     #46←#16/8B        #47←#17/8B   #48←#18/24B  #49←#19/16B  #50←#21/24B
     #51←#22/32B       #52←#24/8B   #53←#25/20B  #54←#28/6B   #55←#30/2B
```

**짝이 단조 증가한다는 것 자체가 증거다.** 우연히 맞은 값은 이런 규칙을 못
만든다.

### 5. 못 찾았던 이유 두 가지

**하나. 오름차순을 가정했다.** 캐릭터 이름 표(#6)는 11칸인데 그중 둘이
`0xFFFF` 다 — **스콜과 리노아는 이름을 세이브에서 읽기 때문**이다. 오름차순
판별이 거기서 끊겼다.

```
[0] 0x37a4  ffff            ← 스콜 (세이브에서 읽는다)
[1] 0x37c8  0000  ゼル
[3] 0x3810  000a  キスティス     ← 안 떴던 그 이름
[4] 0x3834  ffff            ← 리노아
```

**둘. 「값이 등차로 몇 개 맞는 자리」를 표로 셌다.** 그렇게 하면 `#31` 이
표 24벌로 덮이는 헛것이 나온다 — 2개씩 우연히 맞은 자리를 주워 담은 것이다.
표는 **레코드 배열의 한 필드**다. 그래서 셋을 요구해야 한다.

1. 레코드 간격이 섹션 크기를 **정확히 나눈다**
2. 표가 섹션 **첫 레코드**에서 시작한다
3. 그 필드의 값이 **전부** 문자열 오프셋이거나 빈칸이다
4. 한 글자 섹션을 덮는 필드들은 **간격이 같아야 한다** (레코드 크기는 하나다)

### 6. 코드에서 읽은 것

메뉴 오버레이 `sub_801F1050`(0x801f1050) — 상대 오프셋 역참조의 원형이다.

```
sll  $a1, 1          ; 색인 x 2
addu $v1, $a0, $a1
addiu $v1, 2
lhu  $v0, 0($v1)     ; u16 을 읽어
addu $v0, $a0, $v0   ; base 를 더한다  ← 상대 오프셋
```

글자 해독기도 같이 확인했다(`sub_801F17A0`). 우리 인코더와 정확히 같다.

```
v15 = *p++;
if (v15 < 32)  index = 224 * v15 + (*p++) - 5408;   ; 2바이트
else           index = v15 - 32;                     ; 1바이트 (0~223)
```

## 완역으로 가는 길 (수정)

1. ~~오프셋 표를 전부 찾는다~~ **끝났다** (`kernel_offset_tables.py`)
2. 글자 섹션을 다시 짜고 **표를 새 오프셋으로 다시 쓴다**
3. 섹션이 자란 만큼 뒤를 밀고, 머리의 56칸 섹션 오프셋 표를 고친다
4. 파일을 279B 늘린다 (섹터 여유 888B 안). IMG TOC 크기를 올린다
5. 게임이 크기를 TOC 에서 읽는지 확인한다

## 실기에 올리기 전에 반드시 할 검산

이번에 이것을 안 해서 사용자가 깨진 판을 돌렸다.

- **항등 검산.** 표를 다시 쓰는 코드로 **자리를 하나도 안 옮기고** 돌려서
  파일이 **바이트 단위로 원본과 같은지** 본다. 여기서 어긋나면 표 이해가
  틀린 것이다 — 게임을 켜기 전에 잡힌다
- **뒤섞기 검산.** 문자열 순서를 그대로 두고 길이만 1바이트씩 늘려 본 뒤,
  모든 표의 값이 **정확히 그만큼** 움직였는지 되읽어 확인한다
- **가리켜지지 않는 문자열이 0개인가.** 표 25벌이 문자열 1,320개를 빠짐없이
  덮어야 한다. 하나라도 남으면 그것이 다음 「키스티스 이름」이다

## 실기에 올리기 전 검산 (이제 도구가 한다)

`scripts/kernel_repack.py --selftest`

- **항등 검산** — 아무것도 안 옮기고 돌리면 파일이 **바이트 단위로 원본과
  같은가.** 이게 좋은 이유는 **내 모델이 맞는지에 기대지 않기 때문**이다.
  표를 하나라도 잘못 알고 있으면 여기서 죽는다
- **밀기 검산** — 문자열 하나를 줄여 뒤를 전부 민 뒤, **게임이 하듯 표를
  따라가** 같은 글자가 나오는지 본다. 내 오프셋 표와 맞춰 보면 같은 믿음을
  두 번 확인하는 것이라 소용이 없다
- 디스크에 쓴 뒤에도 같은 역참조로 1,320건을 다시 확인한다

### 축약 396 -> 67건

제약이 문자열 단위에서 섹션 단위로 바뀌자 축약의 대부분이 필요 없어졌다.
`scripts/fit_kernel_text.py` 가 **완역에서 시작해 모자란 섹션에만** 필요한
만큼 축약을 얹는다. 남은 67건은 **전부 설명문**이고, 아이템·마법·어빌리티
이름은 완역 그대로다.

이름과 설명은 구조가 갈라 준다 — 레코드의 **+0 필드가 이름, +2 가 설명**이다.
표가 하나뿐이고 간격이 2B 면 둘이 번갈아 든다(#39·#55). 띄어쓰기만 지우는
것은 용어를 안 건드리므로 이름에도 허용한다.

것**이다(`GFHP+10%` 자리에 「G.F.의 HP를 10% 증가시킵니다」).
