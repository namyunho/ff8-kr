# 폰트와 텍스트 인코딩 분석

검토일: 2026-07-27
대상: `Final Fantasy VIII (Japan, Asia) (Disc 1)`

이 문서는 Disc 1의 글꼴 공급자와 문자 인코딩을 정적 분석으로 확정한 기록이다.
런타임 VRAM 검증은 아직 수행하지 않았다.

## 파일 구조 — IMG 엔트리 #130

```text
offset      크기        내용
0x0000         4        u32 = 8      → 폭 테이블 오프셋
0x0004         4        u32 = 452    → TIM 헤더 오프셋
0x0008       452        글리프 폭 테이블 (니블 팩)
0x01C4         8        TIM 헤더: magic 0x10, flag 0x08 (4bpp + CLUT)
0x01CC        12        CLUT 블록 헤더: blockSize 1,036, RECT (896,256) 16 × 16
0x01D8     1,024        CLUT 데이터
0x05D8        12        IMG 블록 헤더: blockSize 16,140, RECT (640,0) 64 × 252
0x05E4    32,256        픽셀 데이터 (256 × 252, 4bpp)
합계      33,764
```

`0x05E4`부터 파일 끝까지가 정확히 `64 × 252 × 2 = 32,256`바이트다
(`33,764 − 1,508 = 32,256`).

### `blockSize` 와 RECT 는 쓰임이 다르다

두 필드를 하나로 뭉뚱그리면 틀린다. **쓰임이 나뉘어 있다.**

| 용도 | 정본 필드 |
|---|---|
| 파일 안에서 다음 블록으로 건너뛰기 | **`blockSize`** |
| VRAM 전송량 결정 | **RECT** |

적재기 `sub_8002C358` 이 그대로 보여 준다.

```asm
addiu $a3, $a2, 8      ; a3 = TIM + 8  = 0x01CC   CLUT 블록
lw    $v0, 8($a2)      ; v0 = CLUT blockSize = 1036
addu  $s2, $a3, $v0    ; s2 = 0x01CC + 1036 = 0x05D8   IMG 블록
```

즉 **픽셀 데이터의 시작 위치는 CLUT 블록의 `blockSize` 가 정한다.** CLUT
블록은 `blockSize` 1,036 인데 RECT 로는 `16 × 16 × 2 = 512` 라 524바이트가
어긋나고, IMG 블록은 `blockSize` 16,140 인데 실제 데이터는 32,256 이다.
전송량만 보면 RECT 가 맞지만, **순회에까지 RECT 를 적용하면 픽셀 시작이
12바이트 밀린다. 4bpp 에서 12바이트는 24픽셀 = 정확히 2셀이라 모든 글리프가
인덱스 4 만큼 어긋난다.**

> **이 문서의 이전 판이 실제로 그 오류를 담고 있었다.** 픽셀 시작을 `0x05F0`
> 으로 적었고, 그 값으로 렌더하면 인덱스 74 가 カ 가 아니라 ク 로 나온다.
> `0x05E4` 로 고치면 아래 확정값(カ=74, ド=38, ワ=150, キ=76, ク=78, ケ=80,
> コ=82, ル=138, ア=106, リ=136, ナ=114, ム=128, グ=14, ー=223)이 순서대로
> 그대로 재현된다. 폭 테이블도 같은 정렬을 지지한다 — 폭 9 인 10연속 구간이
> 인덱스 51..60 이고 이는 숫자 `0`..`9` 다.
>
> `scripts/build_hangul_font.py` 는 영향받지 않는다. 생성기는 CLUT 블록에
> `blockSize` 1,036 을 그대로 쓰므로 픽셀이 `0x05E4` 에 놓인다. 잘못된 것은
> 문서와 그 주석뿐이었다.

**TIM 헤더의 `VRAM(640,0)`도 실제 적재 위치가 아니다.** 적재기가 좌표를
하드코딩된 값으로 덮어쓴다(아래 참조).

## 적재 경로 — `sub_8002C358`

IDA와 Ghidra가 독립적으로 같은 결과를 냈다. 호출자는 `0x80011CDC`
(함수 `sub_80011CA8`) **한 곳뿐**이며, 그 호출은 다음과 같다.

```c
int sub_80011CA8(void)
{
    sub_800386B0(0, 0, 0x80144000, 0);
    while (sub_8003924C() != 0)
        ;
    sub_8002C358(dword_801B0000, 0);   // ← 뱅크 인자가 상수 0
    do
        result = DrawSync(1);
    while (result != 0);
    return result;
}
```

**뱅크 1은 원본 코드에서 한 번도 적재되지 않는다.** 적재기와 인코딩은 뱅크 1을
지원하지만 호출이 없다. 따라서 원본에서 실제로 살아 있는 글리프는 뱅크 0의
**882개**이고, 1,764개를 쓰려면 뱅크 1을 적재하는 호출을 새로 넣어야 한다.
폰트 파일은 RAM `0x801B0000` 에 적재된 상태로 전달된다.

```c
if (param_2 == 0) {                       // 뱅크 0
    dst_rect = 0x010003C0;                // VRAM (960, 256)   ← 정정
    width_table = &dword_800821F8;
    if (tim_flag & 8) {                   // CLUT 있으면 먼저 올린다
        rect = 0x00E00120;                // VRAM (288, 224)
        if (height > 16) height = 16;     // 높이 16으로 클램프
        LoadImage(&rect, clut_data);
    }
} else {                                  // 뱅크 1
    dst_rect = 0x01000340;                // VRAM (832, 256)   ← 정정
    width_table = &dword_800823BC;
}
memcpy(width_table, file + file[0], 452); // 폭 테이블을 RAM 으로
LoadImage(&dst_rect, image_pixels);       // 크기만 TIM 에서 가져온다
```

VRAM 배치는 다음과 같다. 세 영역이 인접해 빈틈이 없다.

```text
x=832..896  y=256..508   **뱅크 1** (필드 전용 TDW)
x=896..960  y=256        CLUT
x=960..1024 y=256..508   **뱅크 0** (시스템 폰트)
```

> **이 표는 한때 뒤바뀌어 있었다.** 디컴파일러가 `bne`(0이 **아니면** 뛴다)를
> `if (a2 != 0)` 로 내는데, 그 블록을 "뱅크1 경로" 로 읽은 것이 원인이다.
> 실제로는 **뛰는 쪽이 뱅크1, 떨어지는 쪽이 뱅크0** 이다. 디스어셈블로 확인한다.
>
> ```asm
> bne   zero, t0, +0x22      ; t0 = 뱅크 인자. 0 이 아니면 뛴다
> addiu v0, zero, 0x3c0      ; ← 떨어지는 쪽 = 뱅크0, x = 960
> addiu s1, v1, 0x21f8       ;   폭표 0x800821F8
> ...
> 0x8002c444:                ; ← 뛰는 쪽 = 뱅크1
> addiu s1, v0, 0x23bc       ;   폭표 0x800823BC
> addiu v0, zero, 0x0340     ;   x = 832
> ```
>
> 런타임 관측이 이것을 잡았다. 폰트 파일의 픽셀 252행 전체가 `(960,256)` 에서
> 바이트까지 일치했고, 폭 테이블은 `0x800821F8` 에서 888/888 일치했다. 둘 다
> **뱅크0** 이므로 어긋난 것이 아니라 표가 틀렸던 것이다.

**기존 두 슬롯은 좌우로 넓힐 수 없다.** 뱅크 0의 오른쪽은 CLUT, 뱅크 1의
오른쪽은 VRAM 경계(1024)다. 다만 뱅크를 **다른 위치에 추가**하는 것은 가능하다.
디스크 전체 TIM 의 RECT 94개로 점유 맵을 만든 결과 `x=320..512, y=256..508`
구간이 비어 있어 64×252 슬롯 3개가 더 들어간다. **이 맵은 정적 RECT 기반이라
필드 배경의 런타임 점유를 반영하지 않는다.** 런타임 검증 전에는 추정이다.

## 글리프 폭 — `sub_8002E3EC`

452바이트 테이블은 니블 단위 폭 테이블이다.

```c
int glyph_width(int index)
{
    unsigned char *table;
    if (index & 0x400) { index &= 0x3FF; table = dword_800823BC; }  // 뱅크 1
    else               {                 table = dword_800821F8; }  // 뱅크 0
    unsigned v = table[index >> 1];
    if (index & 1) v >>= 4;
    return v & 0xF;
}
```

452바이트 × 2니블 = **904 엔트리**로 뱅크당 인덱스 0..895를 모두 덮는다.
니블 값 분포는 `13`이 537개로 가장 많고 `12`가 131개, `11`이 102개,
`9`가 49개, `10`이 42개다. 12픽셀 셀에서 `13`은 글리프 12픽셀 + 간격 1픽셀의
전각 진행폭으로 읽는 것이 자연스럽다.

> 테이블 인덱스와 텍스처 격자 칸은 1:1이 아니다. 셀 하나에 글리프 두 개가
> 인터리브되므로 `셀 = 인덱스 >> 1` 이다. 둘을 1:1로 놓고 검증하면 틀린
> 결론이 나온다. 자세한 내용은 아래 블리터 절을 본다.

## 텍스트 인코딩 — `sub_8002E4A0`

문자열 폭·높이 계산기가 인코딩을 그대로 드러낸다.

| 바이트 | 의미 |
|---|---|
| `0x00` | 문자열 종료 |
| `0x01` | 줄 초기화 (행 카운터를 1로) |
| `0x02` | 줄바꿈 |
| `0x05` + 1바이트 | 변수 삽입. `sub_8002C700(id)` 로 문자열을 얻어 폭을 더한다 |
| `0x07` | 페이지 리셋 |
| `0x03`,`0x04`,`0x06`,`0x08`..`0x0F` | 파라미터 1바이트를 소비하는 제어 코드 |
| `0x10`..`0x17` | 폭에 기여하지 않는 코드 |
| `0x18`..`0x1B` + 1바이트 | 2바이트 문자, 뱅크 0 |
| `0x1C`..`0x1F` + 1바이트 | 2바이트 문자, 뱅크 1 |
| `0x20`..`0xFF` | 1바이트 문자, `index = byte - 32` |

2바이트 문자의 인덱스 산출식:

```text
lead 0x18..0x1B :  index =  224 * lead + trail - 5408
lead 0x1C..0x1F :  index = (224 * lead + trail - 6304) | 0x400
```

`trail`이 `0x20..0xFF`(224가지)일 때 각 lead가 224개 인덱스를 담당한다.

| lead | 뱅크 | 인덱스 범위 |
|---|---:|---|
| `0x18` | 0 | 0 .. 223 |
| `0x19` | 0 | 224 .. 447 |
| `0x1A` | 0 | 448 .. 671 |
| `0x1B` | 0 | 672 .. 895 |
| `0x1C` | 1 | 0 .. 223 |
| `0x1D` | 1 | 224 .. 447 |
| `0x1E` | 1 | 448 .. 671 |
| `0x1F` | 1 | 672 .. 895 |

즉 **인코딩이 표현할 수 있는 글리프는 뱅크당 896개, 합계 1,792개**다.
1바이트 문자(`0x20..0xFF`)는 뱅크 0의 인덱스 0..223과 같은 공간을 가리킨다.

행 높이는 `16 * 행수 - 4`로 계산된다. 한 줄의 진행 높이가 16픽셀이라는 뜻이다.

## 글리프 블리터와 2중 팔레트 인터리브

블리터는 두 개다. `sub_8002E8F8` 이 범용 문자열 출력, `sub_8002EE90` 이
대사창 렌더러이며 둘 다 같은 계산을 쓴다.

```c
// 텍스처 좌표
*(WORD *)(prim + 16) = 12 * (((index >> 1) % 21) | (((index >> 1) / 21) << 8));
// CLUT 선택
attr = 14354;                       // 0x3812 → VRAM (288, 224)
if (index & 1) attr = 14418;        // 0x3852 → VRAM (288, 225)
*(WORD *)(prim + 18) = attr + ((theme & 7) << 7);
```

**셀 위치는 `index >> 1` 로 정하고 짝/홀은 CLUT 로 가른다.** 즉 한 셀에 글리프
두 개가 인터리브돼 있다. 4bpp 픽셀의 **하위 2비트가 짝수 글리프, 상위 2비트가
홀수 글리프**다. 원본 CLUT 가 이 구조를 그대로 증명한다.

```text
pal0 = 000000 a5a5a5 636363 525a52  (4색 x 4반복)   -> 하위 2비트만 읽는다
pal1 = 000000 x4  a5a5a5 x4  636363 x4  525a52 x4   -> 상위 2비트만 읽는다
pal2 / pal3 = 같은 구조의 두 번째 색 테마
```

티스토리 자료가 말한 "8x8 폰트 2중 팔레트 방식" 의 실체가 이것이다.

**따라서 수용량은 뱅크당 441칸이 아니라 882글리프다.**

| 항목 | 값 |
|---|---:|
| 텍스처 셀 | 441 (21 × 21) |
| 셀당 글리프 | 2 |
| **뱅크당 글리프** | **882** |
| 폭 테이블 엔트리 | 904 (452바이트 × 2니블) |
| 뱅크 2개 | 1,764 |
| **뱅크 3개** | **2,646 — 완성형 2,350자 전체 수용** |

폭 테이블 904 엔트리가 882 를 덮는다는 점이 이 해석의 독립 근거다.
`theme` 은 `(v9 & 7) << 7` 로 CLUT 를 8단계 옮기므로 색 테마가 8종이다.

## 대사 출력 파이프라인

부트 EXE 안에서 대사가 화면에 나오기까지의 경로를 전수 추적했다.

```text
필드 스크립트 (오버레이 — 부트 EXE 밖)
  └─ sub_8002D708 / sub_8002D748 / sub_8002D7DC   메시지 표시 API
       └─ sub_8002D670(창id, 원시메시지포인터)     세터
            window[2] = ptr   ← 오프셋 8, 렌더러가 읽는 값
            window[3] = ptr   ← 페이지 되감기용 시작 위치
            window[9] = 0     ← 상태 머신 리셋
       └─ sub_8002CC10(창id, OT버퍼)               창 관리
            └─ sub_8002EE90(OT버퍼, 창구조체)      대사창 렌더러
                 ├─ sub_8002F73C(원시, 버퍼, 한계)  토큰 확장
                 ├─ sub_8002F5FC(원시)              다음 줄
                 ├─ sub_8002E3EC(index)             글리프 폭
                 └─ SPRT 프리미티브 발행
```

### 창 구조체

`dword_80081D10` 이 창 구조체 배열이며 **한 창이 15 dword(60바이트)** 다.
`&dword_80081D10[15 * windowId]` 로 인덱싱한다. 확인한 필드는 다음과 같다.

| 오프셋 | 용도 |
|---:|---|
| `+8` | **원시 메시지 포인터** (0이면 렌더링하지 않는다) |
| `+12` | 메시지 시작 위치 백업 |
| `+18` | 세로 기준 좌표 |
| `+20` | 색 테마 (상위 4비트) |
| `+24` | 창 id |
| `+32` `+34` | 선택지 커서 범위 |
| `+36` | 상태 머신 상태 |
| `+40` | 완료 플래그 |
| `+41` `+42` `+43` | 선택지 최소·최대·현재 |
| `+48` `+50` | 텍스트 시작 x, y |

### 토큰 확장기 `sub_8002F73C`

`sub_8002F73C(char *src, BYTE *dst, int limit)` 가 원시 메시지를 출력용 버퍼로
편다. 여기서 변수 삽입 제어 코드가 실제 문자열로 치환된다.

| 코드 | 동작 |
|---|---|
| `0x03` + 1바이트 | 파라미터 상위 니블로 분기해 이름·수치 삽입 |
| `0x04` + 1바이트 | 캐릭터 이름 / GF 이름 / 숫자 테이블 조회 |
| `0x0C` + 1바이트 | `sub_80020BE4(param - 32)` 문자열 조회 |
| `0x0D` + 1바이트 | `sub_80020CBC(param - 32)` 문자열 조회 |
| `0x0E` `0x0F` + 1바이트 | `sub_8002F6C4` 로 표 참조 |
| `0x00` `0x01` `0x02` `0x07` | 확장 종료 |

버퍼 한계는 기본 128바이트이며 `a3 < 0` 이면 그 값을 쓴다.

### 메시지 조회 — `sub_801F1078` (오버레이 #4)

`jal 0x8002D670` 바이트 패턴으로 디스크를 훑어 세터를 쓰는 오버레이를 찾았다.
오버레이 #12(base `0x801E4000`)의 세 지점이 모두 같은 형태다.

```asm
addiu $a0, $zero, 1          ; root 선택
addiu $a1, $zero, 7          ; 그룹
addiu $a2, $zero, 10         ; 메시지 id  (다른 지점은 11, 12)
jal   0x801F1078             ; 메시지 조회
addu  $a3, $zero, $zero      ; 서브 인덱스
addu  $s0, $v0, $zero        ; 반환 = 원시 메시지 포인터
jal   0x8002D670             ; 세터
addu  $a1, $s0, $zero
```

조회 함수는 오버레이 #4(base `0x801F0000`)의 `+0x1078` 에 있다.

```c
void *lookup(void *base, int index)          // sub_801F1050
{
    unsigned short off = *(unsigned short *)((char *)base + 2 + index * 2);
    return off ? (char *)base + off : NULL;  // 0 은 빈 슬롯
}

void *get_message(int root_sel, int group, int id, int sub)   // sub_801F1078
{
    void *root = root_sel ? (void *)0x801E1000 : *(void **)0x80208894;
    void *t1 = lookup(root, group);
    void *msg = t1 ? lookup(t1, id * 2 + sub) : NULL;
    return msg ? msg : (void *)0x80208844;   // 실패 시 빈 문자열
}
```

**메시지 아카이브는 2단 u16 상대 오프셋 테이블이다.** 각 단은 2바이트 헤더 뒤에
u16 배열이 오고, 값은 그 단의 시작을 기준으로 한 상대 오프셋이며 `0` 은 빈
슬롯을 뜻한다. 2단 인덱스가 `id * 2 + sub` 인 점에 주의한다.

### `0x801E1000` 의 출처 — 확정

모듈 로더를 추적해 답을 얻었다. 경로는 `docs/disc1-baseline.md` 의 "모듈 적재
경로" 절에 정리했고, 결론만 옮기면 다음과 같다.

```text
sub_8003632C  (메뉴 진입 시퀀서)
  └─ sub_80036078(1, 0x801E1000)
       └─ sub_80035F48(0, 아카이브 18, 서브 1, 0x801E1000, 콜백없음, 0)
            └─ sub_80035C84  아카이브 18 = TOC #22 = mngrp.bin (LBA 98,035)
                             서브 1 = 섹터 오프셋 1, 크기 10,240
                             → 실제 LBA 98,036
```

**`0x801E1000` 에는 `mngrp.bin` 의 서브엔트리 1(LBA 98,036, 10,240바이트)이
적재된다.** 아카이브 이름은 부트 EXE 안의 이름 문자열 표에서 그대로 읽었다.

같은 시퀀서가 직후에 `0x801F0BEC` 를 간접 호출한다. `0x801F0000` 은
`menumain.ovl` 의 적재 주소이므로 **메시지 조회 `sub_801F1078` 이 오버레이 #4
안에 있다는 기존 판정과 일치한다.**

### 2단 테이블 검증 — 통과

적재되는 10,240바이트를 그대로 파싱해 `get_message(1, 7, 10, 0)` 을 재현했다.

| 항목 | 값 |
|---|---|
| 1단 헤더 u16 | 16 (그룹 수) |
| 유효 그룹 | 15 (그룹 15 는 빈 슬롯) |
| 메시지 총수 | **579** |
| `0x00` 으로 정상 종료 | **579 / 579** |
| 최대 글리프 인덱스 | 817 (뱅크 0 범위 안) |
| `get_message(1,7,10,0)` | 그룹 7 `+0x1280`, 2단 헤더 70, 인덱스 20 → `+0x13C7`, 16바이트 |

원본 폰트로 렌더한 결과 읽히는 일본어가 나왔다.

```text
つかう / アイテムを使用します
バトルはいち / バトル時のアイテム配置

```

정션·상점·환경설정·이름 입력 — `mngrp.bin` 이라는 이름과 정확히 맞는
**메뉴/시스템 메시지 아카이브**다.

따라서 이 2단 u16 형식은 **메뉴 계열 전용**이며, 필드 대사는 형식이 다르다.
필드 쪽은 아래에서 따로 확정했다.

## 필드 메시지 — MSD 섹션

필드 대사는 위 2단 형식이 아니다. 경로가 완전히 다르다.

```text
field.bin (IMG TOC #2, LBA 33,249, LZSS → 191,824B)
  └─ 필드 파일 목록 1,003개  [u32 절대 LBA][u32 바이트 크기]
       └─ 각 필드의 *.DAT (LZSS)
            └─ 섹션 포인터 12개 중 [8] 이 MSD(텍스트) 섹션
                 └─ [u32 오프셋 배열][null 종료 메시지들]
```

### 필드 파일 목록

`field.bin` 을 해제하면 다음 28바이트 뒤에 목록이 있다. 이 시그니처는 함수
에필로그이며 목록은 그 직후에 시작한다.

```text
04 00 05 24 18 00 bf 8f 14 00 b1 8f 10 00 b0 8f 20 00 bd 27 08 00 e0 03 00 00 00 00
```

실측: 해제본 오프셋 `0x2864C` 에서 발견, 목록은 `0x28668` 부터 8,024바이트
= **엔트리 1,003개**. 형식은 IMG TOC 와 같은 `[u32 절대 LBA][u32 크기]` 다.
LBA 범위는 33,301..87,815 이고 **정렬돼 있지 않다.**

이전 판이 기록한 대사 위치 6곳이 전부 이 목록 안의 파일에 들어간다.

| 기록된 LBA | 목록 인덱스 | 파일 LBA | 크기 |
|---:|---:|---:|---:|
| 34,230 | 104 | 34,228 | 12,558 |
| 34,358 | 107 | 34,356 | 12,558 |
| 44,238 | 275 | 44,232 | 19,278 |
| 45,363 | 293 | 45,360 | 12,977 |
| 45,550 | 296 | 45,547 | 12,198 |
| 49,880 | 365 | 49,876 | 15,495 |

### DAT 섹션 헤더

각 필드 DAT 는 `[u32 압축크기][LZSS 스트림]` 이다. 해제하면 선두에 **PSX RAM
주소로 된 포인터 12개**가 있고, 첫 섹션이 파일 오프셋 48 에서 시작한다.

```text
파일오프셋(i) = ptr[i] - ptr[0] + 48
```

| 인덱스 | 섹션 |
|---:|---|
| 0 | INF 트리거·게이트웨이 |
| 1 | CA 카메라 |
| 2 | ID 워크메시 |
| 3 | MAP 배경 정보 |
| 4 | MSK 무비 카메라 |
| 5 | RAT 인카운터율 |
| 6 | MRT 전투 편성 |
| 7 | AKAO 사운드 |
| **8** | **MSD 텍스트** |
| 9 | PMD 파티클 |
| 10 | JSM 스크립트 |
| 11 | 파일 끝 |

`ptr[11]` 로 계산한 오프셋이 **해제 크기와 정확히 일치**한다. 이것이 헤더
해석의 검산이다. 실측 예(목록 #104): 해제 34,820바이트, `ptr[11]` → 34,820.

### MSD 형식

```text
[u32 offset[N]]      N = offset[0] / 4        ← 첫 오프셋이 배열 끝을 표시한다
[null 종료 메시지들]                            오프셋은 MSD 섹션 시작 기준
```

값 `0` 을 빈 슬롯으로 쓰는 메뉴 형식과 달리, **MSD 는 빈 메시지를 `0x00`
하나만 있는 문자열로 표현한다.** 오프셋은 단조 증가한다.

검증 결과다. 앞선 판은 **앞쪽 140개 DAT 만** 훑은 부분 결과였다. 목록
1,003엔트리를 전수로 훑으면 수가 달라진다. 5,445 는 앞 138개 필드까지의
누적치이며 전체가 아니다.

| 항목 | 부분(앞 140 DAT) | **전수(목록 1,003엔트리)** |
|---|---|---|
| 필드 DAT | 140 | **302** |
| MSD 메시지 | 5,445 | **9,442** |
| 그중 빈 문자열 | 89 | **277** |
| 형식 위반 | 0 | **0** |

DAT 는 목록만으로 가려지지 않는다. 해제한 뒤 포인터 12개가 단조 증가하고
`ptr[11]` 이 해제 크기와 맞물리는지로 판정한다. 이렇게 고른 302개는 **전부**
목록 인덱스가 `≡ 2 (mod 3)` 이라 3종 세트 구조와도 어긋나지 않는다.
`scripts/build_text_db.py` 가 이 판정을 그대로 쓴다.

목록 #104(필드 이름 `test5`)를 원본 폰트로 렌더한 결과다.

```text
「リノア？ ＹＥＳ ＮＯ」
「 キスティス  アーヴァイン  ゼル  なし」
「 1 マスターとのバトル後  2 マスターとのバトル前  3 カドワキ先生と
```

이전 판이 찾은 「カドワキ」 가 이 파일의 **메시지 #66** 안에 있다.

### 파일 3종 세트 순서 — 확인

필드 파일 목록은 필드마다 **MIM → DAT → LZK 순서**로 세 엔트리를 연달아
놓는다. 해제 크기 패턴이 크게/작게/중간으로 3주기 반복하며, 가운데가 DAT 다.

| 목록 | 해제 크기 | 종류 |
|---:|---:|---|
| 103 | 441,944 | MIM |
| 104 | 34,820 | **DAT** |
| 105 | 228,080 | LZK |
| 106 | 441,944 | MIM |
| 107 | 34,820 | **DAT** |
| 108 | 228,080 | LZK |

### 필드 전용 추가 폰트 — MIM 의 TDW 섹션

**뱅크 1 은 죽어 있지 않다.** MIM 의 섹션 3 이 필드 전용 폰트이고, 구조가
`sysfnt.tdw`(IMG TOC #130)와 같다.

```text
0x000000   4    u32 = 8     폭 테이블 오프셋
0x000004   4    u32         TIM 오프셋
0x000008   —    폭 테이블 (니블 팩)
                TIM: magic 0x10, flag 0x08 (4bpp + CLUT)
```

MIM 선두가 이 섹션의 위치를 준다.

```text
[0] u32   섹션 3 (TDW) 의 PSX RAM 주소
[4] u32   섹션 4 (PMP) 의 PSX RAM 주소
[8] u32   PVP (관측값 12)
```

실측 두 필드에서 **TDW 의 글리프 수와 그 필드 MSD 가 쓰는 뱅크 1 인덱스
범위가 정확히 맞물린다.**

| 필드 | TDW 폭표 | 텍스처 | 글리프 | MSD 뱅크 1 인덱스 |
|---|---:|---|---:|---|
| MIM #103 / DAT #104 | 64 | 256 × 24 | 84 | 0 .. 56 (57종, 107회) |
| MIM #97 / DAT #98 | 128 | 256 × 36 | 126 | 0 .. 123 (124종, 421회) |

즉 **필드는 자기 전용 글리프를 MIM 에 싣고 MSD 가 `0x1C`~`0x1F` 리드로
참조한다.** 필드 텍스트 표본에서 `0x1C` 리드가 4,950회 나온 이유가 이것이다.

> **한국어화 계획에 직접 영향을 준다.** 뱅크 1 슬롯은 비어 있는 자원이 아니라
> **필드마다 내용이 바뀌는 자리**다. 한글 뱅크를 여기에 그대로 올릴 수 없다.

### 남은 경계

- **뱅크 1 적재 경로는 미확정이다.** `jal sub_8002C358` 을 디스크 전체에서
  훑은 결과 **정확히 1곳**(LBA 28 `+0x4DC` = 런타임 `0x80011CDC`)뿐이고 뱅크
  인자는 `0` 이다. 즉 TDW 는 이 함수로 올라가지 않는다. 다른 경로가 있다.
  VRAM `(960,256)` 에 무엇이 언제 올라가는지는 런타임 확인이 필요하다.
- 목록 앞쪽 76개가 `D000.MCH`..`D075.MCH` 라는 외부 자료의 서술은 **확인하지
  않았다.**
- MIM 섹션 4(PMP)는 실측 필드에서 4바이트뿐이라 내용을 판정하지 않았다.

## 텍스트 저장 위치

대사 문자열은 **TOC 가 덮지 않는 공백 구간**에 있다. 「カドワキ」 를 단일바이트
`6A 46 B6 6C` 로 인코딩해 디스크 전체를 검색한 결과 6곳이 나왔고 모두
**LBA 34,230 ~ 49,880** 에 있었다.

| LBA | 오프셋 |
|---:|---|
| 34,230 | `+0x7BA` |
| 34,358 | `+0x7BA` |
| 44,238 | `+0x325` |
| 45,363 | `+0x0FE` |
| 45,550 | `+0x23A` |
| 49,880 | `+0x406` |

이 구간을 디코딩해 원본 폰트로 렌더한 결과 실제 대사가 읽혔다.

```text
「これから、試験なんだろ？」   「ケガはもういいのかい」
キスティス                     「あなた、なにも聞いてなかったでしょ」
「一人前の教官にはわからないかもしれない、けど」
「B班が持ち場を離れた」        「このコーナーはじゅんびちゅうです」
```

발람 가든, 키스티스, 시험, B반 — Disc 1 초반 내용이 맞다.

**이 6곳은 모두 `field.bin` 파일 목록 안의 필드 DAT 였다.** 위 표의 "LBA" 는
LZSS 스트림 중간을 가리키므로 그 자체로는 경계가 없다. 올바른 접근은
`field.bin` → 목록 → DAT 해제 → MSD 섹션이며 "필드 메시지 — MSD 섹션" 절에서
확정했다. 위 렌더가 제어 코드 파라미터를 일부 오독한 이유도 여기에 있다.
**압축된 스트림을 해제 없이 읽었기 때문**이지 인코딩 문제가 아니었다.

> 이 절의 원래 서술 "TOC 가 덮지 않는 공백 구간" 은 절반만 맞다. IMG TOC 가
> 직접 덮지 않는 것은 사실이나 **색인이 없는 공백이 아니라 `field.bin` 이
> 색인하는 구역**이다.

## 인덱스 ↔ 문자 대응표

단일바이트 영역(인덱스 0..223, 바이트 `0x20`..`0xFF`)의 배열 순서는 다음과 같다.

| 인덱스 | 내용 |
|---|---|
| 0 .. 49 | 탁음·반탁음 가나 (バ ば ビ び …) |
| 50 .. 60 | 숫자 `0`..`9` |
| 61, 62 | `、` `。` |
| 63 | **공백** — 픽셀이 없다 |
| 64 .. 155 | 청음 가타카나·히라가나 (ハ は ヒ ひ … ン ん ヲ を) |
| 156 .. 173 | 소문자 가나 9쌍 (ッ っ ャ ゃ ュ ゅ ョ ょ ァ ぁ ィ ぃ ゥ ぅ ェ ぇ ォ ぉ) |
| 174 .. 199 | 라틴 대문자 `A`..`Z` |
| 200 .. 209 | `!` `?` `…` `+` `−` `=` `※` `/` `%` `&` |
| 210 .. 213 | `「` `」` `(` `)` |
| 214 .. 217 | 収 容 所 駅 |
| 218 .. 223 | `・` `.` `,` `:` `～` `ー` |

**소문자 가나는 큰 글자와 같은 짝 구조(짝수 가타카나 / 홀수 히라가나)를 쓴다.**
모양이 같아 헷갈리므로 글리프 크기로 가른다. 예: 106(ア)은 9줄 28픽셀,
164(ァ)는 7줄 21픽셀이다. 같은 이유로 142 는 한자 口(300)가 아니라 가타카나
ロ 다 — 300 은 10줄 34픽셀, 142 는 8줄 30픽셀이다.

218 이후는 61(`、`) 62(`。`) 와 겹치지 않는 ASCII 계열 부호다.

확인한 값 예시: カ=74, キ=76, ク=78, ケ=80, コ=82, ド=38, ワ=150, ル=138,
ア=106, リ=136, ナ=114, ム=128, グ=14, ー=223.

224 이상은 2바이트 lead 로만 접근하며 대부분 한자다. 다만 **선두 두 자리는
한자가 아니다** — 224 는 라틴 소문자 `e`, 225 는 皿 이고 오십음순은 226 부터
시작한다.

| 694 .. 879 | 순서 없음 |
| 880, 881 | 빈 글리프 |

603..693 은 91자가 한 번도 어긋나지 않아 이 구간만큼은 순서로 검산할 수 있다.
탁음은 청음과 같은 순위로 다룬다(階 かい → 凱 がい → 街 がい → 官 かん).
순서가 없는 구간은 이미 확정된 글리프와 부수를 픽셀 단위로 대조해 좁혔다.

뱅크0 안에서 비트맵이 완전히 같은 글리프는 616 과 801 한 쌍뿐이고(둘 다 記),
픽셀이 하나도 없는 글리프는 63, 880, 881 세 개다. 63 은 공백이라 문자가 있고
880, 881 은 쓰이지 않는 자리다.

### 메시지 ↔ 문자열 코덱

`scripts/glyph_text.py` 가 대응표로 메시지 바이트를 펴고 다시 되돌린다.
`decode` 한 문자열을 `encode` 하면 **원본 바이트가 그대로 나온다.** 이 성질이
번역문 삽입의 전제다 — 문자열만 바꾸고 나머지는 건드리지 않는다.

**제어 코드는 하나도 버리지 않고 눈에 보이는 표기로 남긴다.** 대사 사이의
코드를 지우면 창 밖으로 흘러넘치거나 이름·수치 삽입이 깨진다. 번역할 때도
코드를 보면서 자리를 잡아야 한다. 줄바꿈 `02` 도 개행 문자로 펴지 않는다 —
표 계열 편집기를 거치면 조용히 사라지는 쪽이 개행이다.

| 표기 | 뜻 |
|---|---|
| `{01}` | 파라미터 없는 제어 코드 |
| `{03:30}` | 파라미터 있는 제어 코드. 코드와 값 모두 16진 두 자리 |
| `{b1:123}` | 필드 전용 폰트(뱅크1) 글리프. 뱅크0 대응표의 대상이 아니다 |
| `{g:801}` | 같은 문자가 두 인덱스에 배정됐을 때 표준이 아닌 쪽 |

중괄호는 이 폰트에 없으므로 본문과 겹치지 않는다. 제어 코드 자리는 `[01]x` 로
좁혀야 한다. `{b1:10}` 의 `b1` 도 유효한 16진이라 열어 두면 제어 코드로 읽힌다.

검증: 필드 303개 9,165 메시지를 풀었다가 되돌려 **왕복 실패 0건**이고, 쓰인
뱅크0 인덱스 중 대응표에 없는 것은 **0개**다. 같은 본문에서 뱅크1 글리프는
8,346개 나오며 이는 필드마다 다른 TDW 라 이 표로 읽지 않는다.

### 판독을 검산하는 세 가지 방법

눈으로 읽은 값은 반드시 아래로 되짚는다. 실제로 셋 다 오류를 잡아냈다.

1. **같은 문자가 두 인덱스에 배정됐는지** — 비트맵이 다른데 문자가 같으면 둘 중
   하나는 틀렸다. 816(間→聞), 577(客→各) 을 이 검사로 잡았다.
2. **글리프와 배정 문자를 나란히 렌더해 대조** — 347..351 이 한 칸씩 밀려 있던
   것을 이 대조로 찾았다. 347 자리의 臭 를 빠뜨려 襲 集 出 術 이 모두 앞으로
   당겨졌고 351 에는 실체 없는 瞬 이 들어가 있었다. **오십음순 구간이라도
   통째로 밀리면 순서 검산으로는 잡히지 않는다.**
3. **실제 대사를 디코드해 일본어로 읽히는지** — 가장 강한 검산이다.
   749(償→後) 와 350(術→出) 은 「あとはよろしく頼むよ」「言い出しました」가
   깨져 나오는 것으로 드러났다.

## 텍스처 내용

`work/` 에 렌더링해 육안 확인한 결과, 하나의 텍스처가 다음을 순서대로 담는다.

1. 탁음·반탁음 히라가나 (ば び ぶ べ ぼ …)
2. 청음 히라가나·가타카나 (か き く け こ / さ し す せ そ / あ い う え お …)
3. 숫자와 구두점 (`1 3 5 7 8 9`, 、 。)
4. 라틴 대문자
5. 괄호·기호
6. 한자 (나머지 대부분)

CLUT 팔레트 0의 색은 `000000 / a5a5a5 / 636363 / 525a52` 4색이 4회 반복된다.
따라서 픽셀의 **하위 2비트만 색을 결정**하고 상위 2비트는 팔레트 뱅크
선택용이다. 실효 계조는 4단계(투명 + 3단계 밝기)이며, 원본 폰트는 이 4계조로
안티에일리어싱돼 있다.

## 런타임 VRAM 실측 — 뱅크 좌표표가 뒤바뀌어 있었다 (2026-07-31)

PCSX-Redux 웹 API(`/api/v1/gpu/vram/raw`)로 실행 중 VRAM 1MB 를 통째로 받아
쟀다. `scripts/psx_live.py` 가 통로다.

### 관측

폰트 파일(TOC #130)의 픽셀 행 0·20·60·100·150·200·251 을 VRAM 전체에서 찾으니
**전부 `(960, 256+행)` 에서 바이트까지 일치**한다. 즉 시스템 폰트 252행 전체가
`(960,256)` 에 있다. 폭 테이블은 `0x800821F8` 에서 **888/888 일치**한다.

`(832,256)` 에는 두 셀행(84글리프)만 있고 문자 모양이지만 시스템 폰트가 아니다.
필드 TDW 의 IMG RECT 높이가 12행(227필드)인 것과 맞물린다.

### 판정

코드가 뱅크 인자로 폭 테이블과 VRAM RECT 를 **함께** 고르므로, 관측이 어긋나
보였다. 실제로는 **문서의 표가 뒤바뀌어 있었다.**

| 뱅크 인자 | 폭 테이블 | VRAM |
|---|---|---|
| `0` | `0x800821F8` | **`(960,256)`** |
| `1` | `0x800823BC` | **`(832,256)`** |

원인은 디컴파일 읽기다. Hex-Rays 가 `bne`(0 이 **아니면** 뛴다)를
`if (a2 != 0)` 로 내는데 그 블록을 "뱅크1 경로" 로 읽었다. 디스어셈블을 보면
**뛰는 쪽이 뱅크1, 떨어지는 쪽이 뱅크0** 이다.

**이 문서와 `AGENTS.md` 가 이 값을 확정으로 싣고 있었다.** 런타임 관측이 아니면
드러나지 않았을 오류다.

### 정적 점유 맵도 틀렸다

| 자리 | 정적 판정 | 실측 |
|---|---|---|
| `x=320..512, y=256..508` | 비어 있음(TIM RECT 94개 기준) | **65% 채움** |
| `x=448..831, y=256..511` | — | **0% — 실제로 비어 있다** |

정적 RECT 로 만든 점유 맵은 런타임 점유를 반영하지 못한다(R3). 이제
`psx_live.py --map` 이 실제 점유를 그린다.

## 폰트 확장 가능성 — 조사 결과

뱅크0 882칸으로 한글 완성형이 모자란다. **882칸을 넘길 방법이 있는가**를
`sub_8002EE90`(글리프 렌더러), `sub_8002E4A0`(문자열 측정),
`sub_8002E3EC`(폭 조회)와 폰트 파일의 CLUT 로 조사했다.

### 인코딩이 허용하는 것 (확정, 코드)

렌더러의 글자 해석은 이렇다.

```c
if (b >= 0x19) {                       // 글자
    if (b < 0x20) {                    // 2바이트
        t = *p++;
        index = (b >= 0x1C) ? ((224*b + t - 6304) | 0x400)   // 뱅크1
                            :  (224*b + t - 5408);            // 뱅크0
    } else index = b - 32;             // 1바이트
}
```

| 항목 | 값 |
|---|---|
| 뱅크 선택 | 인덱스 비트 `0x400` **하나뿐**. 뱅크는 2개가 상한이다 |
| 뱅크당 인덱스 | `0x3FF` 로 마스크되지만 리드가 4개뿐이라 실효 0..895 |
| 폭 필드 | **4비트**(`andi $v0, $v1, 0xF`) → **0 이 표현된다** |
| X 전진 | `x += width`. **분기도 하한도 없다** |
| VRAM 좌표 | `12 * ((cell%21) | ((cell/21)<<8))`, cell = index>>1 |
| 뱅크별 tpage | 하드코딩 상수 2개(`0xE0FFFF9F` / `0xE0FFFF9D`)를 뱅크 비트로 고른다 |
| 색 | `{06:XX}` 의 하위 4비트가 `(v & 7) << 7` 로 **CLUT 행 8개**를 고른다 |

마지막 줄이 `{06:XX}` 의 정체다. **색 지정 코드**이며, 관찰했던 "여닫는 쌍"은
색을 바꿨다 되돌리는 것이다.

### 쓰이지 않는 리드 바이트가 여덟 개 있다 (확정, 코드)

두 함수 모두 **`0x10`..`0x17` 을 아무것도 하지 않고 흘려보낸다.** 파라미터도
소비하지 않고 폭도 더하지 않는다. 여기에 뱅크를 더 붙이는 코드 패치가 가능하다
— 리드 하나가 224인덱스이므로 여덟 개면 **1,792칸**이다.

**다만 `0x18` 은 두 함수가 어긋난다.** 측정기는 뱅크0 리드로 읽어 다음 바이트를
소비하고, 렌더러는 흘려보내며 소비하지 않는다. 원본은 인덱스 0..223 을 1바이트
로만 쓰므로 `0x18` 이 실제로 나오지 않아 드러나지 않았다. **확장할 때 `0x18` 을
쓰면 폭 계산과 출력이 어긋난다.**

### 글리프 배경이 투명하다 (확정, 데이터)

폰트 파일의 CLUT 를 읽었다.

```text
CLUT0 (짝수 글리프)  0000 D294 B18C A96A  ×4 반복   ← 텍셀 하위 2비트가 색
CLUT1 (홀수 글리프)  0000×4 D294×4 B18C×4 A96A×4   ← 텍셀 상위 2비트가 색
```

두 경우 모두 **자기 비트가 0이면 CLUT 값이 `0x0000`** 이다. PS1 GPU 는 텍스처
프리미티브에서 `0x0000` 을 완전 투명으로 처리하므로 글리프의 배경은 그려지지
않는다. 셀 하나에 글리프 둘을 인터리브하는 방식이 여기서 나온다.

### 그래서 — 코드 패치 없는 확장 경로가 있다

폭 0 글리프를 겹쳐 그려 **자모를 조합**할 수 있다.

1. 폭이 4비트라 0 을 넣을 수 있고, 폭 테이블은 **폰트 파일 안에** 있다
2. 렌더러가 `x += width` 로만 전진하므로 폭 0 이면 다음 글자가 같은 자리에 온다
3. 배경이 투명하므로 뒤엣것이 앞엣것을 지우지 않는다
4. 측정기도 같은 폭 테이블을 쓰므로 폭 계산이 저절로 맞는다

**게임 코드를 한 줄도 고치지 않는다.** 바꾸는 것은 폰트 데이터와 인코더뿐이다.
초성·중성·종성 자모를 12×12 셀 안에 미리 배치해 넣고, 음절 하나를 글리프 두셋
으로 인코딩한다. 조합형 한 벌은 100~200글리프면 되므로 882칸 안에서 완성형
11,172자를 전부 표현할 수 있다.

바이트가 는다 — 음절 하나가 1~2바이트에서 2~3바이트가 된다. 그래서 **섞어 쓰는
편이 낫다**: 자주 쓰는 음절은 통글자로 두고 드문 음절만 조합한다. 초벌번역
실측에서 상위 827자가 본문의 99.754% 를 덮으므로, 나머지를 조합으로 돌리면
바이트 증가가 0.25% 안에서 끝난다.

### 자모 조합 — 갈무리로는 안 된다 (실측)

"12×12 에서 조합한 글자가 읽히는가" 는 실기 없이 답이 나온다. 갈무리는 완성형
폰트이므로 **음절 비트맵에서 자모를 역으로 뽑아** 다시 겹쳐 원본과 대조하면
된다. 같은 초성·같은 문맥을 쓰는 음절들의 **공통 픽셀**이 곧 그 초성이다.

교집합은 **안전한 최댓값**이다. 이보다 크게 잡으면 어떤 음절에는 없는 픽셀이
튄다. 그러므로 교집합들의 합집합이 원본을 못 덮으면 그 폰트는 그 granularity
로 분해되지 않는다는 뜻이다. `scripts/jamo_compose.py` 로 번역문이 쓰는 음절
827자를 재봤다.

| 문맥을 잘게 쪼갤수록 | 조각 수 | 원본과 완전 일치 | 중앙 어긋남 |
|---|---:|---:|---:|
| 초성 3벌 × 받침유무 | 189 | 3.4% | 18px |
| 초성을 중성별로 | 484 | 36.2% | 7px |
| 이웃까지 반영 | **936** | 53.4% | 0px |
| 압축 없음(문맥 최대) | 2,262 | 100% | 0px |

**53% 를 얻으려고 936조각이 필요한데 그건 아끼려던 882칸보다 많다.** 갈무리는
음절마다 12×12 에 따로 눌러 담은 디자인이라 자모로 갈라지지 않는다. `뼈` 는
42픽셀이 어긋난다.

**이것은 "갈무리에서 유도하기" 가 실패한 것이지 기술적 불가가 아니다.** 처음
부터 조합형으로 **설계된** 도트 폰트라면 초성 8벌 × 19 + 중성 4벌 × 21 +
종성 4벌 × 27 = **344글리프**로 구성상 완벽하게 조합된다. 882칸 안에 넉넉히
들어간다. 폰트를 바꾸는 일이다.

### 아직 검증하지 않은 것

- **겹쳐 그리기가 화면에서 실제로 합성되는가.** 위는 코드와 데이터에서 읽은
  것이고 실행으로 확인하지 않았다. 원본 폰트에는 폭 0 인 **실사용 글리프가
  없다**(881~887 은 미배정 빈 자리다). 즉 원본이 이 경로를 쓴 적이 없다
- **VRAM 여유** — 뱅크를 더 붙이는 안(①)은 여전히 R3 에 걸려 있다. 정적 RECT
  로는 `x=912..959, y=256..507` 이 비어 보이지만 필드 배경의 런타임 점유를
  반영하지 않는다

### BIOS 에 폰트를 넣는 안 — 기각

"폰트를 BIOS 에 주입하고 게임이 BIOS 를 참조하게 하자" 는 안이 나올 수 있다.
**얻는 것이 없다.**

**병목은 저장 위치가 아니다.** 폰트 파일은 33,764바이트뿐이고 디스크에는 FMV 가
615MB 를 쓴다. 저장 공간이 모자란 적이 없다. 882 라는 수는 VRAM 슬롯 크기
(64×252 halfword = 441칸 × 2)와 뱅크 비트 `0x400` 에서 나오며, **폰트가 어디에
저장되든 둘 다 그대로다.** GPU 는 VRAM 만 샘플링하므로 결국 `LoadImage` 로
같은 자리에 올라간다.

비용은 크다.

- BIOS 는 저작권 펌웨어다. 사용자마다 자기 BIOS 를 직접 패치해야 한다
- 실기에서는 모드칩이나 BIOS 교체가 필요해 사실상 에뮬레이터 전용이 된다
- 게임이 BIOS 폰트를 호출하지 않으므로(확정) ROM 에서 읽어 VRAM 에 올리는
  코드를 새로 넣어야 한다 — 폰트 파일을 갈아 끼우는 것보다 패치가 늘어난다

`SCPH-1001` 을 뜯은 결과 16×15 한자 2,934자와 악센트 라틴만 있고 한글이 없다는
것은 별개로 이미 확인했다(`docs/korean-font-feasibility.md`).

혼동하기 쉬운 곳이라 적어 둔다.

| 제약 | 현재 | 여유 |
|---|---|---|
| 인덱스 인코딩 | 뱅크 2개 × 896 = **1,792 주소 가능** | 이미 남는다. 우리가 882만 쓴다 |
| VRAM 거주 | 뱅크0 하나만 우리 것 | 뱅크1 은 필드 전용 TDW 가 덮는다(R1) |

**주소가 모자라서가 아니라 앉을 자리가 없어서** 882 에 묶여 있다. 리드 바이트를
늘리는 안(`0x10`..`0x17`)도 그 글리프가 앉을 VRAM 이 먼저 있어야 하므로 VRAM
안의 종속이다.

### 셀을 줄이면 칸이 는다 — 10×10 이 최적

텍스처는 256×252 로 고정이고 셀 크기가 격자를 정한다. 셀당 글리프 2개는 그대로다.

| 셀 | 열×행 | 글리프 | 필요(1,092) 대비 | 렌더러 단일 곱셈 |
|---|---|---|---|---|
| 12×12 (지금) | 21×21 | 882 | −210 | ○ |
| 11×12 | 23×21 | 966 | −126 | ✗ |
| 10×12 | 25×21 | 1,050 | −42 | ✗ |
| 11×11 | 23×22 | 1,012 | −80 | ○ |
| 10×10 | 25×25 | 1,250 | +158 | ○ — **그러나 52자가 뭉개진다** |
| 9×9 | 28×28 | 1,568 | +476 | ○ — **150자가 뭉개진다** |

**가로만 줄이는 것(10×12)은 손해다.** 세로를 12로 두면 행이 21 에 묶여 1,050 에
그치고, U 는 ×10 V 는 ×12 가 되어 **렌더러의 단일 곱셈이 깨진다.**

```c
uv = 12 * ((cell % 21) | ((cell / 21) << 8));   // U 와 V 를 한 번에
```

`12 * a` 가 255 를 넘지 않아야(a ≤ 20 → 240) 상위 바이트를 침범하지 않는다.
**정사각 셀이어야 이 구조가 유지된다.**

#### 그러나 셀을 줄이면 글자가 뭉개진다 — 12×12 가 하한이다

잉크 상자만 재고 "10×10 에 들어가므로 손실이 없다" 고 판정했는데 **틀렸다.**
들어가는 것과 **구별되는 것**은 다른 문제다. 서로 다른 음절이 같은 비트맵이
되는지를 세야 한다.

| 래스터 | 잉크 | 같은 비트맵이 되는 음절 |
|---|---|---|
| **12px** | 11×11 | **0자** |
| 11px | 10×10 | 47자 / 23쌍 — `지=자` `은=온` `한=힌` `안=인` |
| 10px | 10×9 | 52자 / 25쌍 — `을=올` `있=았` `말=맡=밀=밑` |
| 9px | 9×8 | **150자 / 65쌍** — `을=들=플=줄=물=울=둘=즐=풀=율` |
| 8px | 8×7 | 147자 / 53쌍 |

**11px 에서 이미 깨진다.** 갈무리11 은 11px 설계지만 FF8 의 12×12 셀에 맞추려면
12px 로 뽑아야 획이 다 산다. 9px 은 `을·들·플·줄·물·울·둘·즐·풀·율` 열 글자가
하나로 뭉개져 대사를 못 읽는다.

**잉크 상자는 필요조건이지 충분조건이 아니다.** 셀 축소로 칸을 늘리는 길은
갈무리로는 닫혀 있다.

바꿀 상수는 넷이며 전부 `lui`+`ori` 쌍이다.

| 대상 | 지금 | 10×10 |
|---|---|---|
| 21 나눗셈 매직 | `0x30c30c31` | `0x28f5c290` (shift 34 동일) |
| 프리미티브 w,h | `0x000C000C` | `0x000A000A` |

```asm
0x8002f0f4  lui  v0, 0x30c3      ┐ 21 로 나누는 매직
0x8002f0f8  ori  v0, v0, 0x0c31  ┘
0x8002f0fc  sra  a0, a2, 1       ; cell = index >> 1
0x8002f100  mult a0, v0
0x8002f104  lui  v0, 0x000c      ┐ w,h = 12,12
0x8002f108  ori  v0, v0, 0x000c  ┘
0x8002f12c  sra  v1, t1, 2       ; mfhi + 2 = shift 34
```

같은 쌍이 `sub_8002E8F8`(`0x8002ea44`/`ea54`)과 `sub_8002C0E0`(`0x8002c19c`,
숫자 스프라이트 표)에도 있다.

#### 곱셈은 전부 시프트·덧셈으로 풀려 있다

`×21` 과 `×12` 는 상수가 아니라 명령 열이다. 두 렌더러가 **완전히 같은 열**을
쓴다(`sub_8002EE90` 은 `0x8002f134`, `sub_8002E8F8` 은 `0x8002ea80`).

```asm
sll  v0, v1, 2      ┐
addu v0, v0, v1     │ ×21  (q*4 → q*5 → q*20 → q*21)
sll  v0, v0, 2      │
addu v0, v0, v1     ┘
subu a0, a0, v0     ; a0 = cell % 21
sll  v1, v1, 8      ; (cell/21) << 8
or   a0, a0, v1
sll  v0, a0, 1      ┐
addu v0, v0, a0     │ ×12  (a*2 → a*3 → a*12)
sll  v0, v0, 2      ┘
```

#### 10×10 패치

**전부 제자리 치환이고 명령 수가 같다.** 코드 길이가 안 바뀌므로 뒤의 분기
오프셋도 그대로다.

| 자리 | 지금 | 10×10 |
|---|---|---|
| 나눗셈 매직 | `0x30C30C31` (÷21) | `0x28F5C290` (÷25) |
| ×21 세 번째 | `sll v0, v0, 2` | `sll a1, v0, 2` |
| ×21 네 번째 | `addu v0, v0, v1` | `addu v0, a1, v0` |
| ×12 첫 번째 | `sll v0, a0, 1` | `sll v0, a0, 2` |
| ×12 세 번째 | `sll v0, v0, 2` | `sll v0, v0, 1` |
| 프리미티브 w,h | `0x000C000C` | `0x000A000A` |

`×25` 는 `(q*5)*5` 로 풀며 중간값에 임시 레지스터 하나가 필요하다. `a1` 이 이
구간에서 죽어 있어 쓸 수 있다. `×10` 은 `(a*5)*2` 라 **시프트 양만 2↔1 로
바뀐다.**

전수 검산했다.

| 검증 | 결과 |
|---|---|
| 현재 명령 열이 `12*((c%21)\|((c/21)<<8))` 를 재현 | 441칸 **어긋남 0** |
| 제안 열이 `10*((c%25)\|((c/25)<<8))` 를 재현 | 625칸 **어긋남 0** |
| U 최댓값 240 < 256 (상위 바이트 침범 없음) | ✔ |
| 두 나눗셈 매직 (shift 34 동일) | 0..4095 **어긋남 0** |

숫자 스프라이트 표(`sub_8002C0E0` `0x8002c19c`)에도 같은 매직이 있다. 그쪽은
숫자 10자만 쓰므로 함께 고쳐야 자리가 맞는다.

**아직 안 한 것**: 실기에서 돌려 보지 않았다. 폰트 생성기도 10×10 격자로
고쳐야 한다(`build_hangul_font.py` 의 `CELL`, `COLS`, `ROWS`).

### 정리

| 경로 | 코드 패치 | 상태 |
|---|---|---|
| ③ 뱅크0 서브셋 | 없음 | **채택.** 827자가 본문의 99.754%, 대사 4% 재작성 |
| 폭 0 자모 조합 | 없음 | 기구는 확정. **조합형 폰트가 따로 필요하다** |
| 리드 `0x10`..`0x17` 추가 | 필요 | 1,792칸 여유. 렌더러·측정기·적재기를 함께 고쳐야 한다 |
| ① VRAM 뱅크 추가 | 필요 | R3 미해결 |

서브셋이 코드 패치도 폰트 교체도 없이 끝나므로 **먼저 서브셋으로 간다.** 자모
조합은 나중에 더 많은 글자가 필요해질 때의 선택지로 남는다.

## 아직 닫히지 않은 항목

1. **필드 스크립트의 메시지 opcode** — 출력 경로와 MSD 섹션 형식은 확정했으나,
   JSM 스크립트가 어떤 opcode 로 MSD 인덱스를 지시하는지는 아직 읽지 않았다.
   대사를 *극 순서대로* 정렬하려면 필요하다. 다만 **번역 삽입 자체에는 필수가
   아니다** — MSD 인덱스를 보존한 채 문자열만 바꾸면 된다.
2. **필드 파일 목록의 종류 대응** — 1,003개 엔트리 중 어느 것이 MIM/DAT/LZK
   인지 목록만으로는 판정하지 못한다. 현재는 해제 후 포인터 12개의 단조성과
   `ptr[11] == 해제크기` 로 DAT 를 걸러낸다. 이 판정으로 표본 140개를 얻었고
   위반은 0건이었으나, **1,003개 전수로는 아직 돌리지 않았다.**
3. ~~**뱅크 1 적재 경로**~~ — **풀렸다(런타임 관측).** PCSX-Redux 의 GDB
   서버로 붙어 `0x800823BC` 를 읽으니 **채워져 있었다.** 앞 23바이트가 진짜
   폭 값(`dd dd dd cd 6d …`)이고 그 뒤로 TDW 의 TIM 헤더(magic `0x10`,
   flag `0x08`, CLUT RECT (256,224) 16×16)와 CLUT 데이터가 이어진다.
   `sub_8002C358` 이 `file+8` 에서 **452바이트를 고정 복사**하는 모양 그대로다.

   즉 **`sub_8002C358(tdw, 1)` 이 실제로 불린다.** 디스크 전수 스캔에
   `jal sub_8002C358` 이 1곳뿐이었으므로 **`jalr`(함수 포인터)로 불린다.**

   **정적 분석은 정반대 결론에 도달해 있었다** — "뱅크1 폭표를 쓰는 곳이
   없다". 읽기 참조 20곳만 보이고 쓰기가 안 보였기 때문이다. 실행해 보고서야
   갈렸다.
4. **뱅크 1을 한글에 쓸 수 있는가 — 부정적** — 이전 판은 "뱅크 1 이 비어 있으니
   `sub_8002C358(파일, 1)` 호출을 넣어 쓰자" 고 적었다. **이 전제가 틀렸다.**
   뱅크 1 슬롯은 필드마다 전용 TDW 로 덮인다. 한글 뱅크를 여기에 상주시키면
   필드 전용 글리프가 깨진다. 선택지는 위 "폰트 확장 가능성" 절에서 조사했다.
   1) VRAM 빈 구간에 뱅크 추가 — R3 에 걸려 있다(런타임 점유 미확인)
   2) 필드 TDW 재생성 — 필드 수만큼 작업이 늘어난다
   3) 뱅크 0 서브셋 — 초벌번역 실측으로 **대사 4% 재작성이면 된다**
   4) **폭 0 자모 조합** — 코드 패치가 필요 없다. 남은 위험은 가독성 하나다
5. ~~**2바이트 영역(224 이상) 대응표**~~ — 채웠다. 뱅크0 882글리프 중 **픽셀이
   있는 879자 전부**에 문자를 배정했다(미배정 63, 880, 881 은 빈 글리프다).
   **판독은 추정이며 실행 검증과 연결되지 않았다.** 렌더한 글리프와 배정 문자를
   나란히 놓고 대조했고, 중복 문자 검사와 동일 비트맵 검사를 통과했다.
6. **인덱스 882..895** — 인코딩은 뱅크당 896을 표현하지만 텍스처는 882글리프만
   담는다. 나머지 14개가 실제로 쓰이는지 확인하지 않았다.
7. **런타임 VRAM 검증** — 위 좌표가 실제 화면에서 그대로 쓰이는지 확인하지
   않았다.
