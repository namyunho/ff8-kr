# 번역 파이프라인

작성일: 2026-07-31

필드 대사를 뽑아 번역시키고, 넣을 수 있는지 검사하고, 필요한 한글 음절 수를
세는 경로다. **번역기를 갈아 끼울 수 있게** 만들어져 있다 — 어느 도구가
번역하든 `id<탭>번역문` 만 내면 된다.

M5 의 마지막 전제(번역문의 서로 다른 음절 수 ≤ 882)는 이 경로 끝에서 판정된다.

## 단계

```text
build_text_db.py            필드 DAT → 전수 텍스트 DB
export_for_translation.py   필드마다 워크시트(JSON)와 압축 프롬프트(TXT)
  ↓
  (번역)                    ← 백엔드는 갈아 끼운다. 아래 참조
  ↓
import_translation.py       되받기 · 같은 원문 전파 · 남은 것 배치 분할
check_translation.py        넣을 수 있는지 여덟 가지로 검사
count_korean_syllables.py   서로 다른 음절 수와 빈도순 배치 후보
build_hangul_font.py        그 배치로 FF8 형식 뱅크 생성
```

되받기는 **`ko` 말고 아무것도 받지 않는다.** JSON 을 통째로 돌려받으면 번역기가
`ja` 나 `byte_budget` 을 조용히 바꿀 수 있다. 원문이 오염될 경로를 아예 없앤다.

초안은 `work/` 안에 남는다. 내보내기를 다시 해도 번역이 날아가지 않도록
답장 쪽을 원본으로 두고 필요할 때마다 다시 합친다.

## 번역 백엔드는 고르는 것이다

**둘 다 유지한다. 상황에 따라 고른다.**

| 백엔드 | 쓰는 때 | 비용 | 품질 |
|---|---|---|---|
| **파일 꾸러미** — 밖의 대화형 AI 에 붙여 넣기 | 기본 | 이 세션의 토큰을 안 쓴다 | 좋다 |
| **로컬 모델** — LM Studio / Ollama 의 OpenAI 호환 HTTP | 대량·반복·재작업 | 무료 | **실측 결과 초벌 품질이 떨어진다** |

로컬 모델 품질이 떨어진다는 것은 이 프로젝트에서 관찰한 사실이다. 그러나
**버리지 않는다.** 전수 초벌번역은 파일 꾸러미로 받았다 — 21개 꾸러미 중
실제 대사 17개를 처리해 8,120건을 채웠다. 서브셋 재작업(아래)처럼 같은
문장을 여러 번 고쳐 써야 하는 일에는 무료라는 것이 크게 작용한다.

### 파일 꾸러미

```bash
python3 scripts/import_translation.py work/translate-draft work/translate \
    --bundle work/translate-bundle --bundle-size 300
```

전수 초벌번역을 이 방식으로 받았다. 꾸러미 21개(실제 대사 17 + 디버그 4)를
내고 답을 `work/translate-reply/` 에 모아 한 번에 되받았다.

꾸러미 하나가 **한 번에 붙여 넣을 분량**이다. 지침 전문·용어집·답장 형식
설명·원문이 다 들어 있어 새 대화창에 파일 하나만 넣으면 바로 일이 된다.
하나가 17,000자쯤이다.

자르는 단위는 파일 개수가 아니라 메시지 수다. 필드 하나가 1건부터 216건까지라
개수로는 못 자른다. **필드 번호 순서를 지켜** 자른다 — 번호가 가까운 필드는
게임에서도 붙어 있는 장면이라 앞뒤 문맥이 살아 있어야 번역이 나아진다.

개발용 디버그 필드는 뒤 꾸러미로 몰고 건너뛰어도 된다고 표시한다. 플레이어가
볼 수 없는 메뉴인데 번역하면 뱅크0 칸만 먹는다.

답은 `== 필드이름 ==` 절로 나뉜 `id<탭>번역문` 이며 아무 이름으로나
`work/translate-reply/` 에 저장하면 된다.

```bash
python3 scripts/import_translation.py work/translate-reply work/translate
```

### 로컬 모델

LM Studio 는 GUI 의 Developer 탭 또는 `lms server start` 로 OpenAI 호환 서버를
연다. 기본 `http://localhost:1234/v1` 이다. Ollama 도 같은 규격이다.

**MCP 가 필요 없다.** HTTP 이므로 `Bash` 에서 `curl` 로 직접 몬다.

```bash
curl -s http://localhost:1234/v1/models | python3 -m json.tool
```

권장 설정.

- **온도 0.2 안팎.** 형식 충실도가 문장 매끄러움보다 중요하다
- **한 요청에 20~40건.** 길게 물리면 뒤로 갈수록 형식이 흐트러진다
- 로컬 모델의 진짜 위험은 번역 품질이 아니라 **`{06:25}` 같은 토큰을 뭉개는
  것**이다

### 모델은 고르지 말고 재라

`check_translation.py` 가 **객관적 심판**이다. 제어 코드 누락·순서, 줄 수,
줄 폭, 일본어 잔존, 없는 글자를 기계로 판정한다. 그러므로 후보 모델에 같은
100건을 물리고 구조 위반율·음절 수·바이트를 나란히 뽑으면 된다. 추측할 필요가
없다.

## 검사기가 보는 여덟 가지

| 항목 | 뜻 |
|---|---|
| 코드 누락·추가 | 제어 코드의 종류·개수가 다르다 |
| 코드 순서 | 있기는 한데 순서가 다르다 |
| 구멍 남음 | `{b1:N}` 을 안 메우고 그대로 뒀다 |
| 일본어 남음 | 옮기다 만 가나·한자가 있다 |
| 줄 수 초과 | `{02}` 개수가 늘었다 |
| 메시지 예산 초과(참고) | 그 자체로 실패가 아니다. 필드 총량이 기준이다 |
| 줄 폭 초과 | 한 줄이 창 폭(302px)을 넘겼다 |
| 없는 글자 | 원본 폰트에도, 넣을 한글 배치에도 없다 |

`--report` 로 건별 JSON 을 낸다. 9,000건 규모에서는 사람이 눈으로 못 훑으므로
고칠 자리를 기계로 다시 돌리는 데 쓴다.

바이트 셈은 **항등 시험으로 검증했다** — `ko` 에 `ja` 를 그대로 넣으면 9,160건
전부 원본 바이트 수와 정확히 일치한다.

## 같은 원문에는 같은 번역

전체 9,160건 중 **3,172건(34.6%)이 다른 곳에도 똑같이 있는 원문**이다. 고유
원문은 6,667종뿐이고 카드 규칙 안내문 하나가 60곳에 반복된다.

```bash
python3 scripts/import_translation.py work/translate-draft work/translate --propagate
```

필드마다 따로 번역시키면 번역량이 37% 늘고 같은 문장이 수십 가지 표기로
갈린다. 시범 361건이 1,408건을 더 채웠고(3.9배) 갈린 표기 12종을 잡았다
(『랜덤핸드』 vs 『랜덤 핸드』).

같은 원문에 다른 번역이 이미 있으면 **많은 쪽**으로 맞추고 갈린 사실을 알린다.

## 끊겨도 이어진다

번역은 한 번에 끝나지 않는다. 세션이 끊기거나 한도에 걸린다.

- 답장은 **필드 단위로 파일에 남는다.** 중간에 죽어도 거기까지는 산다
- `--status` 가 남은 것을 메시지 수로 고르게 나눠 보여준다
- `--refresh-prompts` 가 이미 채워진 자리를 빼고 시트를 다시 쓴다

끝났는지는 답장 파일이 있는지가 아니라 **워크시트의 `ko` 가 찼는지**로 본다.
같은 원문 전파로 답장 없이 채워지는 필드가 있기 때문이다.

## 지침이 틀렸던 곳 — 실측 기록

지침은 짐작으로 쓰였고 시범 번역으로 고쳤다. 같은 실수를 되풀이하지 않도록
남긴다.

| 항목 | 틀렸던 내용 | 실측 |
|---|---|---|
| `{06:XX}` | "한 글자처럼 취급" | **여닫는 쌍.** 1,564건이 정확히 2개씩 쓰고 `25`→`27` 이 1,433회. 한쪽만 남기면 뒤 문장이 전부 강조된 채 흐른다 |
| `{01}` | "줄 초기화" 로만 적혀 폭 계산에 안 들어갔다 | 행 카운터를 1로 되돌린다. 폭·줄 수를 잴 때 함께 나눠야 한다 |
| 길이 상한 | `302px` | **한글 25자.** 번역기가 셀 수 있는 단위여야 지켜진다 |
| 쓸 수 있는 글자 | 없던 항목 | 서로 다른 글자 하나가 882칸 중 하나를 먹는다. `【】` 는 뱅크0 에 없다 |
| `glossary.csv` 경로 | 내보내기 디렉터리에 없는 파일을 가리켰다 | `work/text/glossary.csv` |

### 자리표시자 판정은 두 번 틀렸다

**구조로 대사와 식별자를 가르려는 시도가 두 번 다 실패했다.**

1. "제어 코드 없는 짧은 항목 — 식별자 가능성" → 표본 **13건이 전부 진짜 대사**
   였다. 「……はい」, 『エリクサー』を手にいれた!, (SeeDは魔女を倒す……).
   전체에 적용했으면 대사 800여 건이 일본어로 남는다.
2. "라틴 소문자만 있는 줄" → 걸린 **4건이 전부 진짜**였다. `ON/OFF` 토글,
   지명 「FH」, 필드 983의 영어 가사.

남긴 것은 이름이 박힌 자리표시자(`だみー`, `てすと`)와 숫자만 있는 줄뿐이며
걸린 것을 전수로 눈으로 확인했다. 목록은 내보내기가 생성한다 — 손으로
관리하는 목록은 조용히 낡고, 그 낡음이 대사를 삼킨다.

## M5 판정 — 서브셋으로 간다

M5 의 마지막 전제는 **번역문의 서로 다른 음절 수 ≤ 882** 였다.

글자 수 전제부터 확인됐다. 그려지는 글자가 원문 대비 **0.98배**로 오히려
줄었다. 한국어가 길어질 것이라는 걱정은 근거가 없다.

### 882를 넘는다. 그래도 뱅크0 하나로 간다

실제 대사 8,154건 중 **8,120건(99.6%)**이 번역된 시점의 값이다.

| 항목 | 값 |
|---|---|
| 서로 다른 한글 음절 | **1,080** |
| 한글이 아닌 글자 | 55종 (원본 폰트에 있음) |
| 필드 전용 폰트에서 오는 글자 | 9종 — `ost■□◆◎【】` |
| **필요한 칸 합계** | **1,135 / 882 → 253 초과** |

전제는 깨졌다. 그러나 한국어 음절 빈도가 극단적으로 쏠려 있어 **잘려 나가는
것은 거의 안 쓰이는 음절**이다.

| 항목 | 값 |
|---|---|
| 한글에 쓸 수 있는 칸 | 827 |
| 고른 827자가 덮는 본문 | **99.753%** |
| 다시 써야 하는 메시지 | **303 / 8,120 (3.7%)** |

**어떤 음절을 버릴지는 우리 선택이고, 빈도순이 최적이 아니다.** 목적은 빈도
최대화가 아니라 손봐야 할 메시지의 최소화다. 드문 음절 둘이 같은 메시지에
있으면 둘 다 버려도 깨지는 메시지는 하나뿐이므로, 같은 메시지에 몰린 것부터
버리면 피해가 뭉친다. 욕심 알고리즘으로 바꿔 **327 → 303건**이 됐다.

바이트도 확인했다. 빈도순 배치를 적용하면 261필드 중 원본 총량을 넘는 것이
**29개뿐이고 최대 +17바이트**다. 최적 파싱 압축이 DAT 304개를 전부 원본보다
작게(평균 95.67%) 만들므로 흡수된다.

`count_korean_syllables.py` 가 칸을 넘길 때 이 판정을 자동으로 낸다. 고칠
자리는 `check_translation.py --layout` 의 "없는 글자" 가 짚는다.

재작업은 같은 문장을 여러 번 고쳐 쓰는 일이므로 **로컬 모델이 값을 하는
구간**이다.

### 추정이 언제부터 믿을 만해졌나

표본이 작을 때의 외삽은 쓸 수 없었다. 기록해 둔다.

| 시점 | 표본(고유 원문) | 실측 음절 | 전체 추정 |
|---|---|---|---|
| 21.9% | 4.7% | 461 | 745 ~ 3,094 — **못 쓴다** |
| 29.8% | 15.0% | 724 | 1,072 / 1,088 (두 구간 독립 적합) |
| 99.6% | 100% | **1,080** | — |

**중복 메시지를 빼지 않으면 추정이 낙관적으로 기운다.** 중복은 토큰만 늘리고
새 음절은 거의 안 늘려 Heaps 지수를 낮춘다. 중복을 포함해 적합했을 때는 745가
나왔고, 빼고 적합하니 1,072가 나왔다. 실측은 1,080이었다.

## 기계 초벌번역이 실제로 낸 오류

전수 8,120건을 검사한 결과다. 예산 초과(배치 전 보수 추정)를 빼면
**142건(1.7%)**만 손보면 된다.

| 종류 | 건수 |
|---|---|
| 구멍 남음 (`{b1:N}` 미해결) | 78 |
| 코드 누락·추가 | 42 |
| 줄 폭 초과 | 25 |
| 줄 수 초과 | 13 |
| 일본어 남음 | 1 |

지침이 명확하면 기계 번역은 구조를 지킨다. 초기 시범 361건에서는 구조 위반이
0건이었다.

### 배치가 오타를 정당화하고 있었다

배치를 **"번역문이 쓰는 음절"** 로 만들었다. 그러면 기계 번역의 오타 음절까지
칸을 받고, 검사기는 "배치에 있으니 괜찮다" 고 판정한다. **오타가 스스로를
정당화한 셈이다.**

갈무리는 KS X 1001 완성형 2,350자만 담는다. 그 밖의 음절은 그릴 수 없으므로
화면에서 빈칸이 되고, **거의 예외 없이 오타다** — 정상적인 낱말에 안 쓰이는
글자이기 때문이다. 전수에서 **39종 69회**가 나왔다.

```text
겑겚곷곹깄꾽꿤눖눥덐덝됙뒐듰땤땴떈떐뜾랝
랰뤌뫐븼뿘싨쌄쐳쓨앋엕왥잌쟖쟜쪻쵌쿯홐
```

맥락을 보면 전부 오타다 — `겑자기`(갑자기), `꿤 좋은`(꽤), `엕마 선생님`(엄마),
`이거 뫐지`(뭐지), `은혜는 겚는`(갚는), `안 쓨`(썼). 30필드 61건에 흩어져 있고
가장 큰 필드 `bgroom_6`(55건 중 12건, 22%)이 특히 나쁘다. 긴 필드에서 번역기가
무너진 것으로 보인다.

**정본은 번역문이 아니라 폰트다.** `build_hangul_font.covered()` 를 기준으로
검사기가 잡고 계수기가 칸을 주지 않게 했다. 39칸이 회수돼 다시 써야 할 메시지가
**305 → 269건**이 됐다.

### 검사기가 스스로 낸 오탐

"일본어 남음" 이 처음에 60건 걸렸는데 **전부 오탐**이었다. 정규식이 가타카나
블록 전체(`U+3040–30FF`)를 훑었고 그 안에 `・`(U+30FB)와 `ー`(U+30FC)가 있다.
이 둘은 뱅크0 에 실재하고 지침이 쓰라고 허용한 부호다. 블록째로 자르면 진짜
문제가 오탐 속에 묻힌다.

### 파일로 주고받을 때의 손상

긴 번역문이 실제 개행으로 쪼개져 오는 일이 있다. 탭이 없는 줄을 버리면 그
대사가 문장 중간에서 잘린 채 게임에 들어가므로, 되받기가 **앞 줄에 이어
붙이고 그 사실을 알린다.** 전수 21개 파일에서 3건 발생했다.

### 폰트가 못 그리는 글자

번역기가 지침의 글자 목록 밖을 쓰는 일이 있다. `--normalize` 가 뱅크0 에 있는
것으로 바꾼다. 판정이 두 겹이다 — 뱅크0 에 있으면 두고, 없더라도 **그 필드의
원문이 쓰는 글자면** 필드 전용 폰트에서 오므로 둔다.

| 바꾼 것 | 횟수 |
|---|---|
| `~` → `～` | 536 |
| `'` → 지움 | 24 |
| `·` → `・` | 4 |
| `―` → `-` | 3 |
| `o` → `O` | 1 |

`~` 가 536회인데 같은 번역문이 `～` 도 495회 썼다. 지침의 "부호를 한 벌로
통일한다" 를 어긴 것이고, 통일하면 칸이 하나 는다.

## 규칙

- 원작 대사의 완역본을 이 저장소에 담지 않는다. 도구와 워크시트, 그리고 기계
  번역을 검사·교정하는 데까지가 범위다
- 번역 초안은 `work/` 에 둔다. 추적하지 않는다
- 미확정을 확정으로 쓰지 않는다. 중간 집계는 중간 집계라고 적는다
