# 한국어화 이정표

작성일: 2026-07-28
대상: `Final Fantasy VIII (Japan, Asia) (Disc 1)`

이 문서는 **어디까지 왔고 다음에 무엇이 열려야 하는지**를 단계로 적는다.
각 단계에는 전제·산출물·통과 조건을 둔다. 통과 조건을 만족하지 못한 단계는
"진행 중" 으로 남기고 다음 단계를 확정으로 쓰지 않는다.

세부 근거는 각 절이 가리키는 정본 문서에 있다. 이 문서는 **색인이자
진행표**이며, 여기에 새로운 판정을 만들지 않는다.

## M1 — 컨테이너 해부 · 완료

ISO 루트에 파일이 3개뿐이고 게임 데이터 전부가 `FF8DISC1.IMG` 안에 있다.

- IMG 목차는 **LBA 826 의 첫 섹터**, `[u32 절대 LBA][u32 크기]` × **134**
- 목차는 런타임에 RAM `0x80099400` 으로 적재된다
- 모듈 적재는 3계층(`sub_80011E10` → 로더 스텁 → `sub_800385E4`)
- 오버레이 목적지와 **이름**이 EXE 안의 표 `0x80054340` 에 있다
- 필드 데이터는 목차 밖이며 `field.bin`(TOC#2)이 색인한다 — 엔트리 1,003개

**통과 조건**: 목차 엔트리 수가 코드 상수와 일치할 것. → 부트스트랩
`1,072바이트 = 134 × 8` 로 확인. ✔

정본: `docs/disc1-baseline.md`
도구: `scripts/psx_disc.py`, `scripts/trace_module_loader.py`

## M2 — 폰트 해독 · 완료

- 시스템 폰트 = IMG TOC **#130** (`sysfnt.tdw`), 12 × 12 셀, 4bpp 256 × 252
- 셀 하나에 글리프 **둘**이 인터리브 → 뱅크당 **882**
- 픽셀 시작은 **`0x05E4`** — CLUT 블록의 `blockSize` 1,036 이 정한다
- 인덱스 ↔ 문자 대응표(단일바이트 영역) 확정
- **필드마다 전용 추가 폰트(TDW)가 MIM 섹션 3 에 있다**

**통과 조건**: 확정한 인덱스로 렌더한 글리프가 기대 문자와 일치할 것.
→ 74·38·150·76·78·80·82·138·106·136·114·128·14·223 이 순서대로
カ ド ワ キ ク ケ コ ル ア リ ナ ム グ ー 로 재현. ✔

정본: `docs/font-analysis.md`
도구: `scripts/build_hangul_font.py`

## M3 — 텍스트 경로 · 완료

출력 파이프라인과 두 계열의 메시지 저장 형식을 확정했다.

```text
메뉴 계열   mngrp.bin(TOC#22) 서브 1 → RAM 0x801E1000
            2단 u16 상대 오프셋 표, 값 0 은 빈 슬롯
            그룹 16, 메시지 579

필드 계열   field.bin → 목록 → 필드 DAT → 섹션 포인터 [8] = MSD
            [u32 오프셋 배열], 첫 값이 배열 끝 (N = offset[0] / 4)
```

**통과 조건**: 두 형식 모두 파싱 결과가 100% 정합할 것.
→ 메뉴 579/579 정상 종료, 위반 0건. ✔
→ 필드는 앞 140개 DAT 표본에서 5,445/5,445 였고, 이후 목록 1,003엔트리를
  전수로 훑어 **DAT 302개 / 메시지 9,442건, 위반 0건**으로 확장했다. ✔
→ 렌더 결과가 실제 일본어로 읽힐 것. ✔

정본: `docs/font-analysis.md`

## M4 — 텍스트 전수 추출 · 진행 중

지금까지는 **표본**이다. 전수로 올려야 한다.

| 할 일 | 상태 |
|---|---|
| 필드 목록 1,003엔트리를 MIM/DAT/LZK 로 전수 분류 | 전수 완료 — DAT 302개 |
| 모든 필드 DAT 의 MSD 를 뽑아 통합 텍스트 DB 구성 | 완료 — `scripts/build_text_db.py` |
| `mngrp.bin` 의 나머지 서브엔트리에 텍스트가 더 있는지 확인 | 미착수 |
| 2바이트 영역(인덱스 224 이상) 대응표 | 판독 완료 — 픽셀 있는 879자 전부 |
| 필드 전용 TDW 를 필드별로 대응표에 반영 | 53/820 판독 (등장 44.5%) |
| 번역 워크시트 내보내기·되받기·검사 | 완료 |

### 줄과 쪽을 재는 규칙을 고쳤다

내보내기와 검사기가 줄을 `{02}` 로만 나눴다. `{01}` 은 행 카운터를 1로
되돌리므로(`sub_8002E4A0` 확정) 이것으로도 줄이 끊기는데 나누지 않아, 쪽
경계를 넘는 글자가 한 줄로 합산됐다. 842건이 이 코드를 쓴다.

| 나누는 방식 | 최대 줄 폭 | 302px 초과 |
|---|---|---|
| `{02}` 만 | 659px | 303건 |
| `{02}` + `{01}` | **448px** | **3건** |

상한 302px 은 원본 #293/#296/#299 의 줄 387개로 정한 값인데, **그 세 필드가
하필 이 결함에 둔감했다.** 전수 26,883줄로 다시 재니 99.9%가 299px 이하이고
넘는 줄은 3개뿐이며 셋 다 디버그·미판독 텍스트다. 상한 자체는 성립한다.

`{b1:N}` 은 제어 코드가 아니라 화면에 그려지는 글자인데 폭 계산에서 제거되고
있었다. 두 규칙을 `scripts/text_metrics.py` 로 모아 세 도구가 함께 쓴다.

바이트 셈은 항등 시험으로 검증했다 — `ko` 에 `ja` 를 그대로 넣으면 9,160건
전부 원본 바이트 수와 정확히 일치한다.

### 번역 대상의 실제 크기

전체 메시지 9,160건 중 **3,172건(34.6%)이 다른 곳에도 똑같이 있는 원문**이다.
고유 원문은 6,667종뿐이고, 카드 규칙 안내문 하나가 60곳에 반복된다. 필드마다
따로 번역시키면 번역량이 37% 늘고 같은 문장이 수십 가지 표기로 갈린다.
`import_translation.py --propagate` 가 원문 기준으로 채우고 갈린 것을 알린다.

한때 쓰던 `do-not-translate.csv` 의 "제어 코드 없는 짧은 항목 — 식별자 가능성"
판정은 **표본 13건이 전부 진짜 대사였다** — 「……はい」,
『エリクサー』を手にいれた!, (SeeDは魔女を倒す……). 전체에 적용했으면 대사
800여 건이 일본어로 남는다. 길이나 제어 코드 유무로는 자리표시자를 못 가른다.

**통과 조건**
1. 추출한 텍스트를 **다시 원본 바이트로 되돌렸을 때 완전 일치**(round-trip).
2. 텍스트 DB 의 모든 글리프 인덱스가 해당 필드에서 실제로 그릴 수 있는
   범위 안에 있을 것.

**막는 요소**: 없다. 바로 진행 가능하다.

### 항목 6 결론 — 전투 이름 글꼴을 찾았다 (2026-08-07)

**이름은 낱글자로 그려지지 않는다. 통짜 이름 그림이 VRAM 에 조립돼 있다.**

전투 화면(`キスティス 501` / `パぽ 486`)을 정지시켜 뜬 뒤, 화면 글자의 픽셀
모양으로 VRAM 전체를 역검색해 **100% 일치가 한 곳** 나왔다.

| 항목 | 값 |
|---|---|
| 이름 띠 VRAM 자리 | halfword `x≈900..958`, `y≈352..380` (전투 UI 시트 `x896..960` 구역 안) |
| `キスティス` 의 `ス` | 4bpp 픽셀 `(3639, 352)`, 13×12 |
| 형식 | 4bpp 텍스처. 안티에일리어스 계조 + 어두운 외곽선이 구워져 있다 |

이 띠는 **전투 진입 때 조립된다** — `パぽ` 는 플레이어가 넣은 이름이라 디스크에
미리 그려져 있을 수 없다. 그래서 조립에 쓰는 글꼴을 RAM 에서 찾았다.

**조립용 글꼴 = 제3의 일본어 가나·영문 시트** (`work/analysis/battle-font/`)

| 항목 | 값 |
|---|---|
| 런타임 주소 | **`0x801b8e00` ~ `0x801bd000`** (16,896B, 132줄) |
| 스트라이드 | `128B` = 4bpp 픽셀 **256 폭** (뒤 4px 는 격자 밖) |
| 격자 | 12×12 셀, 원점 `(0,0)`, **21열 × 11줄 = 231칸** (220칸에 글자) — 뱅크0 와 같은 구조 |
| 확인된 글리프 | `キ` = `0x801ba05a` = 저장 열 15, 줄 3 (12행 전부 일치) |
| 배치 | **카타카나 뒤에 짝 히라가나** (`ハ は ヒ ひ フ ふ …`). 알파벳은 `A..Z` 연속 |
| **저장 방식** | 격자가 아니라 **12픽셀씩 이어 붙인 연속 스트림**이고 **원점이 24픽셀(2칸) 밀려 있다** |

**격자가 아니다.** `256` 은 `12` 로 나눠떨어지지 않는다(`256 = 21×12 + 4`).
줄 끝에 남는 4픽셀에 글자의 왼쪽이 걸치고 나머지 8픽셀은 **다음 버퍼 줄의
머리**로 넘어간다. 버퍼를 그냥 256폭 그림으로 보면 그 글자들이 **1픽셀 아래로
내려가 보이고 왼쪽 4픽셀이 잘려 보인다.** (사용자 지적으로 두 단계에 걸쳐 잡음,
2026-08-07)

버퍼를 선형 픽셀 배열 `P[k]`(`k = 버퍼줄 × 256 + x`)로 보면 한 줄로 정리된다:

```
셀 (b, c) 의 글자행 j, 글자내 x = i 인 픽셀
    k = (12·b + j) × 256 + 24 + 12·c + i        b = 줄 0..10, c = 열 0..20
선형 인덱스 = b × 21 + c
```

**팔레트도 확보했다.** CLUT 뱅크가 VRAM `(256, 224)` 부터 **16벌 × 16칸**으로
있고, 이 글꼴은 `y=226`(회색 계조)을 쓴다. 같은 글꼴에 `y=227`(붉은 계조)을
입힌 것이 메뉴의 빨간 글씨(`PLAY TIME`, `EXP`)다. `y=226` 값:

```
0000 b9ce ffff f39c eb5a e318 d6b5 ce73 c631 bdef b5ad ad6b a529 9ce7 94a5 8c63
회색 0~31:  -  14  31  28  26  24  21  19  17  15  13  11   9   7   5   3
인덱스 0 = 0x0000 = 투명, 2 가 가장 밝고 15 가 가장 어둡다
```

찾은 방법: 화면에 그려진 이름 픽셀과 VRAM 텍스처 인덱스를 1:1 대응시켜
인덱스→색을 실측하고, 그 조합을 담은 16칸을 VRAM 전체에서 찾았다(유일하게 1곳).

`c = 19, 20` 은 이 식만으로 자동으로 줄을 넘어가며 걸쳐 읽힌다. 검산: `キ` =
버퍼 `(x=180, 줄 36)` → `k = 9396 = (12×3+0)×256 + 24 + 12×13` → `b=3, c=13`,
선형 인덱스 **76**. 식으로 다시 그리면 `キ` 가 나온다. 알파벳도 줄 8 이
`ウぅエぇオぉ A B C … M N O`, 줄 9 가 `P Q R S …` 로 **`A..Z` 연속 26칸**이 된다.

**이 글꼴은 우리가 한 번도 건드리지 않았다.** 뱅크0/뱅크1 도 아니고
`work/font/bank0*.bin` 어느 것도 아니며, 디스크 원본에서도 묶음 4bpp 로는 안
나온다(= 어느 아카이브 안에 **LZSS 압축**돼 있다).

같은 시트가 **작은 메뉴 글자**도 그린다. 세이브/스테이터스 화면의 빨간 글씨가
`PLAY→PLBZ`, `DISC→DJTD`, `EXP→FXP`, `LEVEL→FVFL` 로 깨지는데, 전부
**짝수 자리 글자만 정확히 +1** 이다(A→B, I→J, S→T, C→D, E→F). 알파벳이
이 시트에 `A..Z` 연속으로 있으니 오프바이원의 출처가 여기로 확정된다.

```
    CLUT   VRAM (256,224) 16x16      팔레트 16벌
    이미지 64halfword x 132행 = 256x132 px 4bpp
    런타임 0x801b8cec (픽셀은 +12바이트 이미지 헤더 뒤)
```

**TIM 17,184B 가 RAM 덤프와 바이트 하나 안 틀리고 일치**한다.

`scripts/patch_battle_font.py` 가 원본에서 읽어 해제 → TIM 교체 → 재압축 →
사본에 쓴다. 재압축이 **101,324B(50섹터)** 로 원본(103,238B, 51섹터)보다 작아
뒤 파일이 안 밀린다. 되읽기·해제까지 확인한다.

**+12바이트 이미지 헤더가 곧 그 「2칸 밀림」이었다.** 사용자가 "왼쪽 2열이
오른쪽으로 가야 한다"고 짚은 것을 경험적으로 `+24픽셀` 오프셋으로 맞췄는데,
TIM 을 찾고 보니 그 24픽셀이 정확히 이미지 블록 헤더 12바이트였다. CLUT 자리
`(256,224)` 도 실측으로 찾아 둔 CLUT 뱅크와 그대로 맞는다.

#### 찾는 데 오래 걸린 이유 — 헛다리 기록

| 시도 | 결과 |
|---|---|
| 디스크 평문 검색 (732MB, 키 20개) | 0곳 |
| 니블 뒤집기·바이트 역순·16비트 스왑 | 0곳 |
| IMG 목차 134개 LZSS 전수 해제 | 0곳 |
| 아카이브 하위 항목(섹터 경계 후보 187곳) | 0곳 |
| 전투 모듈 아카이브 TOC#26 을 4바이트 단위 전수 해제 | 0곳 |
| 쓰기 감시점 `0x801b8e00` | 공용 스트리밍 버퍼라 노이즈만 (CD DMA·메뉴 루프) |

**함정은 「IMG 목차가 곧 디스크의 목록」이라고 본 것이다.** ISO 파일은 셋뿐이고
(`SYSTEM.CNF`, `SLPS_018.80`, `FF8DISC1.IMG` 636MB) 목차 134개는 IMG 의 극히
일부만 가리킨다. **목차를 무시하고 전 섹터(310,543개)를 훑자 한 번에 나왔다.**

풀린 결정적 실마리는 RAM 에서 **TIM 헤더(`magic 0x10`)** 를 찾은 것이다. 픽셀을
키로 쓰면 압축된 원본에 안 걸리지만, TIM 이라는 것을 알면 컨테이너를 풀어 놓고
헤더로 찾을 수 있다.

### (옛) 아카이브 추적 — 1차 시도 결과

**아직 못 찾았다.** 그러나 후보가 크게 줄었고, 헛다리를 확정해 두었다.

| 확인한 것 | 결과 |
|---|---|
| 글꼴이 상주하는가 | **아니다.** RAM 에 한글 글꼴을 주입(`gdb_poke.py`, 되읽기 일치)한 뒤 전투에 다시 들어가니 **원본 일본어로 바이트 하나 안 틀리고 되돌아갔다**(16,896B 중 차이 0). 전투 진입 때마다 다시 실린다 |
| 디스크에 평문으로 있는가 | **없다.** 원본 732MB 전수 검색 0곳 |
| IMG 목차의 LZSS 블록인가 | **아니다.** 목차 134개 전수 해제 0곳 |
| 아카이브 하위 항목인가 | **아니다.** 섹터 경계 10,028곳 중 해제크기가 그럴듯한 187곳 전수 해제 0곳 |

**따라서 CPU 가 압축을 풀어 그 자리에 쓴다.** 잡아야 할 것은 DMA 가 아니라
해제기의 쓰기다.

**`0x801b8e00` 주변은 여러 스트림이 공유하는 버퍼다.** 그래서 감시점이 아무
때나 걸린다 — `docs/lessons.md` 13-1 과 같은 함정이다. 실제로 잡힌 것:

```
PC=0x80044f48  ra=0x80043810  a0=0x801b8800   CD -> RAM DMA (DMA3 CHCR 0x1f8010b8)
                                              그 섹터는 디스크 LBA 88037/129225 에 평문으로 있다 (글꼴 아님)
PC=0x800c15b8  ra=0x800a33f4  a0=0x8015~0x8017 대  메뉴 모듈의 뜨거운 루프 (수십 회 연속)
```

PC 로 걸러 해제기 구간(`0x800393A4`~`0x800394F8`)만 잡으려 했으나, 그 구간의
쓰기는 15분 안에 안 걸렸다. 전투 재진입이 관측 창에 안 들어왔을 수 있다.

**다음에 시도할 것**

1. **감시 주소를 바꾼다.** `0x801b8e00` 은 공용 버퍼라 노이즈가 심하다.
   글꼴 블록 **한복판**(예: `0x801ba05a`, `キ` 자리)에 걸면 다른 스트림이
   덜 밟는다.
2. **폴링으로 먼저 시각을 잡는다.** 웹 API 로 그 자리를 짧게 폴링하며
   「원본 글꼴이 나타나는 순간」을 잡고, 그 직전 구간만 감시점으로 좁힌다.
3. `sub_80035C84` 가 LBA 를 읽는 `dword_80099420[2*archive_idx]` 표를 정적으로
   떠서, **목적지가 `0x801a0000`~`0x801c0000` 인 아카이브**를 후보로 추린다
   (항목 7 의 `trace_module_loader.py` 가 이미 이 표를 판다).
4. 압축 형식이 LZSS 가 아닐 수 있다. 목적지 주변에 남은 **원본 압축 스트림**을
   RAM 에서 찾아 형식을 역으로 본다.

**다음 행동**

1. 이 시트가 **어느 디스크 파일**에서 오는지 확정한다. 압축돼 있으므로
   `scripts/lzss.py` 로 후보 아카이브를 풀어 `battle-name-font.bin` 조각을
   찾는 방식이 빠르다. 전투 모듈 적재 경로(항목 7)와 같은 아카이브일 수 있다.
2. 시트의 **격자 원점과 인덱스↔셀 대응**을 확정한다(`키` 는 버퍼 행 64 기준
   세로 위상 8, 가로 셀 15).
3. 한글 시트를 만들어 같은 자리에 끼운다. 12×12·21열이라 뱅크0 생성기
   (`build_hangul_font.py`)의 셀 배치를 거의 그대로 쓸 수 있다.
4. 짝수 글자 +1 밀림도 같이 푼다 — 시트를 갈면 증상이 바뀌므로 그때 재측정한다.

정본 자료: `work/analysis/battle-font/`(덤프 + PNG + README). **`work/` 는
gitignore 대상이라 저장소에 없다** — 전투 화면에서 다시 뜬다:

```
python3 scripts/find_vram_source.py --rect 164 173 13 12 --ram
```

`--rect` 는 화면에 뜬 이름 글자 하나의 사각형이다(위 값은 `キスティス` 의 `キ`).
에뮬레이터를 **멈춘 상태**로 두고 돌려야 화면과 텍스처가 같은 프레임이 된다.

#### 폐기된 단서 (다시 파지 말 것)

- 뱅크1(832,256) 프레임 내 재사용 가설 — 60연속 폴링 변화 0회 (2026-08-06)
- 전투 모듈 내부 스프라이트 스트리밍(`sub_8009EA1C` / `sub_8009EAC8`) 추적 —
  이름 글꼴과는 무관했다. 아래 옛 메모는 기록용으로만 남긴다.

### (옛) 인계 메모 — 항목 6, 전투 이름 글꼴 추적 (2026-08-06)

전투 HP/이름 표시(`キスティス 390`)의 글꼴 출처를 찾다가, **전투 모듈
(`0x8009BD30`) 안에 자체 스프라이트/애니메이션 시스템**을 발견했다. 이게
가장 유력한 다음 단서다.

- `sub_8009EA1C`(모듈 내 오프셋 `0x2CEC`) — **스프라이트 레코드 파서**.
  커서 포인터(a0)를 계속 전진시키며 `[플래그/카운트][선택적 CLUT
  w·h·포인터][x,y][w,h][픽셀데이터 포인터]`를 순서대로 읽어 출력 구조체에
  채운다. TIM 과 형태는 비슷하지만 **연속 스트림**이라 오프셋 없이 순서로만
  다음 레코드를 찾는다.
- `sub_8009EAC8`(모듈 내 오프셋 `0x2D98`) — **레코드 0x10바이트짜리 표를
  순회하며 `sub_800386B0`(CD 읽기) + `sub_8003924C`(상태 머신 펌프)로
  디스크에서 스트리밍**한다. 이게 `docs/lessons.md` 13-1 에서 "배경음악
  스트리밍"으로 오판했던 그 반복 CD 요청의 진짜 정체일 가능성이 높다 —
  목적지가 매번 다르고(`0x801a0000`, `0x8010640c`, `0x80122000` 등)
  전투 중에만 도는 것과 정확히 들어맞는다.
- 호출 지점 3곳(`0x8009e480`/`0x8009e5f4`/`0x8009ed08`)이 전부
  `sub_8009EA1C`를 부르는데, 커서 시작 주소(a0)는 **오프셋 표 조회**로
  나온다(`0x800a9c30`~`0x800a9c7c`): `a0 = a3 + *(a3 + index*4)` — `a3`
  가 표 기준 주소, `index` 는 애니메이션 프레임 번호 같은 계산값(나눗셈
  두 번으로 나옴, 프레임 카운터 순환으로 추정). `a3` 의 실제 값은 아직
  안 쫓아갔다 — 더 위 호출자를 봐야 한다.

**다음에 시도할 것**

1. `a3`(오프셋 표 기준 주소)를 마저 쫓아 **모듈 안의 고정 오프셋**인지
   확인한다. 고정이면 `work/analysis/`에 저장해 둔
   `scratchpad/combat_module.bin`(이번 세션에 뜬 `0x8009BD30` 111,304B
   전체 덤프 — 세션 스크래치패드라 휘발성, 재현하려면 전투 진입 상태에서
   `cpu/ram/raw` 웹 API로 다시 뜬다)에서 표 전체를 정적으로 읽는다.
2. 표의 각 엔트리가 가리키는 스프라이트 레코드를 `sub_8009EA1C`와 같은
   순서로 파싱해 CLUT+RECT+픽셀 포인터를 뽑고, 그중 **텍스트 모양(획이
   가는 가타카나 폭)인 것**을 찾는다. TIM 이 아니라 커서 스트림이므로
   `psx_disc.py`의 TIM 파서를 그대로는 못 쓰고 이 레코드 형식에 맞는
   파서를 새로 짠다.
3. `sub_8009EAC8`의 CD 읽기 목적지들을 다시 감시점으로 잡되, 이번엔
   "배경음악"으로 넘기지 말고 **각 목적지를 4bpp+CLUT으로 렌더해 글자
   모양을 찾는다** — `docs/lessons.md` 14번(팔레트 없이 보면 절반이
   사라진다)을 반드시 지킨다.
4. 뱅크1(832,256) 재사용 가설은 **기각됐다**(60연속 폴링 1.5초 동안 변화
   0회, 2026-08-06) — 다시 시도하지 않는다.

## M5 — 한글 폰트 탑재 · 진행 중

`scripts/build_hangul_font.py` 가 FF8 형식 뱅크를 만든다. 뱅크 0 은
882자를 담고 완성형 2,350자에는 모자란다.

### R1 — 뱅크 1 을 쓸 수 없다 (경로 확정)

이전 계획은 "뱅크 1 이 비어 있으니 적재 호출을 넣자" 였다. **전제가 틀렸다.**

- 필드 MSD 가 `0x1C` 리드를 표본에서 **4,950회** 쓴다
- 그 인덱스 범위가 해당 필드 MIM 의 TDW 글리프 수와 정확히 맞물린다
  (예: TDW 84글리프 ↔ 인덱스 0..56, TDW 126글리프 ↔ 인덱스 0..123)
- 즉 **뱅크 1 자리는 필드마다 내용이 바뀌는 자리**다

남은 선택지는 셋이었고 **초벌번역 실측으로 ③을 골랐다.**

| 안 | 내용 | 위험 |
|---|---|---|
| ① VRAM 확장 | 빈 구간 `x=320..512, y=256..508`(추정)에 뱅크를 새로 추가 | 점유 맵이 정적 RECT 기반이라 필드 배경의 런타임 점유를 반영하지 않는다 |
| ② TDW 재생성 | 필드 전용 TDW 를 한글로 다시 만든다 | 필드 수만큼 작업이 늘고, 필드마다 쓸 수 있는 글자가 달라진다 |
| ③ 서브셋 | 뱅크 0 안에서 882자로 해결 | **채택.** 초벌번역 실측으로 아래에서 판정했다 |

### 바이트 제약은 풀렸다 (측정, 추정 포함)

`scripts/analyze_text_budget.py` 가 DAT 302개를 전수로 재본 결과다.
③을 가로막는 것은 **칸 수가 아니라 바이트**였고, 배치를 정하면 들어간다.

| 항목 | 값 |
|---|---|
| 일본어 원문이 쓰는 뱅크0 칸 | 840 / 882 |
| 글리프 인코딩 폭 | 1바이트 84.7%, 2바이트 15.3% |
| 지금 글자당 평균 | **1.15바이트** |
| 가장 잦은 224자가 덮는 본문 비율 | **93.00%** |

인덱스 `0..223` 은 1바이트, `224` 이상은 2바이트로 실린다. 한글 음절을 전부
224 뒤에 놓으면 본문이 1.74배가 된다.

| 시나리오 | 탐욕 압축 | **최적 파싱 압축** |
|---|---|---|
| 손대지 않고 재압축만 | 2개 초과 | **0개** |
| 한글을 전부 224 뒤에 (최악) | 27개 초과 | **0개** |
| 빈도 상위 224자를 1바이트 자리에 | 0개 초과 | **0개** |

**압축기를 고치자 최악 시나리오조차 전부 들어간다.** 302개 필드 중 넘치는 것이
하나도 없다. 배치 최적화는 이제 필수가 아니라 여유를 늘리는 수단이다. 그래도
빈도 상위 224자를 1바이트 자리에 놓으면 글자당 평균이 1.07바이트로 지금(1.15)
보다 작아지므로 그렇게 배치하는 편이 낫다.

**주의**: 최악 시나리오는 **번역문의 글자 수가 원문과 같다**고 본 것이다. 번역이
길어지면 그만큼 여유가 준다. 빈도 쏠림 수치도 일본어 원문을 한국어의 대리 지표로
쓴 것이라 실제 값은 번역 초안에 같은 도구를 다시 돌려 재야 한다.

### ③의 남은 전제 — 판정했다

**번역문의 서로 다른 음절 수 ≤ 882.** 이것이 마지막 전제였다.

전수 기계 초벌번역을 끝내고 셌다. 디버그 필드를 뺀 **실제 대사 8,154건 중
8,120건(99.6%)**이 번역된 시점의 값이다.

| 항목 | 값 |
|---|---|
| 서로 다른 한글 음절 | **1,080** |
| 한글이 아닌 글자 | 55종 (원본 폰트에 있음) |
| 필드 전용 폰트에서 오는 글자 | 9종 — `ost■□◆◎【】`. 칸을 안 먹는다 |
| **필요한 칸 합계** | **1,135 / 882 → 253 초과** |

**전제는 깨졌다.** 그러나 ③은 죽지 않았다.

### 칸이 모자라도 ③으로 간다 — 서브셋 판정

한국어 음절 빈도가 극단적으로 쏠려 있어 **잘려 나가는 것은 거의 안 쓰이는
음절**이다.

| 항목 | 값 |
|---|---|
| 한글에 쓸 수 있는 칸 | 827 |
| 상위 827자가 덮는 본문 | **99.754%** |
| 잘리는 음절 | 253종 |
| **다시 써야 하는 메시지** | **327 / 8,120 (4.0%)** |

즉 **뱅크0 하나로 가고 대사의 4%만 고쳐 쓰면 된다.** 고칠 자리는 기계가
짚는다 — `check_translation.py --layout` 의 "없는 글자" 검사다.

바이트도 확인했다. 빈도순 배치를 적용하면 261필드 중 원본 총량을 넘는 것이
**29개뿐이고 최대 +17바이트**다. 최적 파싱 압축이 이미 DAT 304개를 전부
원본보다 작게(평균 95.67%) 만들므로 흡수된다.

글자 수 전제도 확인됐다. 시범 필드에서 그려지는 글자가 원문 2,117 → 번역
2,077 로 **오히려 0.98배**였다. 한국어가 길어질 것이라는 걱정은 근거가 없다.

**남은 것**: ①·②로 돌아갈 필요가 없다. 서브셋 배치를 확정하고 걸리는 327건을
다시 쓴 뒤 폰트를 만든다. `build_hangul_font.py` 가 배치 후보를 그대로 받는다.

정본: `docs/translation-pipeline.md`

### R2 — 뱅크 1 적재 경로 미확정

`jal sub_8002C358` 은 디스크 전체에 **1곳**(런타임 `0x80011CDC`)뿐이고
뱅크 인자가 `0` 이다. TDW 는 다른 경로로 VRAM `(960,256)` 에 올라간다.
그 경로를 모르면 ①·②의 코드 패치를 설계할 수 없다.

**다음 행동**: 런타임 검증(M6 게이트)과 함께 푼다.

정본: `docs/font-analysis.md`, `docs/korean-font-feasibility.md`

## M6 — 재조립·검증 · 미착수

### 크기 제약 (이미 확정된 사실에서 나온다)

- **IMG 목차는 절대 LBA 를 담는다.** 파일 크기를 바꾸면 뒤 파일이 밀려
  목차 전체를 다시 써야 한다 → **크기 유지 in-place 교체가 기본**
- 아카이브 서브엔트리는 오프셋을 `>> 11` 하므로 **섹터 정렬**이다
- `field.bin` 의 필드 목록도 절대 LBA 다 → 필드 파일도 같은 제약

### 압축기 — 최적 파싱으로 원본을 앞선다

한때 필드 167 과 281 은 원본을 풀었다 다시 압축하기만 해도 섹터를 하나 더
먹었다(+50B, +78B). 데이터 문제가 아니라 **탐욕적 매칭이 원본보다 조금 나빴던**
것이고, 두 필드가 하필 섹터 경계에 붙어 있었다.

이 형식은 비용 모델이 단순하다. 리터럴은 1바이트 + 제어 1비트 = 9비트, 일치는
2바이트 + 제어 1비트 = 17비트뿐이고 **오프셋은 비용에 영향이 없다.** 일치는 잘라
써도 유효하므로 위치별 최장 일치 길이만 알면 뒤에서 앞으로 DP 를 돌려 최소 비용
경로를 정확히 구할 수 있다. `scripts/lzss.py` 가 이렇게 한다.

| 필드 | 원본 | 탐욕 | **최적 파싱** | 섹터 |
|---|---|---|---|---|
| 167 | 18,417B | 18,467B | **17,601B** | 9 → 9 ✔ |
| 281 | 28,634B | 28,712B | **27,250B** | 14 → 14 ✔ |

전수 검증: DAT **304개 전부 무손실**이고 **304개 전부 원본보다 작다.** 합계
3,553,865B → 3,400,018B (95.67%). 섹터 초과 0건이다. 여러 필드는 오히려 섹터를
덜 먹는다(예: 14 → 13).

### 통과 조건

1. **무수정 round-trip**: 추출 → 재조립 결과가 원본과 바이트 동일
2. 변경 sector 만 올바른 EDC/ECC 로 다시 만들고, 변경하지 않은 sector 는
   바이트가 그대로일 것
3. Mode 2 Form 1/2 판정과 복제 subheader 를 보존할 것
4. **런타임 확인**: 실행기에서 VRAM·RAM 이 정적 판정과 일치할 것

**막는 요소**: 런타임 게이트가 아직 열리지 않았다. DuckStation 실행 파일을
확인하지 않았고 BIOS 는 저장소에 두지 않는다.

정본: `AGENTS.md` 하드 불변식, `docs/reverse-engineering-mcp.md`

### R7 — MSD 교체가 같은 필드의 다른 섹션을 깨뜨린다

오프닝 수직 관통 시험에서 드러났다. 보건실(296)은 정상이었으나 **복도(350)에서
키스티스가 사라지고 배경이 깨졌으며 이어지는 동영상이 재생되지 않았다.**

`splice_msd` 는 MSD 섹션을 갈아 끼운 뒤 그 뒤 포인터(9, 10, 11)를 늘어난 만큼
민다. 포인터 자체는 맞게 밀리지만 **섹션 안에 든 값이 옛 주소를 가리키고 있으면
같이 밀리지 않는다.** 필드 스크립트(JSM)나 다른 섹션이 절대 주소로 서로를
참조한다면 이 방식으로는 깨진다.

확인해야 할 것

1. 섹션 9, 10, 11 이 각각 무엇인지 (아직 확정하지 않았다)
2. DAT 안에 절대 주소를 담은 자리가 더 있는지
3. 296 은 MSD 가 207바이트 늘었는데 멀쩡하고 350 은 93바이트 늘었는데 깨졌다.
   **크기 증가량이 원인이 아니다.** 섹션 구성 차이를 봐야 한다
4. 동영상 미재생이 350 때문인지 299(`bghoke_3`, 「キスティス登場ムービー」)
   때문인지 — 299 도 함께 고쳤으므로 하나씩 되돌려 갈라야 한다

**우회안이 실측으로 성립한다.** MSD 를 원본과 같은 크기로 유지하면 뒤 섹션이
한 바이트도 안 밀려 R7 이 애초에 발생하지 않는다. 문제는 "번역문이 그 안에
들어가는가" 였고, 이제 쟀다.

`patch_disc.py --fit` 이 필드마다 번역문을 실제 바이트로 인코딩해 원본 MSD
크기와 견준다.

| 결과 | 필드 |
|---|---|
| **원본 크기 안에 들어간다** | **126개 (92.0%)** |
| 근소 초과 (≤32B) | 10개 |
| 초과 | 1개 — `test1`(디버그), +53B |

**92% 는 R7 이 원천적으로 발생하지 않는다.** `rebuild_msd` 가 작아진 만큼을
종료 바이트로 채운다. 메시지 수는 `offset[0] / 4` 로 정해지므로 마지막 메시지
뒤의 남는 바이트는 읽히지 않는다. 무수정 재구성이 원본과 바이트까지 동일한
것을 확인했다.

남은 11개는 비-디버그 최대가 +19B 라 문장을 조금만 줄이면 들어간다.

이 결과는 **배치 순서에 크게 의존한다.** 1바이트 자리(0..223)에 상위 224

## 판정의 근거를 다루는 규칙

1. 정적 분석 결과는 **실행 검증과 연결되기 전까지 추정**이다.
2. 두 정적 도구가 같은 결과를 내더라도 **잘못된 base 나 코드/데이터 경계를
   공유했다면 독립 증거가 아니다.**
3. 외부 자료는 탐색 방향에만 쓴다. 대조 결과는 `docs/external-sources.md`.
4. 검증에 실패하면 실패했다고 남긴다. 미확정을 확정으로 쓰지 않는다.
